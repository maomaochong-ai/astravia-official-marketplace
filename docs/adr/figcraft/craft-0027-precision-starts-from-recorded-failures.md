# craft-0027 — 精度从记录开始，不从换感知栈开始

- **Status:** Accepted
- **Date:** 2026-11-09
- **Context:** craft 系列 0.0.26
- **Related:** [0024](craft-0024-the-agent-stays-in-the-frame.md) — 通道只剩像素、
  [0026](craft-0026-act-says-what-it-expects.md) — 判对错需要期望

## The situation

调研里最诱人的补法是把感知层往上抬一格：OCR 把"点菜单"变成"点名字"，
图标检测接住工具栏那些没字只有形状的按钮，可访问性树在有原生控件的应用里直接给出元素
（业界确实这么分层：可访问性树 → OCR → 截图，逐级升级，见 `clawdcursor`、`OmniParser`、`PaddleOCR`）。

但这条路在这个插件上有两个具体障碍：

1. **依赖与体积是一次跃迁。** OCR 要么带模型文件，要么带 WASM 运行时；图标检测还要权重。
   它们换来的收益取决于任务分布——如果用户大多在画布中心做连续手势，收益接近零。
2. **中文字形把"文字锚点"钉死在英文界面上。** 上游 web 构建只烘了 Latin + 一款日文字体，
   简体专属字形画不出来（[0022](craft-0022-a-document-outlives-its-tab.md) 已记）。
   也就是说：中文界面下 OCR 读到的是一串方块与日文变体，`click_text("图层")` **必然**失败。
   一旦引入文字锚点，就把"界面语言"绑进了定位链路。

在拿到真实失败样本之前，这两个代价都没法评估——而现在**样本根本留不下来**：
`act` 的返回只在会话里存在，会话结束就没了。

## The decision

**本轮不加感知依赖；先把失败记下来。**

- `act` / `probe` 每次把一行追加到 `.craft/<APP.id>/runs/<yyyymmdd>.jsonl`：
  `{at, tool, steps, change, assert, shot, elapsedMs}`。保留最近 7 个文件，超出的删掉
  （与 `shots/` 的 6 张同一套保留策略：记录不该悄悄把仓库灌满）。
- **升级判据写死**：攒到 20 条以上 `change.changed === false` 的点击轨迹，
  且其中多数是"菜单/面板项点不中"而不是"手势本身无效"，锚点才值得做。达不到就一直不做。
- **如果做，形状先定死**：只允许两种锚点——(a) OCR 文本框中心，(b) 图标 bbox 中心；
  `op: "click_text"` 走 (a)，并且**只在英文界面（`hl=en`）上定位**；拒绝多尺度模板匹配
  （跨缩放的误报会把"没找到"变成"找到错的"，比失败更贵）。

## Why not decide the perception stack now

因为"要不要 OCR"不是一个可以靠推理定的问题，是一个要靠样本定的问题。
现在拍板，要么凭空加依赖（用户为此付费、为此等下载），要么凭空拒绝（下一轮又要重开一次讨论）。
记录把这个问题变成可结算的：20 条轨迹之后，答案自己会出来。

## What this does not do

- **它不提升精度。** 这一轮精度的提升全部来自 [0025](craft-0025-settled-means-quiet-not-identical.md) 与
  [0026](craft-0026-act-says-what-it-expects.md)；0027 只负责让下一轮有据可依。
- **它不做回放。** 记录是给人/模型读的轨迹，不是可重放的宏。要回放得连输入事件一起存，
  那是另一个问题（`OpenAdapt` 那类做法）。
- **它不含隐私设计。** `.jsonl` 里有步骤文字与可能含内容的截图文件名；它写在项目里，跟着项目走。
  真要对敏感场景兜底，得另加开关。
