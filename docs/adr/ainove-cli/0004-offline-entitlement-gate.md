# ADR 0004：离线特权状态校验用签名凭证，且只作为本地门禁

- 状态：已接受（2026-10-29）
- 决策对象：`abilities/plugins/novelwright/src/entitlement/`

## 1. 背景

「插件特权状态离线验证后，侧边栏才出现插件名」是本插件的产品要求。它必须回答一个具体问题：
**没有网络时，怎么判断这台机器有资格用完整功能？**

可枚举的三种做法：

| 做法 | 断网可用 | 可伪造 | 代价 |
| --- | --- | --- | --- |
| 本地布尔值 / 明文 `plan: "pro"` | ✅ | ✅ 改一个字符串即可（CWE-602 的教科书形态） | 无 |
| 在线校验（每次启动打授权接口） | ❌ 直接不可用 | 需中间人 | 依赖网络与后端 |
| **离线签名凭证**：授权方用私钥签发，插件内置公钥验签 | ✅ | 需私钥 | 一次密钥管理 |

第三种是唯一同时满足「离线」与「不可伪造」的形状，因此采用。

## 2. 决策

1. **凭证格式**：`{ v: 1, subject, plan, entitlements[], issuedAt, expiresAt, keyId }` 的
   **规范化 JSON**（键按字典序、无空白）作为签名消息；`signature` 是 Ed25519 detached
   signature（base64url）。整体作为一段文本交给用户粘贴，或由 `entitlement.json` 预置。
2. **验签在插件内完成**：WebCrypto `crypto.subtle.importKey("raw", ..., "Ed25519")` +
   `verify`。内置公钥（`src/entitlement/trusted-keys.ts`）是**公钥**，泄露无风险；私钥永不进包。
3. **校验项全部 fail-closed**：版本号、`keyId` 是否在信任列表、签名、`subject` 非空、
   `expiresAt` 未过期（含 24h 时钟回拨容忍）、`entitlements` 含 `studio`。
   任一项不通过 → 状态 `invalid`，与「无凭证」同等对待。
4. **门禁范围**：侧边栏视图仍然注册（否则用户连输凭证的地方都没有），但视图内只渲染
   **激活页**；`novelwright_*` 写类工具在 handler 里先验状态，未授权直接返回结构化拒绝。
   读类工具（状态查询）放开，方便排障。
5. **明确边界，写进产品文案**：离线签名只能证明「这份凭证由我们的私钥签发过」，**不能**
   证明使用者就是购买者本人。逆转它需要在服务端做设备绑定与吊销列表——属于在线校验的领域。
   插件不宣称自己做到了这一点，也不把「本地校验通过」写成「已授权给此设备」。

## 3. 为什么不把校验写得更「防破解」

给 Ed25519 验签加花指令、校验自身完整性、反调试——在渲染进程里全是可以被 patch 的 JS。
投入产出比极低，而且会误导后续维护者以为这里有真实安全边界。真正该做的是：**把凭证当优惠券
而不是锁**，高价值权益（云端同步、多人协作）留在服务端，本地只决定 UI 是否解锁到哪一档。

## 4. 后果

- 断网可用；换机器需重新激活（凭证不绑定硬件，这是刻意的：绑定会让换机变成客服工单）。
- 时钟回拨超过 24h 会让凭证失效——牺牲一点可用性换「过期凭证不能靠改系统时间续命」。
- 测试直接用真实信任锚：`test/entitlement.test.ts` 用随包社区凭证做正例，逐字节篡改做反例
  （改 claims、改签名、换未知 keyId、过期、结构破损）。不再维护独立的测试密钥对——只有一个信任
  锚时，正例用生产锚才是真验，另造一套测试公钥反而会把「测试绿、真机红」放进来。
- **随包社区凭证让新装即 `active`。** 它不是漏洞，是这个产品的取舍：开箱能写，比开箱先要一个
  激活码更符合使用场景。代价要说清——本地签名只能证明「这份凭证由本插件的密钥签发」，不能证明
  「这份副本是购买的」。所以它是本插件自己的礼貌性门禁，**不是付费墙**，激活页与详情页都照实写。
- 用户凭证优先于社区凭证；激活失败不落盘，不会覆盖手上仍然有效的那份。没有 `clear()`：清掉用户
  凭证只会回落到社区凭证继续 `active`，那个按钮给的是假的确定感。
