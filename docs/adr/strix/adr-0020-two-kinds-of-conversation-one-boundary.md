# ADR 0020：两种会话，一套边界

- 状态：已采纳
- 日期：2026-11-15
- 关联：[ADR 0003](adr-0003-panel-reuses-host-session-and-model.md)、[ADR 0014](adr-0014-panel-instances-and-navigation.md)、[ADR 0016](adr-0016-team-members-are-declared-not-spawned.md)、[ADR 0019](adr-0019-panel-entries-and-density.md)
- 取代：无

## 背景

宿主里有两种会话，插件看到的却是同一个 `ConversationState`。这一版被三件事推到台前：

1. **团队对话里，面板不会自己到前面来。** 用户选了团队成员发一句话，插件面板停在首屏不动。
2. **在团队对话里用面板，行为和普通对话不一样。** 而这些不一样从来没有写下来过。
3. **按停止会停到别的会话。** 在 A 项目跑评估，切到 B 项目，在面板上按「停止生成」，B 项目正在生成的普通对话被终止。

第三件是事故，不是抱怨。所以这一版不是"再修一个 UI 细节"，而是把三种表面上的写动作一次划清。

## 事实（读宿主源码得到，不是推断）

`apps/desktop/src/renderer/domains/plugins/runtime/plugin-host-bridge.ts`：

| | 单智能体会话 | 团队会话 |
|---|---|---|
| `snapshot()` 来源 | `activeSessionAtom` | `pluginConversationOverrideAtom`（团队 composer 挂载时发布） |
| `id` | 会话 `runtimeId` | 团队会话 id |
| `sessionPath` | 会话文件路径 | **写死 `null`** |
| `turn-start` | `session.subscribe` 翻译而来 | 团队 composer 发送时 `publishPluginTurnStart()` 直报 |
| `message-*` / `tool-call-*` | 有（订阅在那条 runtime 上） | **没有**（团队没有可订阅的单一 runtime） |
| `sendPrompt` 落到谁 | `pluginSendMessageRef`（`useSessionManager` 设的）→ 当前单会话 | **同一个 ref** → 上一个单会话 |
| `abort()` 打到谁 | `activeSessionAtom.runtimeId` | **同一个 atom** → 上一个单会话，或什么都不打 |
| `insertText` 写到哪 | `inputValueAtom`，单会话输入框读 | 团队 composer 读自己的 `model.draft`，**不读那个 atom** |
| 输入框上的插件入口 | 胶囊（`actionBar.items.filter(active)`）+ 行内条目 | **完全没有**（`TeamComposerConnector` 不走 `useInputActionBarModel`） |

一行话说清：**团队会话里，插件在输入框上没有入口，三条写路径全部指向"上一个单会话"，而且收不到工具与消息事件。** 面板在那条表面上唯一站得住的角色是"显示服务自己的状态"。

## 决定

### 1. 形态由宿主给的那一个字段判定

`sessionPath` 为空 = 团队会话。这不是猜的：宿主在 override 那一支把它写死为 `null`，单会话那一支取 `ActiveSession.sessionPath`（必填字符串）。

空串也按团队处理。新会话在会话文件落地前可能是空串：误判成团队只会让面板"多跟随一轮"，误判成单会话则会让面板往错的会话里写。两害相权取前者。

### 2. 跟不跟随，看"这种会话上有没有开关"

| 形态 | 跟随规则 |
|---|---|
| 单会话 | 胶囊开着才跟随。没开 = 这一轮不是插件的活，抢焦点就是骚扰。 |
| 团队会话 | **总是跟随**。那里根本没有胶囊可开——缺席不是拒绝。 |
| 未知（还没收到 `conversation-changed`） | 按胶囊判断。未知不等于团队。 |

代价写在明处：宿主不告诉插件"现在跑的是哪支团队"，所以别的团队的对话也会把 strix 面板带出来一次。落地是"切一个标签页"，不是"改写对话"；用户按一下首屏按钮就能回去，且 pin 住之后同一会话不再被拽。

### 3. 写动作按形态授权，停止只看归属

```
                    send            stop
单会话            允许            仅当这一轮是本面板发起的
团队会话          拒绝            拒绝
无会话            拒绝            拒绝
```

`stop` 的判据是 `runOwner === 当前会话 id`：`runOwner` 只在面板自己把 prompt 送出去时写入，`turn-end` 与成功的 `stop` 都会清掉它。

于是四种情形都有确定答案：

- 面板发起的运行、宿主正看着这个会话 → 可以停。
- 面板发起的运行、用户已切到别的会话 → 不能停（`abort()` 会打到那个会话）。
- 用户自己在宿主输入框发的一轮 → 不能停（它不是面板发起的）。要停就按宿主自己的停止键。
- 团队会话 → 不能停（`abort()` 根本不指向这条会话）。要停就按团队输入框旁边的取消。

停止键在这些情况下是灰的，而不是"按下去才提示"：一颗按不动的键比一句事后解释诚实。

### 4. 团队会话里，面板只读

面板在团队会话里不代发、不代停、不代答。用户的话走团队输入框；面板显示服务自己的状态（沙箱、发现、计划、覆盖、笔记、命令、退出码）。

首屏的发送键在那条会话上直接换成一句说明，而不是让用户写完再被拒。

### 5. 首屏多一条不发送的入口

「工作台」按钮：进工作台看现场，不发消息、不建会话。理由很具体——在此之前，进工作台只有"发一句话"一条路，于是"我想看看刚才那轮跑到哪了"也必须先编一句话；而团队会话里用户根本没有别的入口。

它与首屏按钮「返回首屏」互为一对：那边 pin 住不再跟随，这边主动解除 pin。

## 后果

- **会话隔离成立。** 插件只能收拾自己摆出来的东西；停止键不再有跨会话的能力。
- **团队对话能用了。** 面板会跟到前面；面板不冒充输入框。
- **少一个分区。** 「会话」那两条事实（在哪跑、会话 id、镜像）并入「统计」：它们描述的是这一轮的状态，不是独立主题（ADR 0019 的六个分区因此变成五个）。
- **有人会问"为什么团队里发不了"。** 答案是宿主没给入口，不是插件偷懒；写进界面文案，不写进注释。

## 没做的事（刻意）

- **没给团队会话造第二套发送路径。** 那需要宿主暴露团队 composer 的写入口。插件侧没有这个能力，伪造一个只会把话发进错的会话。
- **没让面板按 `cwd` 隔离服务状态。** 服务是插件级的单进程，容器与台账跨会话共享。这是 [ADR 0017](adr-0017-service-source-stays-under-src.md) 的直接后果，要改就得让服务按会话分桶，属于另一个决定。当前的边界是：**面板显示的是"这个插件的当前现场"，不是"这个会话的私有现场"**；会话之间隔离的是面板状态（`session-store.ts` 按会话 id 存快照）与写动作。
- **没有把团队会话里的工具轨迹画出来。** 宿主在那条会话上不发 `tool-call-*`，服务侧的事件流照旧可读；面板因此靠 `/api/state` 与服务事件，不靠会话事件。这条限制在 [ADR 0009](adr-0009-ui-baseline-is-upstream-tui.md) 的"只搬能搬的"里已经成立，这里只是点明它在团队会话中的表现。
