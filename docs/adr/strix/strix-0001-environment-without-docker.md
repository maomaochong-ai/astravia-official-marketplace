# strix-0001 — 沙箱环境由宿主代备，用户不装 Docker

- **Status:** Proposed
- **Date:** 2026-11-13
- **Context:** strix 插件 0.5.x；宿主 0.5.93
- **Related:** 宿主 `providers.cli`（probe/install）与 `providers.services.runtime.artifacts`
  （按平台下载并校验 sha256 的运行时归档）；rea 用前者装 CLI，free-model-gateway /
  open-ai-canvas / dbx-pro / video-downloader 用后者装服务

## The situation

Strix 要跑渗透测试，就得有能执行 nmap / nuclei / sqlmap 这类工具的环境。上游的做法是
起一个 Docker 容器，把工具和样本一起放进去。插件因此隐含了两个前置条件：

1. **一台装了 Docker 的机器**——Docker Desktop 要单独下载、装驱动、开虚拟化、经常还要
   管理员权限；Windows 上还牵扯 WSL2。这一步跟「在编辑器里点一下」完全不是一个量级的操作。
2. **一个能拉到镜像的网络**——企业内网、限速网络下经常拉不下来。

对用户的观感是：插件装好了、面板亮着「就绪」，但一动手就卡在环境上；而他并不知道
「就绪」只代表插件自己起来了，不代表工具能跑。

这是体验问题，不是实现问题。源码里 `dockerReady()` 已经在探测 daemon，`plugin.json` 也
已经用宿主通道装 `strix-agent` CLI——**缺的是决策：这些通道各自负责哪一段，缺的那一段
怎么退化**。

## 术语

- **执行环境（environment）**：一次扫描里工具实际被执行的场所。三种形态：
  - `host`——直接在当前用户下跑宿主已备好的工具；
  - `docker`——在 Docker 容器里跑（上游形态）；
  - `wsl`——在 Windows 上借用已有 WSL 发行版跑。
- **工具链（toolchain）**：nmap / nuclei 这些可执行文件本身，与执行环境无关。
- **就绪（ready）**：某一层真的可用，而不是「插件被加载」。这个词以前被混用，是本 ADR
  要拆开的第一个歧义。

## The decision

**把「装环境」从用户身上移走，拆成宿主能做的三段；Docker 从「前置条件」降级为「加速器」。**

1. **工具链由宿主代备。** 走既有的两条通道，安装过程不出现终端、不要让用户复制命令：
   - CLI 类工具用 `providers.cli`（probe + install），宿主负责执行与重试；
   - 需要固定字节的工具集用 `providers.services.runtime.artifacts`，随包声明平台、
     归档与 sha256，宿主下载后校验再解包。
   这两条路在本仓已有四个插件在用，不是新机制。

2. **执行环境按「已有什么」自动选，顺序为 `wsl` → `docker` → `host`。**
   - 已有 Docker daemon 且能拿到镜像：用 `docker`，隔离最好；
   - Windows 上已有 WSL 发行版：用 `wsl`，工具在发行版里跑，同样不污染宿主；
   - 都没有：用 `host`，工具直接在当前用户下执行，**明确标注隔离较弱**。
   
   选择由插件自己做，不弹窗问用户「你想用哪种」。

3. **绝不代替用户安装 Docker / 不开虚拟化 / 不申请管理员权限。** 这些操作影响整机、
   需要 UAC、可能改变系统设置，超出插件应有的边界。缺 Docker 不是错误，是
   「没有加速器」，退到 `host` 继续能用。

4. **状态只报一次，说清「缺哪一段、接下来会怎样」。** 面板顶部一个环境条，三种值：
   `ready`（环境可用，附带形态名）/ `degraded`（用 `host`，隔离较弱）/
   `unavailable`（连 `host` 都缺，因为工具链没装上，给出宿主的「准备环境」按钮）。
   右下角不再因为环境问题弹错误——那正是上一轮被用户读成「插件坏了」的东西。

5. **一次扫描开始时快照环境形态，中途不再切换。** 否则同一份报告里的证据来自两种隔离，
   无法解释。

## Considered options

- **让插件自己 `docker pull` 并顺手装 Docker Desktop**：需要管理员权限、要重启、要开
  BIOS 虚拟化。用户在终端之外没有任何预期，失败率高且无法回滚。**否。**
- **随包带一个 rootless 运行时（podman / nerdctl + lima）**：包体积增加数百 MB，仍然需要
  虚拟化支持，Windows 上等价于自带一个 WSL。收益不如直接复用系统已有能力。**否。**
- **只支持 Docker，缺就明确报「请先安装 Docker」**：实现最省事，但把安装成本原样推回
  用户，正是本次要消除的。**否。**
- **完全不要沙箱，一律 `host`**：最省事，但渗透测试工具默认会碰真实网络与真实系统，
  一次误操作影响用户整机。保留 `docker` / `wsl` 作为优先形态是必要的。**否（作为唯一方案），
  但作为退化形态接受。**

## What this does not do

- **不在 `host` 形态下提供同等隔离。** 面板必须写明这一点，不能让人以为换个形态还是一样安全。
- **不保证 `host` 形态在所有平台都能凑齐工具。** 缺什么就报什么，不假装装好了。
- **不改变上游 Strix 的报告格式与工具行为**，只换执行场所。
- **不替用户改系统设置**（虚拟化、防火墙、代理）。

## The cost

- 三条执行路径意味着三套启动参数与三套失败文案；`docker.ts` 之外要再补 `wsl.ts` 与
  `host.ts`，由同一个 `environment.resolve()` 收口，避免三处各写一遍判断。
- 「就绪」这个词从此只表示**环境**可用；插件加载完成不再叫就绪，UI 文案需要同步改口。
- `host` 形态下工具以当前用户身份运行，风险由用户承担，因此默认形态的说明不能省。
- 工具集走 `runtime.artifacts` 时，每个平台的归档与 sha256 都要随版本维护，发版成本上升。

## 落地顺序

1. `environment.resolve()` 返回 `{ mode, detail }`，先把现有 `dockerReady()` 包进去；
2. 面板环境条接这三种值，右下角提示只在 `unavailable` 时出现一次；
3. 工具链补齐 `providers.cli` 声明，缺的用 `runtime.artifacts`；
4. 补 `host` 路径，让「没有 Docker 也能跑通一次扫描」成为可验证的验收项；
5. `wsl` 路径放在最后，它只影响 Windows 的形态选择，不影响可用性。
