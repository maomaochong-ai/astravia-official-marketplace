# 一批手势，不是一次点击

- 状态：已采纳（2026-11-04）
- 相关：[0005](0005-the-agent-drives-the-canvas.md)、[0002](0002-bytes-move-through-the-host.md)

## 问题

如果每个动作都是一个工具调用（`click` / `type` / `press_key` / `screenshot`…），画一条带标注的
箭头要七八次往返：每次都要序列化上下文、等宿主、再回到模型。慢还在其次——**中间态不可见**，
用户看着画布上光标一格一格跳，却不知道下一步是什么；出错时也说不清错在第几步。

## 决定

**一个工具，`<id>_act`，携带一串有序步骤。** 步骤在页面内按帧执行，边跑边用
`craft:progress` 回报"第几步 / 共几步 / 在做什么"，标签页把 label 显示在画布 HUD 上。
整批结束后一次回三个东西：

```json
{
  "ok": true,
  "steps": [{ "index": 0, "op": "click", "label": "打开矩形工具", "ok": true }],
  "elapsedMs": 1234,
  "change": {
    "meanBefore": "1e1e1e",
    "meanAfter": "2a2a2a",
    "rgbDelta": [12, 12, 12],
    "distance": 21,
    "changed": true
  },
  "probe": { "region": { … }, "cells": "…", "mean": "2a2a2a" }
}
```

- `steps[].ok` 是"这一步的派发成功"，不是"上游按预期生效"。
- `probe` 是改完之后的文字地图与平均色；`change` 是它和动手前那一次探测的差：
  `distance` 是 RGB 空间里的欧氏距离（上限 441），~0 意味着画布根本没变，
  `changed` 就是 `distance > 6`。**先说改没改，再说改成了什么**——没有这一对，
  "成功了"是自说自话。
- `elapsedMs` 是桥实际花掉的墙钟时间，状态条拿它显示"自动操作中"。
- `capture` 步骤把 PNG 附在 `captures[]` 里，只在用户真的要图时用。

## 为什么批次是"有序步骤"而不是"宏"

步骤是数据，不是脚本：没有循环、没有条件、没有变量。模型想根据结果分支，就再发一批。
这样一批永远能在超时内结束，也不会在页面里留下一个跑到一半的匿名循环。

`stopOnError` 默认开：某一步失败就停，剩下的步骤标记为未执行，而不是带着错误状态继续画。

## 为什么 `ready` 是一个步骤

页面可能还在启动。把"等它就绪"写进批次（`op: "ready"`）比在每次调用前单独轮询干净：
一批可以写成 `[ready, click, drag, label]`，调用方不需要知道启动需要几秒。

## 代价

- 一批不能太长：40 步上限，超过就该拆。长了以后单点失败会浪费前面所有步骤。
- `label` 是给人看的，必须用用户的语言写；写英文会在一批中文任务里显得突兀。
- 每个 `capture` 都会把 PNG 塞进结果，多了会撑爆上下文，所以它不是默认行为。

## 不做的事

- 不为每个手势单开一个工具。
- 不在批次里放条件逻辑或循环。
- 不在没有 `before` / `after` 的情况下声称"画布变了"。
