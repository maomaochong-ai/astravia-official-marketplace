# ADR 0011：界面三层同构——工作台对齐宿主智能体面板，交互沿用 ainovel-cli 的一步一令

- 状态：已接受（2026-10-29，随 0.0.1）
- 决策对象：`abilities/plugins/novelwright` 的全部界面
- 取代：ADR 0003 §2 的「工作台是唯一界面」在**解剖结构**上的表述（0003 的其余条款仍有效）
- 部分取代：ADR 0013 把工作台解剖改成书架 / 书页 / 阅读页三层，§2.2 的排布以此为准；
  §2.1（三层界面语法）、§2.2 的成员胶囊与指令卡语义、§2.3 起的交互规则仍有效
- 相关：ADR 0006（只用宿主语义 token）、ADR 0007（工具只返事实）、ADR 0008（对话桥）

## 1. 背景

ADR 0003 定了「工作台视图是主界面」，ADR 0008 定了「对话交给宿主、插件不自绘聊天框」。两份决策都没有回答
一个更具体的问题：**工作台长什么样，才既像宿主里点开一个智能体，又像 ainovel-cli 那样在写小说？**

宿主一侧的解剖是固定的，插件只能贴合、不能另立：

| 宿主事实 | 出处 |
| --- | --- |
| 团队会话 = 页头 + **成员胶囊条**（`DefaultChatView` 的 `subHeader`）+ 消息时间线 + 输入栏 | `domains/conversation/connectors/team/TeamChatView.tsx` |
| 胶囊条一人一枚、直接写名字，点开对应成员的独立会话；队长带角标；最右一枚是设置齿轮 | `TeamMemberRoster.tsx` |
| 侧边栏里的插件智能体以 `plugin:<pluginId>:<agentId>` 作蓝图 id，点开进宿主对话 | `useSidebarModel.ts` / `parsePluginBlueprintId` |
| 新会话页有「上下文区」：选中本插件智能体时上屏，可 `insertText` 但**不能**直接发送 | `ui-slots.md` §registerNewSessionContext |
| transcript 里可替换某个工具调用的行内渲染 | `ui-slots.md` §registerToolCallSlot |
| 没有「从视图 A 跳到视图 B」的 API，也没有「把会话绑定到指定成员」的 API | `ui.ts` 无对应方法；`ctx.conversation` 只作用于活动会话 |

上游一侧的使用习惯也清楚（`README.md`「逐章验收」「实时干预」「恢复」三节）：

- **一个动作就是一步**：回车 = 放行一章（`/next`），不是「开始连续生成十小时」；
- **状态永远先于动作**：先报进度与 checkpoint，再给恢复指令；
- **输入框就是干预通道**：创作中打字即 steer，不需要暂停；
- **诊断是查询，不是按钮**：`/diag`、`/status` 要了才给。

## 2. 决策

### 2.1 三层界面，一套语法

| 层 | 槽位 | 承担什么 | 不承担什么 |
| --- | --- | --- | --- |
| ① 新会话页 | `registerNewSessionContext` | 选中本插件智能体时，把「下一章/开新书」摆到输入框下方，一键把话术插进草稿 | 发送（宿主刻意不给） |
| ② 对话内 | `registerToolCallSlot`（`next_instruction`、`book_status`） | 把工具结果渲染成指令卡与进度条，读者不必读 JSON | 新的状态来源（数据仍来自工具返回值） |
| ③ 侧边栏工作台 | `registerWorkspaceView` | 书头 + 成员胶囊 + 指令卡 + 章板 + 正文/评审 | 输入框、模型选择、会话管理 |

三层的**语法一致**：都是「谁在做 → 做到哪 → 下一步是什么」。同一个 `routeNovel(book)` 同时供给
②的卡片、③的指令卡和①的话术文本，界面之间不会给出互相矛盾的下一步。

### 2.2 工作台的解剖（自上而下）

```text
书头        书名 · 阶段胶囊 · 进度（3/12 章 · 5600 字）        [状态胶囊 · 激活]
成员胶囊    主会话(队长·架构师) 写作者 编辑 裁定者                 [齿轮位 = 凭证面板]
──────────
指令卡      下一步：写手写第 4 章《……》  因为 章纲已确认
            [继续]  ← 唯一的主按钮，经对话桥发一条指令
章板        第 1–3 章（已提交）· 第 4 章（起草中）· 第 5 章起（待写）
正文/评审   当前章正文预览、最近一次评审的七维分数与 mustFix
```

与宿主团队会话一一对位：书头 ≈ 页头，成员胶囊 ≈ `TeamMemberRoster`，指令卡 ≈ 最后一条待办，
章板 ≈ 时间线上「到哪一步了」的可扫读版本。

**成员胶囊点下去做什么**：宿主不提供「把会话绑到某个成员」的 API，所以胶囊不做成「打开该成员的会话」，
而是**把那位叫上场**——经对话桥发一条该成员的派活话术（架构师规划下一卷 / 写手写第 N 章 / 编辑评第 N 章 /
裁定者定夺待决项）。用户看到的结果与点开成员会话再打字等价，但不需要宿主支持成员级会话绑定。

**齿轮位放什么**：宿主那里是团队设置；插件的设置页已被宿主移除（ADR-0105），所以这一格放凭证状态胶囊，
点开就地展开激活面板。位置沿用，语义按本插件实际拥有的东西替换，不假装有设置页。

### 2.3 指令置顶，诊断沉底

第一屏必须是「下一步」，因为上游的核心体验就是「看一眼、回一句、前进一章」。
诊断类能力（一致性、规则、风格统计、上下文包、工艺库）**不占工作台的固定版面**——它们是查询，
放对话侧用工具调用，用 ② 的行内渲染在需要时出现。把 31 个工具的入口堆进侧栏，等于把 `/diag` 变成首页。

### 2.4 不做输入框，也不做假的输入框

干预（steer）在宿主里天然成立：对话页输入框一直在，创作中打字就是介入。所以工作台里**没有**输入栏，
连 `registerInputAction` 也不加「一键续写」这类开关——那会把「发送前的一道关」搬到侧栏，
与上游「回车即一步」的习惯正好相反。唯一的主按钮是 [继续]，它做的事与在对话里打一句话完全一样。

### 2.5 上游使用习惯的落点

| ainovel-cli | 本插件 | 说明 |
| --- | --- | --- |
| `/next` 放行一章 | 指令卡上的 [继续] | 一次调用，不是「开始连写」 |
| 启动后输入框转干预模式 | 宿主对话输入框 | 插件不接管；不申请草稿读权限 |
| `/review on` 逐章验收 | `novelwright_save_review` 的分数低于 `PASS_SCORE` 时路由停在评审 | 闸门是数据驱动的，不是开关 |
| `/status` | `novelwright_book_status` + 工作台书头 | 一处事实两个呈现 |
| `/diag` | `check_consistency` / `check_rules` / `style_stats` | 只报问题，不自动改 |
| `/read` | `novelwright_read_chapter` + 章板点选 | 同一份稿件 |
| `rules/*.md` 自然语言偏好 | `novelwright_set_user_rules` + `check_rules` | 归一化成结构约束后机械自检 |
| `style/` 文风覆盖 | 随包 `styles/` + `novelwright_reference` | 见 ADR 0012 |

## 3. 被否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 在工作台里自绘输入框并承接 steer | 宿主的会话、流式、工具确认都在对话页；自绘一份等于两套输入语义 |
| 成员胶囊打开该成员的独立会话 | `ctx.conversation` 只作用于活动会话，没有成员绑定入口；能做的只有「打开对话并说一句」 |
| 照搬 `TeamMemberRoster` 的宽度分配测算 | 那是为了让 1–32 个成员在窄条里都不截断；本插件固定 4 位，按自然宽度排即可 |
| 给 31 个工具都写行内渲染 | 只有两个工具有「值得看第二眼」的结构（指令、状态）；其余渲染成卡片只是把 JSON 换个壳 |
| 工作台里放「一键写到第 20 章」 | 与「一步一令」相反，且一次失败就把整段进度绑死 |

## 4. 后果

- 界面新增两个槽位权限：`ui.slot.new-session-context`、`ui.slot.tool-call`（→ 权限共 10 项）。
- 指令卡与工具行内渲染**复用同一个组件**：谁改了渲染，两处同时改，不会一边新一边旧。
- 侧栏工作台仍是可卸载界面：没有它，① 与 ② 依然能用（新会话页 + 对话），因为它们不依赖视图注册。
- 代价：成员胶囊是「叫上场」而不是「切会话」，用户点第一下会看到一条消息发出去——这需要在胶囊的
  无障碍标签里说清楚（`roster.inviteHint`），否则会被当成导航。
