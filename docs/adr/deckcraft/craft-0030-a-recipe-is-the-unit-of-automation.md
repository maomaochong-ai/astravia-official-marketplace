# craft-0030 — 一条成套动作就是一个自动化单元

- **Status:** Accepted
- **Date:** 2026-11-10
- **Context:** craft 系列 0.0.28
- **Related:** [0029](craft-0029-address-the-function-not-the-pixel.md) — 按名字执行功能、
  [0026](craft-0026-act-says-what-it-expects.md) — 判对错的读数、
  [0028](craft-0028-a-skill-ships-what-it-can-act-on.md) — 技能只带用得上的东西

## The situation

`menu` 让一个功能可以被按名字调用，但用户要的是**一件事**，不是一条命令。"帮我导出"往往是
"选择导出方式 → 确认尺寸 → 命名 → 落盘"；每一步都能单独调，合起来却是五轮往返，中间任何一步失败，
模型都得自己拼回去。

技能文本补不了这一段：它只能劝模型"按顺序调用"，而劝告不是机制——模型看不见顺序有没有走完，
用户也看不见。同一个"保存"在不同轮次里走的路不一样，失败原因就各不相同。

## The decision

**把成套动作变成数据，并且只允许它由编辑器真实存在的命令组成。**

- 每条配方（recipe）是 `app.config.ts` 里的一个对象：`{ id, label, when, steps[] }`，
  一个 step 要么是 `{ shortcut }`，要么是 `{ menu: [路径…] }`。**没有坐标**，所以不受窗口大小、
  缩放、面板宽度影响。
- 配方住在 `app.config.ts`：它是每支应用唯一允许不同的源码文件，族内其余文件逐字节相同。
- 新工具 `recipe` 执行它们：`{ "id": "save" }` 跑完返回每一步的结果、`change` 与 `journal`；
  `{ "list": true }` 列出这一版有哪些。
- **只有能寻址的命令才进配方**：有快捷键，或命令名可信到能组成菜单路径。命令表里名字残缺的行
  （`ZmIn`、`edit.redo` 这种导出时错位的）不进配方——一个走不通的配方比没有配方更糟。
- 技能包里的 `references/recipes.md` 由同一份数据生成，写的是"id / 什么时候用 / 它做什么"，
  不是操作手册。

于是"这件事做完了没有"有了第三个答案层：`invoked`（配方跑通没有）→ `change`（画面变了没有）
→ `assert`（变对没有）。

## What this does not do

- **它不保证配方里的功能在界面上一定可达。** 助记符可能被别的菜单抢先、可能被模态对话框挡住；
  失败会落在某一步上并报出 `did-not-run`，不是静默。
- **它不替用户决定文件名。** `save` 写的是当前文档；`save-as` / `export` 会打开应用自己的对话框，
  需要用户选路径——这一步不进配方。
- **它不覆盖没有命令的功能。** 画笔、拖拽、渐变走向这些只能 `act`；配方是给"有名字的活"用的。
- **它不会因为应用功能多就自动变多。** 当前 15 支里，配方数从 0（FigCraft、Craft Anything，命令表只有
  面板项）到 14（DeckCraft），差异来自编辑器实际暴露的命令，不是我们没写。

## The cost

- `app.config.ts` 从"身份声明"变成"身份 + 配方"，这支文件从此有内容要维护；好在它随命令表生成，
  升级 pin 后重跑一次生成即可。
- 配方与命令表之间多了一条一致性要求：`tests/craft-recipes.test.mjs` 会检查每条 step 都能在
  `references/commands.md` 里找到对应行，找不到就红。
