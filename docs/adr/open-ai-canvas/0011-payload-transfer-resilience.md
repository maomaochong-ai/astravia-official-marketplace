# 0011 — 载荷下载卡在 88%：分片失败必须能被看见、且必须自己退出

- 状态：已接受（现行）
- 日期：2026-10-26
- 修正：0009（载荷来源链）里「失败会回退到单连接」的假设
- 相关：0005（载荷清单）、0009（来源链）

## 背景

用户截图是「下载中 · 88%」，长时间不动。现场还在盘上（**Observed**，`~/.astravia/plugin-services/open-ai-canvas/open-ai-canvas/data/runtime/`）：

| 文件 | 字节 |
| --- | --- |
| `1.6.9.2.partial.zip.part0` | 16308064 |
| `1.6.9.2.partial.zip.part1` | 16308064 |
| `1.6.9.2.partial.zip.part2` | 16308064 |
| `1.6.9.2.partial.zip.part3` | 16308064 |
| **`…part4`** | **401336** |
| `…part5` | 16308064 |
| `…part6` | 16308064 |
| `…part7` | 16308058 |

`7 × 16308064 + 16308058 = 130464506` 是载荷全长，(114557778 / 130464506) = **87.80%**，四舍五入就是界面上的 88%。

所以「卡在 88%」不是玄学，是**八个分片里恰好有七个写满、第八片（part4）停在 401336 字节**。这个数字能直接由 `.partN` 的文件长度复算出来，不需要日志。

## 决策

1. **每个分片自己持有一个「停滞计时器」，到点直接 reject 它自己的 Promise。**
   旧实现的看门狗只做 `response.destroy(new Error("分片停滞"))`，指望错误沿 `socket → PassThrough → pipe → sink` 这条链传下来。链上任何一环没把错误转发出去，`await new Promise(...)` 就永远不返回，`Promise.all` 也永远不会 reject，单连接回退分支永远不执行——这正是 part4 的处境。现在计时器持有 `reject` 本身，与流的事件链无关。
2. **整次传输再加一条总截止时间（20 分钟）**，超时直接失败并列出还差哪几片。允许重试，但不允许「每片都在慢悠悠重试」把启动拖成无限期。
3. **失败必须写进日志，不再只在 `CANVAS_DOWNLOAD_DEBUG` 下可见**，并计入 `STATE.retries`。用户看到百分比不动时，界面上的日志要已经写明是哪一片、为什么、已落盘多少。
4. **`/__canvas/progress` 与 `/__canvas/state` 增加逐片进度** `chunks[{index, received, expected}]`。总百分比是一个聚合数，聚合数卡住时人无法判断是网络慢还是死了；逐片数字能。
5. **停滞判死不再走「三次就放弃该片」**：一次停滞即放弃分片模式，交给单连接整体续传（单连接也能 Range 续传），避免在一个坏分片上耗掉三次 30 秒。
6. **失败后的残留必须有一个界面入口清掉。** 分片下载失败会在 `data/runtime/` 留下整个 `.partial.zip` 与 `.partN`（现场就是 114 MB），保留它们是为了续传，但用户看到「重试」时无法知道接的是旧字节还是从头来。新增 `POST /__canvas/payload/reset` 与插件面板的「清理下载残留」：只删 `.partial.zip`、`.zip.tmp` 及其 `.partN`，不碰已安装的运行时目录，回 `{removed, freedBytes}` 让界面报出实际释放量。

## 为什么不是「把分片数调小」或「关掉分片」

分片是为了让 130 MB 的下载在弱网下能跑满带宽、断了只补一片。调小分片数不解决「Promise 永不 settle」，反而让单片更大、卡住时损失更多；关掉分片等于放弃弱网下的可用性，是拿功能换实现省事。

真正的问题不在并发度，在**失败路径依赖了一条可能断掉的错误传播链**。

## 代价

- 每次收到数据都 `clearTimeout` + `setTimeout`，130 MB / 16 MB 一片约 1 万次定时器重建。实测可忽略，但这是拿常数开销换确定性退出。
- 20 分钟总截止意味着极慢网络（<1 Mbps）下会失败而不是「再等等」。失败信息里带剩余分片，用户能判断是换网还是重试。
- `chunks` 数组进了 `/__canvas/state` 的载荷。它最多 8 项，不构成体积问题。

## 验证

- `npm test` 全绿（`41/41` 的 MCP 契约、`24/24` 的 origin 契约等不受影响）。
- 旧版复现证据：0.1.4 及更早的 shim 在 `data/runtime/` 留下 `part4 = 401336` 这种「七满一残」的现场；新逻辑下同一起点会在 30 秒内明确失败并在日志里点名分片，而不是无限等待。
- **未被自动覆盖的部分**：真实的「分片中途断流」没有做成回归脚本——构造它需要可控的假 Range 服务，且要跑满 8 分片才触发。`/__canvas/payload/reset` 同样只有手工调用过，没有进 `verify-*` 契约。当前靠的是现场字节复算 + 代码路径审查。这是已知缺口，不是「已验证」。

## 回滚

`downloadChunk` 里的 `arm()`/`stallTimer` 段回到「`setInterval` + `response.destroy`」即可恢复旧行为；`downloadChunked` 去掉 `Promise.race(deadline)` 即去掉总截止；删掉 `handlePayloadReset` 与 `/__canvas/payload/reset` 分支即去掉清理入口。三处互不依赖。
