# 0009 — 载荷来源改为「本地 / 镜像 / 官方」链路，不再要求用户自备代理

- 状态：已接受（现行）
- 日期：2026-10-25
- 部分推翻：0005（构建农场）决策 4 的「清单解析顺序」——那三步都以 GitHub 为前提
- 相关：0003（运行时分发与跨平台）、0004（启动就绪契约）、0005（构建农场）

## 背景

0005 把载荷来源写死成一条：`https://github.com/maomaochong-ai/astravia-official-marketplace/releases/download/…`。首启要下 `129–135 MB` 的主载荷，再下 `85–96 MB` 的 Agent 运行时（**Observed**：清单与各平台 zip 实测体积），而 `github.com` 在部分网络里根本连不通。

于是首次启动就变成一道与功能无关的关卡：状态卡在「下载载荷」，文案只让人「检查网络或配置代理」。对没有代理的用户，这不是提示，是死路——插件的核心能力一次都没跑到过。

三条前提让「把二进制打进插件包」这条路走不通（**Observed**）：

| 项 | 数值 |
| --- | --- |
| 市场包归档上限 | ≤ 25 MB |
| 市场包解压上限 | ≤ 100 MB |
| 单平台主载荷 + Agent 运行时 | ≈ 215–230 MB |
| 五个平台合计 | ≈ 1.1 GB |

也就是说：所谓「本地构建二进制包」在分发层面不可能等于「包里带二进制」。能把二进制交给用户的方式只有三种——用户自己构建、从能连通的来源取、或由别人的镜像代取。本 ADR 按这三种排序。

## 决策

**来源从「唯一 URL」改成一条有序链，能找到就不再往下走。**

1. **本地目录（零网络）** —— 依次找 `CANVAS_PAYLOAD_DIR`、`<DATA_DIR>/payload`、`<包内>/payload` 里的**同名 zip**，命中即校验 `sha256` 后解包。清单同样支持本地 `payload-manifest.json`。
2. **镜像前缀** —— 默认 `https://ghfast.top/`、`https://gh-proxy.com/`，把基址整体拼在前缀之后：`<前缀><基址>/<文件名>`。可用 `CANVAS_PAYLOAD_MIRRORS` 换、加、或设 `none` 关闭。
3. **配置基址 / 官方 Release** —— `CANVAS_PAYLOAD_BASE_URL`，未设置时即官方 Release 地址。
4. **`api.github.com` 资产地址** —— 只在前三条全失败后单独一搏（多一次请求）。

两条与顺序同等重要的规则：

- **清单并发探测，谁先回 200 用谁**（`probeFirst`）。串行试 N 个来源 = N × 超时，弱网下用户只能盯着进度条；并发探测把等待压到「最快那条」的耗时。胜出的基址记进 `PREFERRED_BASE`，后续归档复用——能列出清单的来源通常也能下文件。
- **显式 `CANVAS_PAYLOAD_BASE_URL` 一旦设置，就不再去碰 `api.github.com`**。内网或离线部署里，一次隐形的 GitHub API 请求既拖慢启动，又会在审计日志里留下不该有的外联。

本地归档的处理有一处刻意的宽容：`sha256` 不匹配时**不报错**，删掉副本、记一条日志、继续走远程。用户放错文件是常态，让他们进「重试 → 还是失败 → 再重试」的死循环才是真问题。

## 为什么不是「把二进制打进插件包」

这是最容易想到、也是被本 ADR 否掉最彻底的一条。

- **体积差了两个数量级**：单个平台约 215 MB，市场包解压上限 100 MB。就算只发一个平台也装不下，何况五个。
- **市场包是源码制品的通道，不是 CDN**：载荷有独立的 Release（`plugin-open-ai-canvas-payloads`）与独立的版本节奏（0005）。把二进制塞进插件包，等于把「每 3 天可能重发 1 GB」绑到「每次改一行文案都可能发一次」的那条流水线上。
- **CI 会直接挡住**：`scripts/marketplace.mjs check` 与发布 workflow 都会校验体积，写进去也发布不出去。

真正被采纳的替代是「本地目录」这一档：它让**已经拥有 zip 的人**（自己构建过、从内网搬过来、同事发过来）完全不联网就能启动；同时对**什么都没有的人**，靠镜像链把「能不能下到」从单点变成多点。这两件事加起来才是“解决各平台网络受限”，而不是把 1.1 GB 塞进一个 25 MB 的信封。

## 代价

- **镜像可用性由第三方承担**。实测（2026-10-25）：`ghfast.top`、`gh-proxy.com` 对清单回 200、对大 zip 回 `206`（续传可用）；`ghproxy.net`、`gh.llkk.cc`、`ghproxy.cc`、`gh.xxooo.cf`、`github.moeyy.xyz` 不可用；`gh-proxy.net`、`hk.gh-proxy.com` 回 302 到不了文件。这些都会变，所以列表是常量而非常识，且允许用户整条关掉。
- **多一层探测 = 多一次请求**。清单阶段最多并发 3–4 个 HEAD/GET，命中即止；代价是最坏情况下的一轮并发超时（默认 12 s），换掉的是「串行 N × 12 s」。
- **本地目录是隐式契约**。用户把文件放进 `<DATA_DIR>/payload` 就会被用上，界面不提示；因此校验失败时的日志必须说清楚是「本地文件不对」，而不是笼统的「下载失败」。
- **信任半径没变小**：镜像只是传输层，`sha256` 仍来自清单，清单仍来自我们自己的 Release。镜像坏了最多让下载失败，不会让坏字节通过校验。

## 验证

`scripts/verify-payload-sources.mjs` 起真实 shim 进程，`ASTRAVIA_SERVICE_RUNTIME_DIR` 指向空目录（逼出「准备运行时」这条路），清单与 zip 由脚本现场生成、`sha256` 现场计算，三个场景各自独立：

| 场景 | 环境 | 断言 |
| --- | --- | --- |
| A 本地目录 | `CANVAS_PAYLOAD_DIR` + 本地清单 + 真实 zip；镜像关闭；基址指向 `127.0.0.1:1` | 到达 ready、`attempts=0`（一次网络都没发）、首页能取到解包出来的 `index.html` |
| B 镜像前缀 | 基址与镜像前缀都指向本地 http 服务 | 到达 ready；请求路径精确等于 `<镜像前缀><基址>/<文件名>`；状态记录镜像主机；日志里没有 `github.com` |
| C 全不可用 | 基址 `127.0.0.1:1`、镜像关闭 | 停在 `payload-unreachable`；文案给出本地目录 / 镜像 / 重试；没有请求 `api.github.com`；不谎报 ready |

结果：**14/14 通过**（**Observed**）。C 场景同时把「显式基址不回落 GitHub API」这条规则钉住——没有它，这个测试会去真的请求 `api.github.com` 并可能开始下载 130 MB。

仍未验证的部分（**Assumed**）：真实 Go 载荷在受限网络里通过 `ghfast.top` 续传的实际成功率，以及 `macOS` / `Windows` 上本地目录的默认落点（`<DATA_DIR>/payload`）在宿主沙箱内的写权限。两者都需要一次实机、真网络的确认。
