# ADR 0004：标签页里的编辑器不对 Agent 开放

- 状态：**已被取代**（2026-11-03）：标签页现在有 Agent 工具，见
  [craft-0002](./craft-0002-agent-tools-talk-to-the-running-page.md)。本文仍然成立的那一半是
  「工具不代替用户编辑」——它们只打开、观察、取图、投字节。
- 关联文档：[0001](./0001-the-tab-runs-upstreams-web-build.md)、[0003](./0003-only-input-and-save-are-visible.md)
- 关联文档：[0001](./0001-the-tab-runs-upstreams-web-build.md)、[0003](./0003-only-input-and-save-are-visible.md)

## 1. 背景

前稿设想了 8 个 MCP 工具 + 一个逃生门，全部建立在那条 loopback 控制通道上。0001 选了标签页形态之后，
那条通道不存在了：编辑器是渲染进程里一个 iframe 中的 wasm 实例，没有端口、没有 socket、没有句柄。

于是「Agent 能不能操作它」变成一个真问题，而不是一个实现细节。

## 2. 候选

### A. 合成 DOM 事件驱动（技术上成立，否决）

同一个文档，插件可以 `canvas.dispatchEvent(new PointerEvent(...))`；egui 的 web 后端从 DOM 事件取输入，
所以「点某个菜单坐标」是能生效的。但要完成一次有意义编辑，Agent 需要：先截屏、识别界面、算坐标、点、
再截屏验证……这是一个把 GUI 当 API 用的闭环，慢、脆、且每次上游改一个按钮位置就全线失效。

真正的图像编辑操作（裁剪、调色、导出）在 Photocraft 里是引擎命令，不在菜单坐标里；模仿人点菜单是
最贵的一条路。

### B. 把编辑器状态镜像成 MCP 资源（否决）

需要读状态的通道，而 [0003](./0003-only-input-and-save-are-visible.md) 已经论证它不存在。

### C. 不给 Agent 面向编辑器的工具（选定）

Agent 面向**文件**：它能读、能写、能跑命令（宿主既有能力），也能从插件拿到「当前打开的是哪个文件」
这一条事实。它不面向**编辑器**：不能替你调滑块、不能替你点保存、不能替你撤销。

### D. 把上游 `photocraft-cli` 作为另一个能力接进来（不选，留档）

`photocraft-cli convert/info/run/batch` 是真正的批处理面，适合「把 200 张图导出成 webp」这类任务。
它是**另一个产品决定**：需要原生二进制、需要版本门、需要文件根授权（前稿 0005 写的就是这一套）。
本插件不带它；想要批处理的人应该得到一个独立能力，而不是让一个图片编辑标签页兼职跑批。

## 3. 决策

**D1** 本插件不注册任何 MCP 服务器、不注册任何 Agent 工具。`plugin.json` 里不出现
`agent.mcpServers`、不申请 `agent.tools.register`。

**D2** Agent 可以知道的一件事：**当前绑定的文件路径**。插件把它作为会话上下文暴露（读侧，只读），
这样用户说「把刚才那张图改成 1200 px」时，Agent 至少知道「那张图」是哪个文件——它去读磁盘上的字节，
不读编辑器里的像素。

**D3** 保存动作永远由人触发。Agent 改写文件后，标签页顶部出现「这个文件在磁盘上被改过」的提示
（0003 D3），由用户决定是否重新载入。**不允许**插件为了「让 Agent 的改动可见」而自动重载——那会
无声地丢掉用户手里正在编辑的内容。

**D4** 若将来要做 Agent 驱动编辑，正确的形状是**上游提供命令级 web 接口**（把 `engine.execute` 那层
搬到 wasm 侧并暴露成消息），由我们接成工具；不是把 GUI 事件合成当成 API。这条写在这里是为了让下一个
人不要把 A 当成捷径。

## 4. 后果

- **好处**：整个插件没有服务进程、没有端口、没有 token，攻击面就是「一个读文件的 iframe」。
  上线成本、审计成本、失败模式都少一个数量级。
- **代价**：这个插件在「能力市场」里是**给眼睛用的**，不是给 Agent 用的。用户如果期待「让 AI 帮我修图」，
  会失望——所以卡片文案必须说实话，不写「AI 修图」。
- **不会误伤**：Agent 仍然可以在同一个工作区里用 `sips`/`magick`/`ffmpeg` 之类的命令行工具处理图片；
  本决策只是说「别指望通过这个标签页的 UI 去驱动 Photocraft」。

## 5. 证据与未验证

Observed：宿主 `ui.d.ts` 的 `registerMcpServer`/工具注册契约（存在，但本插件不申请）；`web.rs` 全文
没有任何命令入口——它只接 `eframe` 的输入与 `services()` 的文件 I/O；上游 `photocraft-cli` 的
`convert/batch` 子命令（`apps/photocraft-cli`）。

未验证：无。本条决策不依赖未测事实，依赖的是「没有通道」这个已经读代码确认的否定事实。
