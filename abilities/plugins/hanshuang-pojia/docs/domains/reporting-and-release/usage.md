# 报告、版本与发布 · 怎么用

这一域把「我看到了什么」变成「别人能看懂、能复核的东西」，以及把插件本身推到能被装上的状态。
两件事互不依赖：分析师每天用前者，只有改代码的人才用后者。

开发侧地图与发布前清单见 [dev.md](dev.md)。

## 报告侧

| 你要的 | 用哪个 | 产出 |
| --- | --- | --- |
| 一份能交出去的评估报告 | `write_assessment_report` | 四节：概要 / 判定点（函数或偏移）/ 验证证据 / 纵深防御；没提供的节写「未提供」，不编 |
| 单个样本的体检报告 | `export_triage_report` | markdown 或 json，走保存对话框，不静默落盘 |
| 补丁 / keygen / 代理 DLL / 验证脚本的骨架 | `generate_artifact` | 带补丁表或测试向量占位；偏移与哈希要你自己填实测值 |

报告里每个断言都要能落到 **Observed / Inferred / Assumed** 之一；没跑的步骤写 `NOT RUN`，
并附下一条可复现命令。五段顺序固定：定位 → 补丁表 → 可运行产物 → 验证 → 回滚。

## 分寸

- **写到哪一层**：只要「定位 + 证据 + 一条能重跑的命令」时，用对话里的五段交付，不必出正式报告；
  要交给第三方评审、要跨人接手、要留档，才用 `write_assessment_report`。
- **不要为了凑满四节而写废话**：缺的那节明确写缺失，比补一段没人验证过的推测有价值。
- **证据优先于结论**：报告的说服力来自可重跑的观察，不来自措辞。

## 发布侧

| 改了什么 | 要不要抬版本 |
| --- | --- |
| 只改 `docs/`、`README`、测试 | 不用 |
| `src/` / `agent/` / `cases/` / `assets/` / `scripts/` / `plugin.json` | 必须抬，否则严格校验直接失败 |

抬版本用仓库级脚本（默认 dry-run，一次改五份身份文件），然后 `check` → `build` → 构建之后再跑内容测试。
发布由 CI 做：普通源码 PR 合入后自动构建并推进分发分支，**合并源码 PR 本身不会自动发布**。

## 面板对应页

「自检」页是所有「看起来没生效」的第一站，四组数字：`tools`（31 个工具注册齐）、`assets`（技能 / 知识库 /
文档 / 路由表指纹 / 14 条战例工程）、`engine`、`permissions`。先看红在哪一项，再怀疑版本。

## 常见坑

| 现象 | 原因 | 怎么办 |
| --- | --- | --- |
| `bump` 说没有可抬的 | 本地对分发分支的引用陈旧 | 先从远端取回上一版索引再 bump |
| `build` 说输出已存在 | 上一次构建目录还在 | 备份改名后重建，别直接删 |
| 内容测试失败但代码没动 | 测试读的是构建产物 | 顺序是构建之后才跑内容测试 |
| 报告里出现真实密钥 / Token | 抓来的原文直接贴进去了 | 用哈希或打码；输出卫生适用于所有交付物 |
