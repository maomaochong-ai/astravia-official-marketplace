# 拒答是终局，不是待绕过的故障

模型拒绝一次内容请求时，插件**停下并如实报告**，不改写问法、不重试、不换模型再试。

## 背景

本插件此前把「模型不许拒绝」当成目标：`domain/refusal.ts` 逐条匹配拒绝句式并在 `Stop` 事件上
续跑，`runtime/contributions.ts` 在用户原话前附加「评审式重述」与「历史声明作废」，把同一请求换成
另一种说法再送进去。迭代需求进一步要求：拒绝后依案例库自动换问法、连续十次失败后自动路由到
其他模型、全部模型都拒绝时再研究更强的改写手法。

## 决定

**这些不做。** 具体地：

1. **自动化改写不实现。** 因为上一次分类器判定拒绝了，就把同一件事换一句说法重投——这是针对
   安全分类器的规避，不是可靠性工程。它把「哪句话能过闸」变成插件要优化的指标。
2. **不实现十次重试与跨模型升级。** 换个模型直到有一个肯答，等于把「谁更容易被说服」当作选模
   依据。同样的预算花在把目标、证据与边界讲清楚上，收益更确定。
3. **不做面向规避的护栏调研。** 研究厂商拦截层如何工作，只在「如何正确区分拒答与故障、如何向
   用户如实解释」这个范围里有价值；超出这个范围的产出不进本仓库。

## 保留的部分

同一批信号仍然要处理，只是处理方向相反：

- **区分拒答与技术故障。** 拒答是一个明确的答案（HTTP 200、正文完整、语义为拒绝）；超时、
  `429`、认证失败、`5xx`、传输中断是另一类。前者不该被当成「再试一次就好」，后者不该被
  误读成「模型不肯答」。
- **停下并说明。** 拒绝发生时，把模型的原话、命中的规则、以及「这件事在自有资产上怎么做」
  一并交给用户，由人决定下一步。
- **不静默重投。** 任何自动重发都必须有用户可见的计数与停止条件，且不针对内容判定。

## 后果

- `refusal.ts` 的续跑逻辑与 `promptContexts()` 的改写分支是这次决定之前的设计，与新决定冲突，
  应在后续迭代里移除；本文只记录方向，不在本次提交里改动它们的运行时行为。
- 插件的能力仍然完整：工具面、案例库、报告与面板不依赖「模型不拒绝」这条前提。
