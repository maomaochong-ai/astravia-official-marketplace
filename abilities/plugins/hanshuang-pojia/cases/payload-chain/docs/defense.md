# 防御侧：这条链在哪几处会被断掉

同一条链在防守方视角有五个可下手的位置。顺序按「投入最小、覆盖最广」排。

## 1. 入口完整性（断第 3 段）

| 做法 | 代价 | 覆盖 |
|---|---|---|
| 对 `.text` 做节区哈希，启动与运行时各校验一次 | 低 | 补丁类改动 |
| 对入口前 N 字节做常量指纹 | 低 | 只改入口的 trampoline |
| 代码签名 + 加载器强校验（Windows 用 WinVerifyTrust，ELF 用 IMA） | 中 | 磁盘上的篡改 |

局限：**进程内**的写入（第 2 段）改的是内存页，磁盘校验看不到；必须配第 3 条。

## 2. 可执行内存（断第 2 段）

- 不允许同时 RWX 的页：申请时 RW，写入后 `VirtualProtect`/`mprotect` 改成 RX；
- 监控 `VirtualAlloc`/`mmap` 后紧跟一次写入再改权限的序列 —— 这个组合本身就很少见；
- 控制流完整性（Windows CFG / Linux CET）：间接跳转落到非函数入口就直接终止。

这是整条链上**最便宜也最有效**的一处：它不依赖知道载荷长什么样。

## 3. 代码洞（断第 3 段的空间前提）

`SLACK_CAVE` 之所以存在，是因为很多二进制里 `.text` 尾部有对齐填充。
链接时用 `-Wl,--no-rosegment` 之类的选项减少空隙、把节区对齐调到最小，
就能让「找不到足够大的洞」成为常态。这条不需要运行时成本。

## 4. 行为面（不针对链，针对结果）

- 进程创建子进程并立刻写入其内存 → EDR 的高价值信号；
- 目标进程出现新的可执行页且其内容与任何已加载模块都不匹配 → 同上；
- 网络连接从「刚被写入过内存」的进程发出 → 强关联。

## 5. 交付侧（让链条对审计可读）

- 每个补丁点记录 `偏移 / 原始字节 / 补丁字节 / 回滚命令` —— 本包的 `injector.py` 正是这个形状；
- 报告里把「链条已生成」与「目标可被接上」分开写：前者是工具输出，后者需要一次真实验证。

## 一句话

第 2 条（可执行内存策略）挡住大多数现成载荷，第 1、3 条挡住针对性改动，
第 4 条兜住前三条都漏掉的情况。只做其中一条，等于告诉对方从哪一侧进来。
