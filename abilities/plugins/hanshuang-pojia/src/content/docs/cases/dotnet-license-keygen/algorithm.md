# 算法全解：三段哈希、19 个五比特组与 192 字符的结构

> 配套：`cases/dotnet-license-keygen/reverse-engineering`（拆包、解壳、验收）
> 常量与结构保留；盐值与真实邮箱已删除；样本哈希与产物不在本仓库。

---

## 一、常量

| 名称 | 值 | 备注 |
| :--- | :--- | :--- |
| 字符集 | `23456789ABCDEFGHJKLMNPQRSTUVWXYZ` | 32 字符；剔除易混的 `0` `1` `I` `O` |
| 密钥长度 | `192` | 定长，长度不等直接拒绝 |
| 校验位起点 | `160` | 从第 160 个字符开始 |
| 校验位长度 | `19` | 19 × 5 = 95 bit |
| 盐值 | 固定字符串（与产品名相关） | **已删除**；仅用于黑名单 MD5 |

32 个字符不是随意的：它正好是 `2^5`，所以校验位能被切成 5-bit 组。
剔除 `0/1/I/O` 的理由是"人眼易混"，这本身也是一个信号——这个字符串是给人念的。

## 二、前置判定

```
if (key == null || email == null) return false;
if (key.Length != 192) return false;
identity = email.ToLowerInvariant();          // 大小写归一
```

归一化很重要：`User@…` 与 `user@…` 必须得到同一个校验位，否则用户在输入框里改一次大小写就失效。
反过来，这也意味着**大小写不携带信息**。

## 三、三段哈希

全部作用于 `identity`，全部产出 32 位字。

### H1 — 多项式，乘数 43

```
h = 0
for c in identity:
    h = (h * 43 + ord(c)) & 0xFFFFFFFF
```

43 是素数，且 `43^k` 在 32 位下很快退化——这不影响使用，因为它只用于生成校验位，不用于抗碰撞。

### H2 — ELF 风格

```
h = 0
for c in identity:
    h = (h << 4) + ord(c)
    g = h & 0xF0000000
    if g != 0:
        h ^= g >> 24
        h ^= g
    h &= 0xFFFFFFFF
```

`g` 那一步是这个哈希的全部意义：不折回的话，累加器在高位溢出，结果随实现宽度而变，不可复现。

### H3 — 四轮移位异或

```
h = 0
j = 0
for c in identity:
    h ^= ord(c) << ((j * 8) % 32)
    j += 1
    h &= 0xFFFFFFFF
```

移位量按 8 的倍数轮转（0/8/16/24），所以每 4 个字符一轮，等价于按 32 位字做 XOR 折叠。

三段哈希之间没有耦合，各自独立，这是"作者只是想打散输入"的典型写法，而不是任何标准 KDF。

## 四、拼接与切片

```
v = (H1 << 64) | (H2 << 32) | H3          # 96 bit
```

从高位起取 19 组：

```
checksum = ""
for i in 0..18:
    group = (v >> (95 - 5*i)) & 0x1F
    checksum += CHARSET[group]
```

### 4.1 95 与 96 的差一

19 × 5 = **95**，而 `v` 是 **96** 位。因此：

- 第 1 组取 bit 95..91（含最高位）；
- 第 19 组取 bit 5..1，**bit 0 永远参与不到**；
- 等价说法：最后一组的最高位恒为 0，即第 19 个字符只能来自字符集前 16 项（`2`…`J`）。

生成器若让第 19 个字符取到后半区（`K`…`Z`），目标必然返回 false。而本地自洽的生成器/校验器
会双双通过——因为它们用了同一套错误位移。

### 4.2 96 位不能放进 `ulong`

```csharp
// 错误（C#）
ulong v = ((ulong)h1 << 64) | ((ulong)h2 << 32) | h3;   // h1 << 64 == h1 << 0
```

编译不报错、运行不抛异常、结果稳定——只是最高 32 位消失了。前 7 个字符左右会由错的位算出。

两种正确写法：

```csharp
// ① 任意精度
BigInteger v = ((BigInteger)h1 << 64) | ((BigInteger)h2 << 32) | h3;

// ② 三字切片，手工跨边界
int group(int i) {              // i = 0..18，从高位起
    int bit = 95 - 5 * i;       // 可能落在 64..95 / 32..63 / 0..31
    ...
}
```

第二种更繁琐但更可移植——Go、Java 的 64 位整型同样会退化。

## 五、密钥布局

```
[0 .. 159]    任意字符（从不校验）
[160 .. 178]  19 个算出的校验字符
[179 .. 191]  任意字符（从不校验）
```

合计 `160 + 19 + 13 = 192`。

比较是 `key.Substring(160, 19) == checksum`：精确、区分大小写、不 trim。
填充字符用同一字符集最稳妥——某些更严格的构建可能额外校验字母表，虽然本版本没有。

## 六、黑名单

校验位通过后，再做一次：

```
if MD5(lower(identity) + SALT) in BLACKLIST: return false;
return true;
```

黑名单是 **6 条**硬编码 MD5 摘要。要点：

- 它是**按身份**（不是按密钥）封禁，说明作者想拦的是"某些已知邮箱"；
- 6 条且随构建固化，没有吊销通道 → 只能靠发版更新；
- 盐值使摘要无法离线核对（盐已脱敏），但机制与条数是可观察的。

把它写成"6 条"而不是"一长串哈希"，是因为**数量本身就是结论**：这不是防护，是名单。

## 八、强度评估

| 项 | 值 | 含义 |
| :--- | :--- | :--- |
| 参与校验的字符 | 19 / 192 | 173 个字符是装饰 |
| 校验位有效熵 | 95 bit（其中最后一位恒 0 → 实际 94 bit 可变） | 不是 MAC，因为**没有密钥** |
| 绑定对象 | 身份串 | 身份串是用户自己输入的公开值 |
| 黑名单 | 6 条 | 无吊销通道 |
| 签名 | 无 | 任何人都能对任意身份算出合法密钥 |
| 服务端 | 离线可用 | 客户端单独决定 |

一句话结论：**这是一段公开输入的确定性函数，而不是凭据。** 密钥的"长"与"随机外观"都不改变
这一点——长度只是把 19 个字符埋进 192 个字符里。

### 与真签名方案的对照

| 方案 | 攻击者需要什么 | 是否可离线 |
| :--- | :--- | :--- |
| 本案（哈希校验和） | 读一遍算法 | 是 |
| HMAC + 客户端密钥 | 提取密钥 | 是（密钥会泄露） |
| Ed25519 / ECDSA 签名 | **签发私钥**（无法从客户端取得） | 是（离线验签） |
| 在线权益 | 服务端漏洞或中继 | 否 |

第三行是这类软件真正需要的：离线可用，且客户端只验签、不计算。

## 九、实现陷阱清单

| 陷阱 | 现象 | 处置 |
| :--- | :--- | :--- |
| 96 位拼接用 64 位整型 | 前几个字符错，但本地自测通过 | 用 `BigInteger` 或手工跨字切片 |
| 19 组按 96 位取 | 第 19 个字符跑到后半区 | 从 bit 95 起算，或显式置最后一组最高位为 0 |
| 忘掉 `ToLower` | 大小写混合的身份串算错 | 先归一 |
| 生成器每次 `new Random()` | 批量密钥完全相同 | 共享一个随机源 |
| 运行期写设置 | 退出后被程序覆盖 | 关闭程序后写入 |
| 填充字符超出字符集 | 某些构建拒绝 | 填充也用同一字符集 |
| 只做本地自洽测试 | 两个实现一起错 | 换语言重实现 + 反射验收 |
