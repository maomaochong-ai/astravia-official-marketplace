# 定制混淆器下的 .NET 授权校验还原：从壳到算法

> 目标：一款 .NET Framework 4.8 / 32 位桌面软件（约 2.5 MB），Inno Setup 打包（约 12 MB）
> 版本：6.3 正式版 与 7.0 Beta（7.0.0.9）
> 结论：校验函数 `CheckLicense(email, key)` 是**纯本地、纯算术**的——没有签名、没有服务端、没有密钥
> 脱敏：产品名、域名、盐值、真实邮箱、样本哈希均已移除

---

## 一、为什么这个案子值得写

同一个"授权校验"，在不同实现下会走向完全不同的结局：

| 实现形态 | 结局 |
| :--- | :--- |
| 验签在虚拟化运行时内（见 `cases/execryptor-vm-activation/`） | 静态不可还原，**不存在本地算号路径** |
| 验签是 Ed25519 等真签名（见 `cases/ed25519-offline-keygen/`） | 只能去找权威私钥的泄露，不是还原算法 |
| **验签是"身份串的哈希 → 查表 → 定长校验位"** | **还原算法即构造密钥，纯算术** |

本案属第三类。区分它们只需要一个问题：**被校验的值是不是由公开输入推出的**。
如果是，它就是校验和（checksum），不是凭据（credential）。

## 二、样本与保护

### 2.1 拆包

Inno Setup 6.1 安装器，`innoextract` 直接解开，得到：

```
app\项目F.exe          .NET Framework 4.8，32 位，约 2.5 MB
app\项目F.pdb          ← 符号文件被误打包（意外收获）
```

PDB 的存在是这类案子里最省时间的一件事：混淆器改的是元数据与 IL，不改 PDB 里的源文件名与行号，
于是"哪个类型是业务入口"从猜测变成阅读。

安装器同时覆盖 6.3 与 7.0 Beta 两个版本 —— 这为后面的"算法是否变化"提供了最直接的实验条件。

### 2.2 保护：不是 ConfuserEx，是自家定制

三层，互相独立：

| 层 | 机制 | 观察 |
| :--- | :--- | :--- |
| 方法体加密 | IL 从元数据剥离 → 嵌入资源加密流 → 运行时解密后经 `DynamicILInfo.SetCode` 注入 `DynamicMethod` | 静态反编译只看到 stub |
| 字符串加密 | 字符串变 token 索引，由 `Reflection.Emit` 生成的动态方法做 XOR 链解密 | 常量全部不可见 |
| 控制流混淆 | `while(true) + switch` 状态机 + 垃圾指令 | 结构可读但无常量 |

判定"定制"而不是通用工具，是因为没有 ConfuserEx 的 `ConfusedByAttribute`、没有 Reactor 的
`#License` 资源、也没有常见的 anti-tamper 段。特征缺失也是证据。

### 2.3 v7 的加密面反而变小

| 版本 | 被 token 化的方法 | 可静态反编译的方法 |
| :--- | :--- | :--- |
| 6.3 | 全程序集 | 极少 |
| 7.0 Beta | **5 个**（校验函数 + 4 个哈希函数） | 约 7,000 个 |

这是一个反直觉但常见的现象：新版把保护收缩到"真正敏感的几个方法"上，其余全部放开。
对审计者是利好——只需要打穿 5 个方法；对防护者则是把攻击面精确标注出来的失误。

## 三、动态解壳：三步拿到真实 IL

### 3.1 找执行器

方法体的解密与注入由同一个执行器完成，它自身**不能被加密**（否则没人能解密）。

| 版本 | 执行器 |
| :--- | :--- |
| 6.3 | `\ue1cd.\ue00f` |
| 7.0 Beta | `\ue215.\ue00f` |

定位方式：在程序集里找"调用 `DynamicILInfo.SetCode` 的方法"，或找持有加密资源流的单例字段。

### 3.2 补 token 分配器

动态方法的成员引用是**运行时分配的 token**。不记录映射，dump 出来的 IL 就是一堆整数——
这是本类案子里最典型的时间黑洞。

做法：用 Harmony 在 `DynamicILInfo.GetTokenFor` 上打前置补丁，记录"动态 token → 成员引用"
（`MethodBase` / `FieldInfo` / `Type`），以字典落盘。

```
token 0x0200000A → MethodInfo: <类型>::<方法>(string, string)
token 0x04000003 → FieldInfo : <类型>::CHARSET
```

有了这张表，IL 里的 `call 0x0200000A` 立刻变成可读的名字。

### 3.3 dump 并反汇编

在目标方法被构建的时刻，读取 `DynamicMethod` 的 IL 字节流，与 token 表一起导出，
然后用 `ildump`（dnlib）或 ILSpy 的"打开 IL 字节"能力读。

校验函数解出来约 **226 字节** IL。这个体量说明问题：一个真正的验签实现不会这么短。

### 3.4 字符串表批量还原

字符串共 3,148 个 token（v7）。逐个调用解密器太慢，做法是：定位解密函数，用反射批量喂 token，
一次性导出全表。本案需要的四个常量（字符集、盐、长度、位置）都在表里。

## 四、算法还原

拿到 IL 后，它就是一段直白的算术。逐句转写为高层描述，得到四个常量与三段哈希：

| 常量 | 值 | 说明 |
| :--- | :--- | :--- |
| 字符集 | `23456789ABCDEFGHJKLMNPQRSTUVWXYZ` | 32 字符，剔除 `0/1/I/O` |
| 密钥长度 | 192 | 定长 |
| 校验位起点 | 160 | 从第 160 个字符开始 |
| 校验位长度 | 19 | 5 bit × 19 = 95 bit |
| 盐值 | 固定字符串（与产品名相关，**已删除**） | 仅用于黑名单 MD5 |

三段哈希（均作用于**小写化**的身份串）：

1. **H1 多项式**：`h = (h*43 + c) mod 2^32`
2. **H2 ELF 风格**：`h = (h<<4) + c`，`g = h & 0xF0000000`，若 `g` 非零则 `h ^= g>>24; h ^= g`
3. **H3 四轮移位异或**：`h ^= c << ((j*8) % 32)`

拼接：`v = (H1 << 64) | (H2 << 32) | H3`（96 bit）
切片：从高位起取 19 个 5-bit 组，逐组查字符集
比较：`key[160..178] == 结果`（精确、区分大小写）
额外：`MD5(小写身份 + 盐)` 命中 **6 条**硬编码摘要 → 拒绝

详细推导见 `cases/dotnet-license-keygen/algorithm`。

### 4.1 两个必须注意的算术事实

**① 95 不是 96。** 19×5 = 95，而 `v` 是 96 bit。于是第 19 个 5-bit 组的最高位永远取不到，
最后一个字符只能来自字符集的前 16 项。生成器若让第 19 个字符取到上半区，目标必然拒绝，
而本地"自洽"的生成器/校验器对会双双通过——因为它们错得一致。

**② 96 bit 放不进 `ulong`。** C# 里 `h1 << 64` 等于 `h1 << 0`，最高 32 位静默丢失。
前几个字符于是由错误的位算出。必须用 `BigInteger`，或保留三个 32 位字、手工跨 64 位边界切片。

第二条是本案例最重要的一课，见第六节。

## 五、激活路径

```
ProService.ActivateNewLicense
  → CheckLicense(email, key)          本地校验（离线，成功即可）
  → HTTP POST <AUTH-SRV>              ← 非必需；断网也能完成
  → 写 项目F5License 设置
```

| 观察 | 含义 |
| :--- | :--- |
| 选项页支持纯离线激活 | 判定完全在客户端 |
| 设置持久化于 `%APPDATA%\项目F\UserProfile\Settings\Preferences.json` 的 `Settings` 对象 | 点分键 `…ProLicense.Name / .Email / .Key` |
| **写入前必须退出程序** | 程序退出时会用内存中的设置覆盖文件 → 运行期写入被回滚 |

最后一条是这类案子最迷惑的失败形态：密钥正确、`CheckLicense` 返回 `True`、界面仍显示未授权。
问题不在校验，在写入时序。

## 六、跨实现验证：自洽测试会掩盖移植错误

还原出算法后，第一步不是造密钥，而是**用两种语言各实现一次**。

| 实现 | 结果 |
| :--- | :--- |
| C#（照 IL 直译，`ulong` 拼接） | 自测通过：生成器与校验器一致 |
| Python（独立实现，原生大整数） | 与 C# 输出逐字符对比 → **第 3 个字符起不一致** |

差异指向拼接：C# 的 `(h1 << 64)` 退化，Python 的 96 bit 正确。

**结论（可复用）**：任何含"宽值拼接"的算法，必须在至少一种原生支持该宽度的语言里实现一次。
C# 的生成器与校验器共享同一个错误表达式，因此自洽测试**结构上不可能**发现它。

第二条同类陷阱：批量生成时若每次 `new Random()`，同一毫秒内生成的密钥会完全相同——
表现为"算法对输入不敏感"的假象。共享一个随机源即可，但前提是先做"不同输入 → 不同输出"的检查。

### 验收

| 检查 | 期望 |
| :--- | :--- |
| 逐字符对比（两实现） | 一致 |
| 工作示例 | 三个哈希与 19 字符校验位可复现 |
| 反射调用真实 `CheckLicense` | `True` |
| 激活后功能门 | 打开 |
| 退出重启后 | 仍为已激活（写入时序正确） |

反射调用这一行不可省：前四项证明"两个实现一致"，只有它能证明"与目标一致"。

## 七、版本对比：先验证，再决定是否重做

7.0 Beta 的保护升级看起来像是"算法也换了"。实际做法是**先跑旧实现**：

| 项 | 6.3 | 7.0 Beta |
| :--- | :--- | :--- |
| 算法常量 | 同上 | **逐字节一致** |
| 混淆类名 / token | — | 不同 |
| 被保护方法数 | 全程序集 | 5 |
| 旧版密钥生成器 | — | **零适配通过** |

一天的工作量由此省下。方法论上更重要的推论是：

> **保护升级不是算法变更的证据。** 先 diff 那 5 个方法的 IL，再决定要不要重新还原。

## 九、根因

| # | 根因 | CWE |
| :--- | :--- | :--- |
| 1 | 权益判定完全在客户端，且判定依据是**公开输入的可计算函数** | **CWE-602** |
| 2 | 校验位只有 95 bit 且无密钥、无签名，不构成任何凭据 | CWE-345 类（真实性未验证） |
| 3 | 192 字符中 173 个不参与校验，长度制造了虚假的强度感 | CWE-693 |
| 4 | 黑名单只有 6 条且随版本固化，无吊销通道 | CWE-693 |
| 5 | 混淆把"少数方法"保护得很好，却没有改变"客户端单独决定"这一事实 | CWE-693 |

第 1 条与第 5 条合起来，解释了"投入很大、收益很小"：保护的成本落在算法可见性上，
而风险落在权威位置上。

### 整改

| 层 | 措施 |
| :--- | :--- |
| 权威 | 服务端签发**签名权益**（Ed25519 / ECDSA），客户端只验签不计算；离线场景用可离线的签名凭据 + 短期有效期 |
| 绑定 | 凭据绑定购买记录与机器指纹，含签发时间与到期时间，可服务端吊销 |
| 算法 | 若必须保留本地校验，改用 HMAC（密钥不落客户端）或签名；绝不能是"公开输入的哈希" |
| 数据 | 设置文件中的凭据做完整性保护（签名字段），防外部改写 |
| 工程 | 不把 PDB 打进安装包；混淆面覆盖"判定与消费"，而不只是"算法" |

## 十、方法论沉淀

1. **先判类型**：被校验值是否由公开输入推出？是 → 校验和，可构造；否 → 凭据，需找权威。
2. **先找执行器**：定制混淆器的通用解法是定位"解密 + 注入"的那一个方法。
3. **先补 token**：动态方法没有 token 映射就是不可读的整数流。
4. **两语言实现**：宽值拼接类错误只能被"另一种宽度"抓到。
5. **反射验收**：自洽测试证明不了与目标一致。
6. **写前退出程序**：设置回写会覆盖外部写入，这是最常见的假失败。
7. **先跑旧实现**：保护升级不等于算法变更。

## 十一、限制与未验证项

| 项 | 状态 |
| :--- | :--- |
| 服务端是否另有在线校验 | `[unverified]` 离线路径不访问服务端；不排除存在独立在线端点 |
| 更新版本是否加入签名 | `[unverified]` 仅覆盖 6.3 与 7.0 Beta |
| 黑名单的语义 | `[observed]` 6 条硬编码摘要，机制清楚；具体条目不在本仓库 |
| 盐值 | 已删除（真实产品名）；其存在与位置已记录 |
| 工作示例数值 | `[observed]` 上游以某示例邮箱演算所得；邮箱已脱敏，数值不可直接复现 |
| 分发风险 | 本仓库不含任何生成器实现或密钥产物 |

最后一行是有意的：这类案例的价值在于"证明它是校验和"，而不在于提供现成的密钥。
把结论写清楚，比把工具发出去更有用。
