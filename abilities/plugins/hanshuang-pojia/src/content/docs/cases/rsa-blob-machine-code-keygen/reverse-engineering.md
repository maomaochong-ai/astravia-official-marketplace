# 项目I —— RSA 签名 blob + 机器码请求串：一条走不通的算号器路线

> 案例类型：Windows 组件型软件（主程序 + 配置器）· BCrypt/CNG RSA 验签 · 本地激活数据（CWE-602）
> 脱敏：产品名、公司名、`CONST` 常量值、完整模数与样本哈希均已移除；保留 RVA、文件偏移、blob 布局、字节序列与判据。

本案例最值得写下来的不是"怎么绕过"，而是**为什么某条路走不通**，以及走不通之后剩下的是哪条。
大量授权审计的时间都花在"再试一次算号"上，而真正决定收益的是尽早把不可能的那条路封死。

---

## 一、目标画像

| 项 | 判定 | 判据 |
| :--- | :--- | :--- |
| 形态 | 安装器 + 主程序 DLL + 配置器 EXE | 安装器为 7-Zip SFX（归档偏移 `0x14000`） |
| 安装器导入表 | **无网络、无加密 API** | 授权逻辑不可能在安装器里 |
| 主组件（x64） | `项目IX64.dll` | 导入 BCrypt、读写授权注册表键 |
| 主组件（arm64） | `项目IA64.dll` | 同源逻辑，公钥 blob 另有一份 |
| 配置器 | `项目ICfg.exe` | 内含 `activate.php` / `sibsab.php` / `SIBActivated` 等交互串 |
| 授权数据 | `HKCU|HKLM\Software\项目I\License\ActivationData`（REG_BINARY） | base64 解码后为 RSA 签名 |
| 校验 | 本机 RSA 验签（`e = 0x10001`） | 无服务器在线校验 |

第一行与第二行是本案例的第一个判据：**安装器不导入加密 API，说明真正的校验在组件里**。
先确认这一点，可以省掉在 SFX stub 里翻找的半天。

## 二、静态分析流程

### 2.1 Ghidra headless + 两个自写脚本

组件较大，全量分析耗时；但组件不像 Qt 程序那样有成千上万个 moc 字符串可用作锚，
所以这里用"关键字枚举 + 按地址补漏"的两段式：

```
SabFindActivation.java
  → 枚举 DefinedData，命中关键字（激活错误串、CONST、注册表路径、LicenseHash）
  → 收集所有引用函数
  → 批量反编译，落盘为可 grep 的伪 C

SabDecompileByAddress.java
  → 已经由动态/交叉引用得到入口地址的函数（Ordinal_100/101/103、机器码函数）
  → 按地址精确反编译，补齐遗漏
```

两段式的意义：第一遍不需要知道函数边界，只需要"所有碰到这些字符串的地方"；
第二遍针对"已知入口但没被字符串覆盖到"的函数。两者合起来，覆盖率远高于单纯的全量反编译，
时间却只有几分之一。

### 2.2 关键字符串锚

| 字符串 / 特征 | 作用 |
| :--- | :--- |
| `SIBActivation: mismatch; expected…` | 校验失败日志，直接指向 `Ordinal_102` |
| `CONST`（64 hex） | 参与签名载荷的常量，`.rdata` VA `0x1800A3E90` |
| `Software\项目I\License` | 授权数据注册表根 |
| `LicenseHash` | 注册表值名，同时是载荷首字段 |
| `RSA1`（blob 魔数） | 公钥定位：`rz-find -s "RSA1"` 一次命中 |
| `SABALL` | 载荷尾部的固定标记（立即数 `0x41424153` / `0x4C4C`，小端） |

用结构（`RSA1` blob 头）而不是词义（"activation"）去找公钥，是这类目标最省时的一条：
blob 自带 `bitLength` / `cbPublicExp` / `cbModulus` 字段，读一次就把算法、指数、模长全确定下来。

## 三、还原点

| 功能 | 位置 | 要点 |
| :--- | :--- | :--- |
| `LicenseHash = md5hex(key)` | `FUN_180001d24` | 默认值长度 > 0x1e 时才迁移（两种历史形态并存） |
| 机器码 A | `FUN_180001a90`（`0x2D1400` SMART + `0x560000` 回退，word-swap） | 取不到 SMBIOS 时用固定占位串 |
| 机器码 B | `FUN_180001b9c`（`'RSMB'` Type1 UUID） | 无此标识时同样回退 |
| 请求串 96 hex | `Ordinal_103` | `lstrcpy` + `lstrcat` 三段拼接 |
| 验签滑窗 | `FUN_180001e8c` | **同一个 128 字节缓冲区被 Ghidra 切成十几个局部变量** |
| `md5hex(x)` | `FUN_180001a20` | `BCryptHash(MD5)` 后 `%02x` × 16，32 字符小写 |
| 试用判定 | `Ordinal_100` / `Ordinal_101` | 首装时间戳 + 100 天 + 2028 年硬编码horizon |
| 验签出口 | `Ordinal_102` | 返回 1 表示已激活，并写 `out[0]='1'` |

表中最后一行是整条链的关键：**验签是一个按序数导出的函数**，没有名字。
这对补丁有利（入口稳定、可直接调用），对分析稍麻烦（需要靠字符串与调用关系定位）。

第五行的坑必须单独讲：Ghidra 把同一块 128 字节输出拆成 `local_b8` / `local_98` / `local_78` /
`iStack_58` / `asStack_54` 等多个变量，看上去像五个独立结构体。**先认出这是一个缓冲区**，
否则会去解释"某个变量的第 32 字节"，而那个字节其实是另一个字段的开头。

## 四、落地与补丁

### 4.1 为什么不是算号器

在动手之前先做了三项否定检查：

| 检查 | 结果 |
| :--- | :--- |
| user key 是否含本地自洽校验段（对照同族另一产品有 19 字符校验串） | **没有** → key 不是自校验的，但也意味着 key 本身不携带可推导信息 |
| 能否用内嵌公钥伪造激活数据 | **不可能**（需要私钥指数） |
| 能否分解模数 | 1016 bit，试除到 2663 命中一个小因子，**剩余 ~1005 bit 余因子不可分解** |

第三条是决定性的：找到一个 2663 的小因子很容易，但 `n = 2663 × (1005 bit 质数)`，
把那个大质数分解出来不在现实算力范围内。**"弱密钥"与"可分解"是两件事**，
报告里必须分开写，否则读者会以为"既然模数小，那就能算"。

于是可行的路线只剩两条并做：

1. **本地要素复现**：把请求串 `R` 在本机算出来，从而能为自己控制的机器生成激活数据；
2. **`Ordinal_102` 验签入口补丁**：让校验函数直接返回"已激活"，并配合防回退。

### 4.2 补丁与验收

补丁落在验签入口，保留状态字节写入（`out[0]='1'`），因为上层会读它。
验收不通过 UI，而是**直接按序数调用**：

```
ctypes: GetProcAddress(dll, ordinal 102) → 直调 patched DLL
  返回 1，out[0] == '1'                    [observed]
```

这一步是整份证据里最硬的一条：它不依赖任何界面文案、不依赖 shell 状态，
只证明"这个导出函数现在说已激活"。

### 4.3 防回退

`SabRollbackGuard` 的做法与配置无关、与字节有关：更新后重新检查目标字节，
只在"仍是原版"时重写；`.bak` 独立保留，还原不依赖守卫进程存活。
具体触发点与抑制映射写在工具注释里，本仓库不搬可执行脚本，只保留形状。

## 五、动态验证

| 验证项 | 结果 |
| :--- | :--- |
| 直调 `Ordinal_102`（patched） | 返回 1，`out[0]='1'` `[observed]` |
| explorer 重启 ×2 后模块重载 | 状态保持 `[observed]` |
| 注册表 before/after diff | 记录激活态键的变化 `[observed]` |
| 打补丁前同机调用 | 返回非 1 `[observed]` |

第二行是"持久性"的正确验证方式：**必须让模块重载**。只重启进程时，状态可能仍在内存里；
只有 shell 重启导致 DLL 重新映射之后仍然激活，才能说明状态落到了注册表。

## 六、试用判定的设计问题

试用逻辑把"首装时间"锚定在某个注册表键的**最后写入时间**上，键名由 `md5hex(产品名 + 分组)`
与固定后缀拼成，宽限 100 天，并额外容忍两种情况：系统时间早于该时间戳、年份 ≥ 2028。

这带来两个由设计产生的旁路：

- 时间戳跟着系统时钟走 → 回拨时钟即可延长；
- 硬编码年份上限 → 到 2028 年后所有机器都"未过期"。

第二点尤其值得写进报告：它不是攻击者的发现，而是产品自己埋的定时炸弹 ——
到期判定会在某一天集体失效，而厂商拿不到任何信号。

## 七、结论与限制

- **keygen 路线不成立**（`[observed]`：小因子之外不可分解；`[inferred]`：key 不含自洽校验段）。
- 可行路线为「本地要素复现 + `Ordinal_102` 补丁 + 防回退」，验收以直调导出为准。
- 在线激活路径未纳入本案例（配置器内有 `activate.php` 等串，但服务端流程未覆盖）。

## 八、限制与未验证项

| 项 | 状态 |
| :--- | :--- |
| 在线激活（`activate.php`）的服务端流程 | `[unverified]` 仅见客户端串，未抓包 |
| 请求串中机器码 A/B 的分支在所有硬件上的取值 | `[inferred]` 按 SMBIOS / 卷序列两条回退推断，未跨硬件矩阵验证 |
| arm64 组件与原 x64 组件的行为一致性 | `[unverified]` 只确认公钥 blob 另有一份 |
| 模数分解的实际耗时（是否值得尝试 ECM） | `[unverified]` 未做 ECM/P-1 长时运行，仅按位长判断不可行 |
| 试用时间戳键在其他 Windows 版本上的可写性 | `[unverified]` 仅在当前测试机验证 |
| 防回退守卫在系统更新后的恢复率 | `[observed]` 单次模拟覆盖可恢复；跨版本未测 |
