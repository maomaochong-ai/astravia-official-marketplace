# 加壳 ELF：分清壳与程序，并为每个地址标上来源（CWE-602 语境下的取证纪律）

> 案例类型：静态样本判定与内存转储／目标：一个被加壳的 64 位 ELF／脱敏：路径与产品名不落文档，样本哈希写为 `<实测哈希>`，偏移以 `<实测偏移>` 占位。

---

## 一、现场

样本是一个 64 位 ELF，`file` 说它「dynamically linked, stripped」。三个观察叠在一起才构成现场：

1. **字符串面塌陷。** `strings` 出来的可读文本只有二三十条，全部是装载提示（映射失败、内存不足、版本不符），没有任何业务词汇。
2. **导入面异常。** 动态符号表里只有寥寥几个名字，且集中在 `mmap`、`mprotect`、`madvise`、`dlopen`、`dlsym` 这一族——一个需要打印、格式化、读文件的程序不会只导入这些。
3. **段布局可疑。** 至少一个 `PT_LOAD` 同时带写与执行权限，而它的文件大小远小于内存大小；入口点落在一个看起来不像 `.text` 的位置。

三条同时成立时，「这个文件不是程序」已经是很强的假设了。但假设不是结论：静态上完全可能出现另一种解释——一个静态链接、只做内存操作的守护进程，或者一个刻意裁剪过的 musl 程序。区别要靠第五节的反证来划。

真正的代价出现在后面：如果现在就打开反汇编器开始读，读到的每一条指令都是壳的指令，而报告的读者会以为它们是产品的逻辑。所以这个案子的第一产出不是「找到了什么功能」，而是**一份标明「这段字节属于壳还是属于载荷」的对照表**。

## 二、判定

判定不靠单一指标，而是五个信号各自算分、各自留证据：

| 信号 | 权重 | 判据 | 证据形态 |
| --- | --- | --- | --- |
| `packer-marker` | 45 | 文件里存在已知 stub 的标记字节 | 标记字符串 + 文件偏移 |
| `rwx-segment` | 30 | 某个 `PT_LOAD` 同时可写可执行 | 段名 + vaddr + 原始字节数 |
| `high-entropy` | 25 | 可执行段熵 ≥ 阈值（默认 7.2） | 该段熵值 + 采样字节数 |
| `no-libc-symbols` | 20 | 动态链接却没有 libc 函数名 | 「缺失即证据」，并列出实际存在的 loader 符号 |
| `entry-outside` | 20 | 入口点不在任何 `PT_LOAD` 覆盖范围内 | 入口值 + 最近段的结束地址 |

权重是阅读辅助，不是判决书：≥55 判 `packed`，25–54 判 `suspicious`，否则 `unpacked`。这个分档写进工具而不是写进人的记忆，是因为同一批样本要由不同的人重复判断，分档口径必须一致。

熵这一项要特别小心。熵高只说明字节分布均匀，而**已经压缩过的资源、加密过的常量区、静态链接的 Go/Rust 二进制的代码段**都能达到 7.5 以上。所以「高熵」必须与「导入面塌陷」同时出现才有意义；单独一个高熵段只能进 `suspicious`。

工具不做的一件事：它不判断「这是不是恶意」。壳是中性的，签名过的商业保护器也是壳。判定只回答「磁盘上的可执行字节是不是待分析的对象」。

## 三、取证

先自检，再跑样本，两步的输出都要留在记录里。

```bash
cd tools
python3 elf_pack_scan.py --self-test
python3 elf_pack_scan.py --sample suspect.bin --min-entropy 7.0
```

自检的两行是证据链的起点：`kit self test: 44/44` 说明共享解析层在合成 PE/ELF/DEX 上都通过，`elf_pack_scan self test: 8/8` 说明这个工具在同一次运行里能把「有壳」和「无壳」两个样本分开（合成样本的壳标记是 `UPX0`，干净样本没有）。没有这两行，工具输出就只是文本。

正式跑之后，记录里要能贴出四张表：

| 表 | 关键列 | 为什么需要 |
| --- | --- | --- |
| segments | 段名、vaddr、raw、vsize、熵、W/X 标志 | 让人一眼看出「文件大小 ≠ 内存大小」 |
| packer markers | 偏移、标记 | 把「像壳」变成「是某个壳」 |
| signals | 信号、权重、证据 | 分档的唯一依据 |
| verdict | 分数、分档、结论句 | 后续步骤的分岔点 |

四张之外还要单独记两条：

1. **两个文件的哈希。** 原始文件与转储文件各算一次（`<实测哈希>` 形式记录），并在每个后续结论旁注明地址属于哪个文件。
2. **解包循环的地址。** 它属于原始文件；写的时候必须带「in packed.bin」这种限定词。这一条是这个案子最容易丢的纪律：混写两个地址空间的报告无法复现。

## 四、否证

**否证一：这是静态链接的正常程序。** Go 与 Rust 的静态二进制熵高、导入少、符号被裁，看上去和壳一样。反证方式有三条：找 `.note.go.buildid` 或 Go 的构建信息字符串；找 Rust 的 panic 路径文本；看是否存在大量连续的 libc 兼容符号（静态链接会把它们编进去，即使不导出）。三条里命中一条，就应该把分档降回 `suspicious` 并改用手工反汇编确认。

**否证二：高熵来自资源而不是代码。** 如果高熵段不带执行权限，或者它的大小与某个已识别的压缩资源块一致，那么熵说明的是资源被压缩，不是代码被加密。

**否证三：入口点在外是链接脚本的写法。** 少数嵌入式工具链会把入口放在一个不映射的地址上，由外部引导代码跳入。判据是：如果 `p_filesz` 为 0 的段存在、或程序头里出现解释器路径为空的情况，需要先排除这种构建习惯，再宣布「入口被改写」。

**否证四：`UPX0` 只是一个名字。** 有的加固器会故意留下别的加固器的标记名作为诱饵。反证是「标记 + 行为一致」：真的 UPX 壳会在入口附近出现一段读自身、写目标、再 `mprotect` 的循环。只有标记而没有循环，标记就只是字符串。

**否证五：你以为的载荷是第二次加壳。** 转储之后如果载荷本身仍然是高熵、仍然没有 libc 符号，那就是二层壳。此时正确的动作是继续跟一层，而不是在报告里把第一层载荷当成程序来分析。

## 五、复现

**步骤一：判定。** 用上一节的命令拿到分档。若为 `packed`，进入转储；若为 `suspicious`，先在反汇编器里读入口附近十几条指令再决定——常见的形状是「对某个数据段做循环、末尾经寄存器计算跳转」，读到这个形状就等于确认。

**步骤二：找循环。** 关注四个特征：

- 内层是 `memcpy` 形状的搬移，源地址落在镜像内部；
- 长度常量等于某个段的文件大小而不是内存大小；
- 搬移之后出现 `mprotect(..., PROT_EXEC)`；
- 尾部是经寄存器间接跳转，寄存器由目标地址加载。

把这四条的出现位置记在原始文件的坐标里。

**步骤三：转储，不要在本机执行。** 两种可接受的方式：在计算跳转处下断点后转储目标区间；或在沙箱里跑一次、唯一产物是转储文件。在分析机上直接运行样本不属于可接受方式，这一条不因为「只是看看」而放宽。

**步骤四：重新分析。** 对转储文件重跑同一套静态流程，然后逐项对照：

| 项 | 原始文件 | 转储文件 |
| --- | --- | --- |
| 熵（可执行段） | 高 | 应显著下降 |
| 动态符号数 | 极少 | 应出现业务函数名 |
| 字符串数 | 二三十条 | 应出现业务词汇 |
| 入口附近形状 | 循环 + 计算跳转 | 常规函数序言 |

**步骤五：验证与回滚。** 这个案子不改动样本，所以「回滚」指的是恢复分析环境：删掉转储文件、清掉调试器会话、把原始文件按哈希校验一次（确认没有被误写）。验证则是「同一份转储重复分析两次，符号表与字符串计数一致」——不一致说明转储期间内存还在变化，需要重做。

## 六、边界与遗留

- 只处理了一个样本、一个架构；32 位与 ARM 的段布局规则不同，结论不能平移。
- 如果载荷本身被虚拟化，停在一层，写清「已获得载荷，未获得其执行语义」。部分结果标注清楚是证据；凭推测补全的不是。
- 转储的完整性要单独说明：是否覆盖了全部 `PT_LOAD`、是否在跳转之前完成、是否可能被后续解密覆盖。三问任一未答，结论都要降级。
- 工具不执行样本、不写文件；报告里不要出现「工具跑过了所以安全」这类表述——它只说明字节被读过了。
