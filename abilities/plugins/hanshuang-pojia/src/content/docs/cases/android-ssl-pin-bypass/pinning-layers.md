# 证书固定：先判层，再动手，最后证明解密（CWE-602 的传输面）

> 案例类型：Android 证书固定层次判定与传输面复核／目标：一个拒绝代理的应用／脱敏：主机名写 `<AUTH-SRV>`，证书主题与指纹不落文档，样本哈希写为 `<实测哈希>`。

---

## 一、现场

现场是一句很短的失败：「把代理打开，应用就转圈，然后提示网络异常」。三个细节让这句话变得可分析：

1. 同一个设备上，浏览器走同一个代理是正常的——所以不是代理配置问题，是这个应用不接受。
2. 失败发生在**任何界面数据出现之前**，说明它在第一个请求上就断了。
3. 把它装到一个较新的系统版本上，错误文案不同，但行为一致。

这时候最自然的动作是装上通用绕过脚本然后重试。这个动作之所以危险，不是因为「不允许」，而是因为**它会成功**：很多通用脚本会关掉所有 `TrustManager` 校验，于是应用「能用了」。但「能用了」有两种完全不同的原因：

- 它真的在固定证书，被绕过了；
- 它根本没固定，之前的失败来自别的东西（代理的 TLS 版本、客户端证书、服务端按 IP 白名单拒绝），脚本恰好顺手改掉了那个原因的一部分。

这两种情况在结论上完全相反，而现象一样。所以现场的第二个观察必须是：**在动手之前，先把「它固定在哪一层」写下来**。

## 二、判定

Android 的固定有五个落点，而且经常叠加：

| 层 | 静态可见的证据 | 失败时的症状 |
| --- | --- | --- |
| network security config | `res/xml` 下的配置、`android:networkSecurityConfig` 属性 | 在任何应用代码之前失败 |
| OkHttp pinner | `CertificatePinner` 构造 + `pin-sha256` 常量 | 抛异常，消息里带主机名 |
| 自定义 TrustManager | 实现 `X509TrustManager` 且比较链 | 先接受任意证书，随后比较失败 |
| 内置证书 | `assets/`、`res/raw/` 下的 `.cer/.pem/.crt/.p12/.bks` | 与自定义 TrustManager 常同时出现 |
| native | `.so` 里的 BoringSSL/OpenSSL 校验符号 | Java 栈上没有任何相关帧 |

判据是「症状对层」而不是「层对症状」。原因很简单：内置证书是**材料**，不是机制；它必须被某一层读取才生效。一个包里存在 `.p12` 而没有读取它的代码，说明这个文件是打包遗留。工具的职责就是把「材料」和「机制」分开列，让操作者去对症状。

所以工具输出五层，每层两列：`present`（本包是否声明）与 `evidence`（声明的证据：条目名或字符串）。判定句由操作者写，形如：「三层同时存在，症状落在自定义 TrustManager 上，因此先处理这一层」。

## 三、取证

```bash
cd tools
python3 pin_surface.py --self-test
python3 pin_surface.py --sample app.apk
```

自检的第二行（`pin_surface self test: 7/7`）覆盖四个合成包：一个什么也没声明的、一个只有 OkHttp pinner 的、一个只有自定义 TrustManager 的、一个五层齐全的。断言里明确要求「五层齐全的那个包，`layers` 长度必须是 5 且每层 `present`」，这样工具在真样本上才不会把「层数」算错。

正式取证要固定三件事，缺一件就不能叫证据：

**1. 一次未经修改的失败。** 原包、原代理、一次请求，把拒绝的原文抄下来（异常类型、消息、HTTP 状态、TLS alert）。这份基线是后面所有比较的参照物。

**2. 同一请求在插桩后的结果。** 同一个端点、同一组参数、同一个账号。差异只有一个：插桩。两个运行的对照表才是证据。

**3. 响应体本身。** 200 不是证据。证据是响应里那个应用会显示的字段，它证明「会话被解开并读到了内容」，而不是「连接被允许了」。如果端点返回的是加密块、由应用另行解密，那么必须写清「传输层已解开，应用层未解」，因为这两件事对结论的影响完全不同。

这三件事对应的记录格式是固定的：

| 项 | 内容 |
| --- | --- |
| 层 | 五层中哪几层 present，各自证据 |
| 基线 | 未插桩时的失败原文 |
| 插桩 | 命中位置（类/方法/行）、脚本哈希 |
| 结果 | 响应状态 + 一个可验证的业务字段 |
| 回滚 | 移除脚本、恢复系统信任存储、卸载重装 |

## 四、否证

**否证一：不是固定，是双向认证。** 如果服务端要求客户端证书，而你的代理没有提供，症状与固定几乎一样。判据是 TLS 握手的 alert 类型，以及包里是否存在 `KeyManager` / `.p12` 被实际加载的路径。

**否证二：不是固定，是服务端按来源拒绝。** 换一个出口 IP 重试，或者看服务端是否返回了明确的地域/风控错误。这一条最容易被误判成「固定」，因为两者都表现为「换代理就不行」。

**否证三：不是固定，是 TLS 指纹。** 有的防护在服务端比对 ClientHello 的指纹（JA3 一类）。此时客户端完全没有固定代码，但换客户端就不通。判据是：静态五层全空 + 换一个同版本官方客户端走同一代理也不通。

**否证四：通用脚本的「成功」其实关掉了别的东西。** 常见的是把系统代理设置重置、或者把 `TrustManager` 换成信任所有证书，顺带让另一个本来失败的请求通过了。反证方式是「最小改动」：只替换证书校验的那一个方法，其他一律不动，看是否仍然通过。

**否证五：包里有一层，但它不在生效路径上。** `network_security_config` 存在，但清单没有引用它；`CertificatePinner` 存在，但构造它的代码在死分支里。判据是引用关系，不是存在性。工具的 `present` 只回答「声明了」，报告里必须再补一句「是否被引用」。

**否证六：命中但没证明。** 如果插桩后请求通过，但响应体是空的、或者是缓存的旧响应，那不能证明解密。清除缓存、换一个只在服务端存在的字段，再看一次。

## 五、复现

**步骤一：枚举。** 跑 `pin_surface.py`，把五层表格贴进记录。对每一层写一句「证据是什么」。

**步骤二：基线。** 原包装机、代理开启、一次请求。记录失败原文与时间戳。

**步骤三：最小插桩。** 只针对第二节判定出的那一层。若是 OkHttp，替换 `CertificatePinner.check`；若是自定义 TrustManager，替换 `checkServerTrusted`；若是配置层，则改配置或用运行期替换 `TrustManagerImpl`；若是 native，先确认 Java 栈上确实没有相关帧，再考虑二进制层。

**步骤四：成对运行。** 同一请求两次，差异只有插桩。给出两次的响应状态与一个业务字段。

**步骤五：回滚。** 移除脚本、恢复系统信任存储（如果是通过装 CA 做的）、清掉应用的网络缓存、必要时卸载重装。回滚后重跑一次基线，确认失败现象恢复——这一步是很多人跳过的，它同时也是「差异确实来自插桩」的最后一个证据。

## 六、边界与遗留

- 只截获了这一个应用的流量；同一台设备上其他应用的流量没有进入分析，也不应进入。
- 没有记录任何真实证书、令牌、账号标识；响应体里出现的凭据只以「存在、位置、长度」描述。
- **固定是控制，不是漏洞。** 绕过固定本身不构成缺陷；值得写的是固定后面有什么：服务端不校验的参数、凭固定保护的身份标识、以及在部分系统版本上接受用户 CA 的差异。
- 如果某一层缺席，只能写「本包未声明这一层」，不能写「该连接无保护」——服务端仍可能有别的强制手段。
- 未解问题要单列：例如 native 层是否参与、是否只有特定 ABI 启用。写「未验证」比写一个推断出的「是」更有价值。
