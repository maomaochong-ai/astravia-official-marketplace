# 商业级混淆 + 代码虚拟化之下，真正该打的是四处 IL 常量

> 目标：`项目N v2.2.4.3`（Windows .NET Framework 桌面系统优化工具 / WPF，`SHA-256 = <实测哈希>`，39,628,904 B）
> 运行时：.NET Framework 4.x
> 保护：Eazfuscator.NET 全保护模式（重命名 + 字符串加密 + 程序集代码加密 + 代码虚拟化）
> 结论：4 类授权架构缺陷，全部离线可复现；而最小补丁集只有 **4 处 IL 常量 + 1 个判据方法**。

## 0. 一句话结论

**保护层强度与安全架构是两个正交维度。** 这个样本把静态分析成本从小时级抬到天级：3,364 个类型全部改名，
字符串常量不在元数据里，一个 PE 节区整体 XOR，关键方法编译成私有字节码由内嵌解释器执行。而付费权益的
裁决点是一个普通的托管谓词，外加四处 `ldc.i4.1`。

| 层 | 保护手段 | 击穿结果 |
| :-- | :--- | :--- |
| L1 | 符号重命名 | ✅ 3,364 个类型全量反编译 |
| L2 | 字符串加密 | ✅ 运行时转储 **7,806 / 7,806** 条 |
| L3 | 程序集代码加密 | ✅ 算法完整还原，**15,380 个方法体全部解密** |
| L4 | 代码虚拟化 | ✅ 三层分离（RSA 封装 / 位置流 XOR / 方法寻址） |
| L5 | 自定义对称密码 | ✅ 参数、S-box、KDF、五级级联 100% 复刻 |
| L6 | 反调试 / 反 Dump | ✅ 未构成有效阻断 |

其中 **722,260 字节 VM 字节码全量解密为明文**，含 3,917 个成员记录、7,107 条可打印串。但这些都不是补丁
依据——补丁依据是第 3 节那张四行表。

## 1. 先画层表，再动手

顺序上最容易犯的错是先啃虚拟化。层表本身就是预算表：

| 层 | 它藏住什么 | 还原手段 | 代价 |
| :-- | :--- | :--- | :--- |
| 重命名 | 名字 | 直接反编译 | 分钟 |
| 字符串加密 | 常量 | 反射调用客户端自己的解密器 | 分钟 |
| 程序集加密 | 一个节区的字节 | 静态复现 keystream 派生 | 小时 |
| 代码虚拟化 | 少数关键方法 | 拆容器，不还原指令集 | 天 |
| 自定义密码 | 业务载荷 | 参数还原 + 测试向量 | 小时 |
| 反调试 | 分析者 | 实测无有效作用 | 分钟 |

表的顺序也是**价值顺序**。本案里字符串一转储，判据就在眼前；虚拟化那几天的产出对补丁毫无贡献。

## 2. 不还原混淆器，改为调用它

字符串解密器自身被控制流混淆（大量 `if (0 == 0) {}`、`_ = N; if (M == 0) {}` 噪声），静态还原成本极高。
正解是反射调用：

```csharp
Assembly a = Assembly.LoadFrom(sample);                       // 每个变体一个独立进程
Type     t = a.GetTypes().First(x => /* static string Decrypt(int) */);
MethodInfo m = t.GetMethod("…", BindingFlags.Static | BindingFlags.NonPublic);
for (int id = 0; id < N; id++) map[id] = (string)m.Invoke(null, new object[] { id });
```

结果 100% 准确，因为它就是程序自己跑的那段代码。**必须每个变体单独起进程**：同族程序集标识相同，同进程内
第二次 `Assembly.LoadFrom` 会返回已加载的实例，于是你测的是上一个文件。这个坑实测浪费了半天。

## 3. 程序集代码加密：派生可复现，方向可利用

### 3.1 定位目标节区

```text
节名前 8 字节 = 两个 uint32，其乘积
    == 0x65452714        →  目标加密节区
    != 0 且 != magic     →  参与密钥种子演化（即反篡改校验源）
```

节名本身就是标签，不是名字。先找「名字是随机字节」的节区，再用乘积确认。

### 3.2 种子演化与 keystream

```text
种子初值：num5..num8 = 1758353659, 186699061, 1283470176, 872273121

内容哈希演化（逐 dword 遍历所有非目标、非空节区）：
    nv = (num5 ^ v) + num6 + (num7 * num8)          # 32 位回绕
    num5, num6, num7, num8 = num6, num7, num8, nv

展开 16 项 keystream：
    for j in 0..15:
        arr[j] = num8;  arr2[j] = num6
        num5 = ROL(num6, 27); num6 = ROL(num7, 29)
        num7 = ROL(num8, 25); num8 = ROL(num5, 21)

    for i in 0..15:
        arr[i] XOR arr2[i]   (i % 3 == 0)
        arr[i] MUL arr2[i]   (i % 3 == 1)
        arr[i] ADD arr2[i]   (i % 3 == 2)
```

### 3.3 逐 dword 解密，与「可安全打补丁」的那条性质

```text
plain      = cipher ^ ks[i & 15]
ks[i & 15] = (ks[i & 15] ^ plain) + 1204611781      # 自反馈用明文，不是密文
```

因为状态以**明文**推进，加密与解密是同一个循环换个输出方向。于是可以「解密 → 改 4 个字节 → 加密回写」，
产出的文件**除补丁点外与原文件逐字节一致**：长度不变、元数据不变，体积与熵检查都看不出东西。

### 3.4 反篡改：机制正确，执法缺失

keystream 由**其它节区的内容**决定，所以改 `.text` / `.rsrc` 会让目标节区解不开——设计上是对的。但实测
观察不到「解不开即拒绝运行」：程序照旧启动，只是行为异常。这本身就是一条发现：**Fail-Open 的完整性校验**。

## 4. 授权链路：四处标记 + 一个谓词

### 4.1 PRO 权益在本地裁决（CWE-602）

26 个功能设置项中有 **4 项**在构造时被打上 PRO 标记：

```text
ldc.i4.1                     ; true = 需要 PRO
call  <PRO 标记写入方法>
```

另有**一个全局授权态查询入口**（`isPro()` 等价物），被 **8 处**托管调用点引用：

| 调用点 | 语义 |
| :--- | :--- |
| 激活页状态机 | `激活成功 && isPro()` → 显示「已激活」 |
| 优化流程 | `isPro() && Key 为空` → 直接判任务完成（跳过执行） |
| 优化流程 | `!isPro() \|\| Key.<条件>` → 执行实际任务 |
| 页面 ViewModel | `IsEditable && isPro()` → 调整项可编辑性 |
| 设置列表构建 | 决定列表项可用性 |
| 页面级闸门 ×3 | 若干模块可见性 |

所以最小补丁集是：**4 处 PRO 标记 + 把谓词改成恒返回 `true`**。其余 8 处调用点自动跟随，一行都不用动。

### 4.2 授权校验 Fail-Open 短路（CWE-287）

授权装载状态机中的唯一判定点：

```text
call  <凭据空值检查>          ; Key 是否为 null / 空 / "null"
brtrue.s  +offset             ; 视为「无需校验」→ 跳过服务端校验
```

空值检查的语义是：`null` / `""` / `"null"` → `true`（不用验），其它任意字符串 → `false`（必须联网验）。
也就是说**把凭据置空，客户端就自认校验通过，完全不发请求**。这是教科书式的 Fail-Open：把「无法判定」
当成「判定通过」。

但要如实写副作用：该旁路能让客户端自认通过，**不足以点亮首页 PRO 徽章**——徽章状态读的是服务端响应
字段；部分流程还会抛 `IndexOutOfRangeException`。所以它主要作为**授权体系设计缺陷的证据**，不是完整的
解锁手段。把这一点写清楚，比把危害写大更有用。

### 4.3 特权状态用户可写（CWE-863）

`HKCU\Software\<VENDOR-KEY>` 下 **71 个键**，全是明文布尔值，任何用户态进程可读可写，客户端读入后不做
任何完整性校验。授权类有 `Key` / `Guid` / `PinCode` / `IsPasswordProtected`；功能开关类有
`TweaXPRO` / `TweaXModel` / `IsAIonGEN` / `AITermsAccepted` / `ShowExperimentalTweaks` / `TweakerMode` /
`InstantTweaksApply` / `AdvancedUserTweaks` / `ShowHiddenTweaks` / `ICanReadAndBeCareful` /
`AlwaysShowFullDescription` / `ShowServicesManagerPage` / `ShowAffinityPage` / `IsNvidiaHardMode` /
`ShowMetrics` / `ShowRAMMetrics` / `ShowDISKMetrics` / `ForceEnableDrivers` 等。

另有导入通道 `HKCU\SOFTWARE\<IMPORT-VENDOR>\KEY`。**这一条不需要改二进制**，仅靠配置写入即可改变功能行为。

### 4.4 明文传输 + 硬编码密钥（CWE-319 / CWE-798）

| 问题 | 影响 |
| :--- | :--- |
| 授权主接口走**明文 HTTP**（`<AUTH-ENDPOINT>`） | 中间人可窃听 / 篡改 |
| 硬编码 AES-128 密钥（随包分发，全客户端共用） | 可离线解密历史流量并伪造授权响应 |
| 固定 64 字节前缀 ‖ AES-CBC 密文的封装 | 便于流量识别与重放 |
| 裸 IP 兜底地址 | 域名封锁后仍可通信，扩大攻击面 |

业务接口走 HTTPS（`<API-HOST>`），但授权接口不走——这个不一致本身就是证据。

## 5. 虚拟化：三层分离（不是还原 ISA）

容器 754,692 B，三层嵌套：

```text
┌─ 第 1 层：RSA-2048 / PKCS#1 v1.5 逐块
│     n = a1(128B FieldRva) ‖ Base64Decode(内嵌字符串)(128B)；e = 65537
│     块 256 B，明文 245 B/块（PKCS#1 固定 8 字节填充）→ 2948 × 245 = 722,260 B
│     2,948 块全部通过校验、填充长度恰为 8 → 构建期定长分块的铁证
├─ 第 2 层：位置流 XOR
│     seed = seedArg ^ (-559030707) = 0xB20B1B87     (seedArg = 1822868938)
│     plain[i] = cipher[i] ^ (byte)(seed ^ i)
│     熵 7.9997 → 6.7565，可打印串 6,161 → 7,107
└─ 第 3 层：方法寻址（名称即自描述令牌）
      令牌 → Ascii85 解码（字母表 '!'..'u'，K = 85⁴..85⁰，'z' 为全零组）
           → 位置流 XOR（seedArg = 1485391981）
           → 乱序 ReadInt64
           → VM 流偏移 → 方法记录
```

方法记录格式与指令编码：

```text
+0x00  18 字节记录头（签名 / 类型描述）
+0x12  [1 字节长度][方法名 ASCII]
+…     [u32 代码长度][代码区]

指令为 4 字节定长 token，操作码随机重排：
    0x42487a8f = ret            （几乎所有方法的最后一条）
    0x5d914689 = ldarg.0 / ldfld（12 字节方法首条；属性 getter 第 2 条）
    0xb4f09a23 = ldarg.0 引用型 this
```

**第 3 层才是真正的杠杆。** 解码可逆：XOR 之后那 8 个字节恰好是偏移小端字节的固定置换
（`a[0]=b0, a[7]=b1, a[1]=b2, a[2]=b3, a[4]=b4, a[3]=b5, a[6]=b6, a[5]=b7`），因此可以为**任意**偏移生成
合法令牌，也能逐字节复现原令牌。含义是：虚拟化方法的调用目标由一个短字符串决定，**改写字符串即可把调用
重定向到任意虚拟化方法**——不需要私钥，也不需要还原指令集。

若确实要改 VM 字节码（只有公钥，无法重加密）：自造 RSA-2048 密钥对 → 替换 `a1`（128 B，位于加密节区，
可用 L3 补丁能力改写）→ 等长替换内嵌 base64 字符串 → 用私钥重加密（245 B 分块 + PKCS#1 v1.5）→ 原地
覆写等大小资源。

## 6. 自定义对称密码（L5）

| 参数 | 值 |
| :--- | :--- |
| 分组 / 密钥 / 模式 / 轮数 | 32-bit / **80-bit** / ECB 无填充 / **12** |

```text
轮函数（S 为 256 字节 S-box，由 FieldRva 初始化）：
    hi = v >> 8;  lo = v & 0xFF
    b5 = S[lo ^ key[(4·sum+0)%10]] ^ hi
    b7 = S[b5 ^ key[(4·sum+1)%10]] ^ lo
    b8 = S[b7 ^ key[(4·sum+2)%10]] ^ b5
    b9 = S[b8 ^ key[(4·sum+3)%10]] ^ b7
    → (b8 << 8) | b9

轮调度：encrypt: delta=+1, sum=0；decrypt: delta=-1, sum=23
级联：SymmetricAlgorithm[5]，每级 10 B 密钥 + 4 B IV（共 70 B），DeriveBytes(pwd, salt, 1)
```

这套密码保护的是**业务数据通道**，不是 VM 容器（VM 流是纯 RSA）。分不清这一点会让人去找一个不存在的
AES 密钥。

## 7. 复现与验证（R1–R5）

| # | 门禁 | 结果 |
| :-- | :--- | :--- |
| R1 | 可复现性 | ✅ 补丁脚本连续多次执行结果一致 |
| R2 | 可观测性 | ✅ 反射探针二值判据：原版 `False` → 补丁版 `True` |
| R3 | 幂等可重入 | ✅ 每次从原版样本重新生成，不叠加 |
| R4 | 可还原性 | ✅ 注册表脚本支持 `-Restore`；样本可由脚本重新生成 |
| R5 | 版本绑定 | ✅ 版本号 + 原始 SHA-256 已固化 |

三档变体（这是让人看懂「哪一处贡献了什么」的关键设计）：

| 变体 | 补丁内容 | `isPro()` |
| :--- | :--- | :---: |
| A（对照） | 仅 4 处 PRO 标记 | `False` |
| B（推荐） | A + 主开关 | **`True`** |
| C（完整） | B + 授权旁路 | `True`（附带第 4.2 节的副作用） |

补丁工具的三条纪律：**永远从原版样本重新生成**（天然幂等，不叠加）；**写之前逐点校验原始字节**（偏移错了
就当场失败，而不是把节区写坏）；**同时给出反向脚本**。

## 8. 加固建议

| 层级 | 措施 |
| :--- | :--- |
| 架构 | 确立「服务端权威」：客户端只持有并呈递凭据；核心权益资源由服务端加密下发 |
| 鉴权逻辑 | 全面 **Fail-Closed**：凭据缺失 / 为空 / 非法一律判定失败 |
| 凭据形态 | 非对称签名凭据（Ed25519 / RSA-PSS），绑定硬件指纹 + 有效期 + 可吊销 |
| 传输层 | 全链路 HTTPS + 证书绑定；移除裸 IP；Nonce + 时戳 + 请求签名防重放 |
| 密钥管理 | 移除随包分发密钥，改会话协商临时密钥（ECDH）+ 服务端签名 |
| 本地状态 | 本地配置仅作「用户偏好」，**不得作为权益判据** |
| 运行时 | 现有反篡改机制应「解不开即拒绝运行」，而非静默降级 |

## 9. 限制与未验证项

- `[observed]` 六层保护的实际表现与还原结果、四处 PRO 标记、8 处调用点、Fail-Open 分支语义、71 个注册表
  键、明文授权端点、2,948 块 RSA 校验、位置流解密的熵与串数变化、三档变体的谓词取值。
- `[inferred]` 「业务数据通道」与「VM 容器」的密码归属，由两条链路的常量不相交推出，未逐条业务接口验证。
- `[unverified]` VM 指令集的完整语义（只识别了 3 个高频 token）；公钥替换路径未实际执行到「改写字节码
  后运行通过」；不同 Eazfuscator 版本下第 2 层 seedArg 是否仍是魔数偏移——若版本不同需重新推导。
- 未评估：反调试层在带 EDR 的终端上的实际表现；服务端是否对同一凭据做设备数限制。
- 已脱敏：真实产品名与厂商域名（改 `<AUTH-ENDPOINT>` / `<API-HOST>` / `<VENDOR-KEY>` / `<IMPORT-VENDOR>`）、
  样本哈希（`<实测哈希>`）。保留：节区魔数、种子、反馈常数、seedArg、编码置换、4 字节 token、分组/密钥/
  轮数等结构常量——它们是可复现性的一部分，不是样本字节。
