# 项目H —— 离线授权码与现代签名的可替换公钥（逆向全链路）

> 案例类型：x64 · Qt 6 桌面程序 · Ed25519 离线激活（CWE-602 / 密钥处理）
> 脱敏：产品名、官方公钥、密钥对、设备码实测值与样本哈希均已移除；保留 RVA、文件偏移、字节序列、算法结构与判据。

本案例是"看起来最安全"的那一类：签名是真签名（Ed25519），验证是真验证（CryptoPP），
载荷还做了 gzip 压缩和一次异或遮蔽。但它仍然可以被完整旁路，原因不在密码学，而在**密钥的存放方式**：
验证公钥被当成秘密，加密后内嵌进程序，而程序必须在运行时把它解出来。
于是问题从"伪造签名"变成"换掉公钥"，后者是数据编辑，不是密码分析。

## 一、样本概况

| 项 | 值 |
| :--- | :--- |
| 分发包 | `项目H-<目标版本>-x64.zip` |
| 主程序 | `项目H.exe`（x64，Qt 6.2.4，MSVC，**无壳、无签名**） |
| MD5 | `<实测哈希>`（与官方安装版同字节） |
| 授权子系统 | 内置，CryptoPP Ed25519 + Qt |
| 激活形态 | 离线激活码（粘贴式）+ 在线激活（共用同一条解析/验签链） |

"无壳、无签名"意味着不需要脱壳，也不需要处理运行时完整性校验 —— 公钥可以直接在文件里改。
如果这里有壳或自校验，本案例的公钥替换步骤要改走运行期内存改写。

## 二、静态定位：字符串交叉引用是最可靠的锚

在一个 Qt 程序里找授权逻辑，猜函数名几乎必然失败（符号被剥、名称被内联）。
但 Qt 的 moc 字符串、API 路径字符串、控件对象名都是天然的锚点，且它们只出现在相关路径上。

```
"pi/activation"             → 网络 API（RVA 0x140242e90 / 0x140243a80 / 0x140243eb0）
"requestOfflineActivation"  → 解锁对话的 UI 逻辑（FUN_1401b3930）
"pty_offlineLicenseCode"    → 离线激活页的控件名
".?AV项目H@@"               → RTTI 类型名，确认类边界
```

由这些引用点向内读，得到关键函数链（RVA，基址 `0x140000000`，`[observed]`）：

| 函数 | 作用 |
| :--- | :--- |
| `14024c9c0` | 格式校验入口：`code[2]=='-'`、校验字符、base64 解码 |
| `14024f160` | 主处理：postProcess + JSON 解析 + 应用 entitlements |
| `14024ab20` | postProcess：异或 → gunzip → 异或，并重拼签名头 |
| `14024e6d0` / `14024b900` / `14024b1d0` | 验签包装 → CryptoPP `ed25519Verifier` |
| `14024b630` | 真正的验签调用 |
| `140249fa0` | 恢复官方公钥（内嵌 58 字节密文，**替换目标**） |
| `140245880` | 状态检查：plan / 域 / 机器码 / 有效期，写出错误码 |
| `140245b50` / `140288f90` | 现算期望设备码（blake2s） |
| `14026db40` / `14026dc80` | 字段 encode / decode（旋转 + 异或） |
| `140275930` | 反调试（调试器检测）——被调试时改变异或路径 |

这张表本身就是方法论产物：**先按字符串找到少量函数，再按调用关系向内收**，
比在 27 MB 级别的反汇编输出里搜索快一个数量级，而且每一步都有字符串作证，不需要"感觉像"。

## 三、动态验证：Qt 容器的坑

Qt 6 的容器内存布局是这条链上最大的时间黑洞。`QByteArray` / `QString` **不是裸指针**：

```
QByteArray*: +0 = d (QArrayData*)  +8 = data 指针  +16 = size  (+24 = alloc)
              → 取数据要从 +8 读指针，而不是 d+16
QString 同理（内容为 UTF-16）
```

踩错的典型症状是"读到的字节看起来像垃圾但长度合理"，于是误判成"还没解压"或"密钥不对"。
先把读取辅助函数写对，再开始探针。

本次探针与结论（`[observed]`）：

| 探针 | 结论 |
| :--- | :--- |
| hook `249FA0` onLeave | 运行时解出的官方公钥（32 字节）与内嵌密文可互相验证 |
| hook `250020` / `24b630` | **验签消息 = gzip 解压后的 JSON 明文** |
| hook `245b50` / `288d10` / `288c00` | 期望设备码为 15 字符，形如 `XXXX-XXXXXXXX` + 校验字符 + 设备数 |
| hook `26db40` / `26dc80` | encode / decode 互逆；JSON 里 machineid 填明文即可 |
| spawn 全程 hook IO | 启动时**不加载**任何已存激活状态（离线激活无持久化路径） |
| 强制 `245880` 返回 0 | UI 立即显示"专业版已激活"——主程序完全信任该返回值 |

第三行值得展开：设备码的格式是**定长**的。`(len - dash - 2) / 2 = 6` 恒成立，
所以生成端不需要预先知道最终长度就能算出各段 —— 这一点让"按本机 MachineGuid 生成可用码"
变成纯算术问题，而不是搜索问题。

第五行是这类审计里最容易被忽略的一条：**离线激活不落盘**。成功状态只在内存里，
重启回到免费版。这不是"补丁没做对"，而是产品本身的实现。它必须写进交付结论，
否则读者会以为拿到了一个持久化的东西。

## 四、四个突破点

### 4.1 公钥可整体替换

官方公钥是 32 字节，以 58 字节密文内嵌在 `FUN_140249fa0` 里（15 个立即数 `mov`），
运行时由 `FUN_24fe70` / `FUN_24f920` 解密还原。密文构造是**已知明文 + 密文即可推导密钥流**的
重复异或（周期 16 字节），因此任意新公钥都能加密回去：

```
stream    = 内嵌密文 XOR 官方公钥      # 33 字节
stream[0:16] == stream[16:32]          # 周期自证
新密文     = 新公钥 XOR stream[0:32] + stream[32]
```

回写到 9 处文件偏移（`0x2493C8` … `0x249400`；前 8 个完整 dword + 第 9 个 dword 的首字节，
其余字节保持原样）。替换后运行时解出的就是我们的公钥，于是我们用自己的私钥签发的载荷自然通过验证。

这里是本案例的核心判断：**"加密公钥"不是安全措施**。公钥本来就是公开的；
把它加密只增加了一道程序必须自己解开的步骤，而这道步骤的明文与密文都在同一份文件里。

### 4.2 验签消息就是明文 JSON

postProcess 的 A/C 两次异或与验签前的一次异或完全抵消，消息等于签名时的 JSON 字节。
因此不存在"先算摘要再签"的结构，也不需要处理任何规范化问题 ——
这既是审计的便利，也是设计缺陷：签名没有域分隔、没有版本前缀、没有长度绑定，
同一个密钥签出的任意 JSON 在语义上都可以被重放。

### 4.3 机器码自洽

期望设备码由 `blake2s(digest_size=16)` 取后 6 字节转大写 hex（12 字符）构造，
再加一个由相邻 ASCII 差和得到的校验字符和一个设备数字符，共 15 字符。
因为格式定长且自洽，生成端只要复现哈希与校验字符即可，不需要探测客户端的长度假设。

### 4.4 主程序信任状态检查的返回值

即使载荷字段全空，只要 `FUN_245880` 返回 0，UI 就显示已激活。这构成了第二条独立通路
（强制错误码为 0），也是"客户端裁决"这一根因的直接体现 —— 只不过本例的主要通路是密钥替换，
这条留作备选。

## 五、端到端验收

```
1. 生成 patched 项目H.exe（公钥换成本地密钥对）
2. 按本机 MachineGuid 生成激活码
3. GUI：输入激活码 → 离线激活 → 粘贴
4. 界面显示「专业版已激活」「个人版（1 设备）」        [observed]
5. 运行期复核：进程内解出的公钥 == 本地公钥             [observed]
```

第 5 步是整个验收里最硬的一条证据。它不依赖 UI 文案、不依赖日志措辞，
只比较内存里的 32 字节与文件里的 32 字节 —— 若相等，说明补丁确实改变了验证依据。

第 4 步的 UI 文案本身也可能撒谎（后续状态检查可能另有一套逻辑），所以两步必须都做。

## 六、限制与未验证项

| 项 | 状态 |
| :--- | :--- |
| 离线激活的状态持久化 | `[observed]` 不落盘；全量 IO hook 未观察到配置文件/注册表写入，重启回到免费版 |
| 可选 `--persist` 补丁的稳定性 | `[observed]` 部分环境对话框行为偶有回退，故默认不启用 |
| 在线激活响应是否可同法伪造 | `[inferred]` 与离线共用同一条验签链，理论上可；服务端流程（邮箱 + 序列号）未纳入 |
| 反调试分支在无调试器下的确定性 | `[observed]` 无调试器复现稳定；带调试器时异或路径改变，结果不可比 |
| 其他小版本上的偏移一致性 | `[unverified]` 仅本版本实测 |
| 公钥替换后官方在线激活的兼容性 | `[unverified]` 未测（换钥后官方签发的码必然失效，属预期） |

第四行是一条方法纪律而不是技术细节：**带调试器跑出来的失败，不能作为"补丁无效"的证据**。
反调试检测会改变控制流，于是同一个载荷在两种环境下得到两种结论 —— 这时先去掉调试器，再下判断。

## 七、方法论沉淀

1. **字符串交叉引用 > 猜函数名**：moc 字符串、控件对象名、API 路径是天然锚点。
2. **先确认 Qt 容器布局再探针**：`QByteArray` 的 data 指针在 `+8`，读错偏移会浪费数小时。
3. **反调试会改变控制流**：结论必须在无调试器环境下复现。
4. **持久化补丁要用"逐项保留"验证因果**：只改一个出口时启动是否还存活、全量改动是否引入对话回退，
   两者都要单独观察，否则无法区分"改动有效"与"改动恰好没破坏别的路径"。
5. **把"不落盘"当结论而不是缺陷**：它界定交付物的实际效果。
