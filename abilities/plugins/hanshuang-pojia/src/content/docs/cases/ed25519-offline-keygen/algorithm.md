# 项目H —— 授权算法原理：激活码结构、设备码与公钥替换

> 目标函数：桌面版内置的授权子系统（RVA 约 `0x140240000`）；离线激活与在线激活共用同一条解析/验签链。
> 脱敏：官方公钥、密钥对、设备码实测值与样本哈希均已移除；公式、偏移与字节序列保留。

---

## 一、常量表

| 常量 | 值 / 形态 |
| :--- | :--- |
| 字符集 | 标准 base64（激活码主体） |
| 签名算法 | Ed25519（CryptoPP `ed25519Verifier`） |
| 签名长度 `SIG_LEN` | 64 |
| 载荷压缩 | gzip，`wbits=31`（Python 与 Qt 双端可解析） |
| 机器码哈希 | `blake2s(digest_size=16)`，输入为「产品名」+「版本位」+ MachineGuid |
| 官方公钥 | 32 字节原始格式；**值已移除** |
| 公钥存放 | 58 字节密文内嵌，15 个立即数 `mov`，运行时解密 |
| 公钥变换 | 重复异或，周期 16 字节 |

`wbits=31` 这一项看着琐碎，其实是双端互通的关键：Qt 的 gzip 读取器与 Python 的 `zlib`
在窗口位参数上并不等价，写成 `31` 才能让两边对同一份字节给出同一结果。迁移或重写工具时，
这一处最容易埋雷。

## 二、设备码（`hwi.machineid`）

客户端在**每次**校验时重新现算期望设备码，并与载荷里的 `hwi.machineid` 比较：

```
hex12 = blake2s(产品名, 版本位, MachineGuid)[-6:].hex().upper()   # 12 字符
s     = hex12[0:4] + '-' + hex12[4:12]                            # 形如 XXXX-XXXXXXXX
check = adjacent_char_diff_sum(hex12) 映射为单个字符
期望设备码 = s + check + '1'                                       # 15 字符
```

自洽性检查：15 字符 = 4 + 1（连字符）+ 8 + 1（校验字符）+ 1（设备数），恰好含 12 个 hex 字符，
与 `[-6:]`（6 字节 = 12 hex）一致。**因为格式定长**，生成端无需预知最终长度即可构造，
这使"按本机 MachineGuid 生成可用码"退化为纯算术问题。

载荷里的 `hwi.machineid` 存**明文**即可：客户端解析时用 `encode_field` 编码存储，
校验时用 `decode_field` 还原为明文，两者互逆（密钥字节随输出一起携带）。

### encode / decode（`FUN_26db40` / `FUN_26dc80`）

```
encode:
    rot  = |int8(key) ^ L| % L            # L = 明文长度
    body = rotate_right(明文, rot)
    for i: body[i] ^= (key ^ i) & 0xFF
    输出 = key 字节 + body

decode:
    rot  = |int8(key) ^ (L-1)| % (L-1)    # 注意 mod 是 L-1
    for i: body[i] ^= (key ^ i) & 0xFF
    body = rotate_left(body, rot)          # 与 encode 的右旋配对
    输出 = body
```

两处细节必须对齐，否则"看起来能读但内容错位"：`encode` 的模是 `L`，`decode` 的模是 `L-1`
（因为 `key` 字节已被剥离），旋转方向相反。迁移实现时，用一组自造向量做往返测试是最省时的
验证方式。

## 三、激活码结构

```
code = v + check + '-' + base64(payload)

v       : 版本字符（官方离线码为数字；生成端可固定为任一字符）
check   : 由 `code[3:]` 的相邻 ASCII 差和映射得到的单字符
payload : sig(64) || body
          body = gzip(json) XOR sig        # 先生成 gzip，再按 64 字节周期异或签名
```

关键点是"先压缩后异或"：如果顺序反过来，客户端解压会失败并原样透传，最终表现为验签失败 ——
一个看起来像"密钥不对"、实际是"顺序不对"的错误。

---

## 四、客户端校验链

```
1. 入口 FUN_14024c9c0：len > 3 且 code[2]=='-'；核对 code[1]；base64 解码 payload
2. postProcess FUN_14024ab20（仅当 len(payload) >= 65，否则原样失败）：
     body = payload[64:]
     A: body ^= sig
     B: body  = gunzip(body)         # 失败 → 原样透传（必然失败）
     C: body ^= sig
     输出 = sig || body（重新拼回签名头）
3. 验签 FUN_14024b1d0 / FUN_14024b630（CryptoPP ed25519Verifier）：
     sig'  = left(64)
     msg   = mid(64)
     （无调试器时）msg ^= sig'        # 反调试：FUN_275930 = 调试器检测
     verify(pub, msg, sig')
4. 成功后返回 msg（= JSON 明文）→ 上层 JSON 解析 → entitlement 对象
5. 状态检查 FUN_140245880：
     - plan 合法
     - 域（工作组）可选；非空时须匹配本机工作组或其短哈希
     - hwi.machineid == 现算期望设备码
     - 生效时间 + 有效期 > now 且 到期时间 > now；过期/未生效给不同错误码
   err == 0 时主程序认为已激活
```

第 3 步的算术值得单独强调：`A` 与 `C` 相互抵消，验签前的那次异或再抵消一次，
所以**真正的验签消息等于 gzip 解压后的 JSON 明文**。这解释了为什么构造载荷时只需要
"签一段 JSON"，而不需要处理任何摘要或规范化。

同时这也是一个应当写进报告的设计缺陷：签名没有域分隔字符串、没有版本前缀、没有长度绑定，
同一个密钥签出的任意 JSON 在语义上都可以被重放。

## 五、公钥替换（补丁原理）

官方公钥以密文内嵌，密文主体 33 字节 = 公钥 32 字节 + `0x00` 终止符。
运行时等价于 `密文 XOR 密钥流`，密钥流周期 16 字节：

```
KEYS   = 内嵌密文 XOR 官方公钥          # 33 字节；KEYS[0:16] == KEYS[16:32]
新密文 = 新公钥 XOR KEYS[0:32] + KEYS[32]
```

回写到 `FUN_140249fa0` 的 **9 个文件偏移**（`0x2493C8` … `0x249400`，前 8 个完整 dword +
第 9 个 dword 的首字节；第 9 个的其余字节保持原样）。补丁后运行时解出的公钥即我们的公钥，
于是我们持有对应私钥可以签发合法载荷。

三个必须做的自检：

1. `KEYS[0:16] == KEYS[16:32]` —— 周期自证；不等说明明文取错了。
2. 用官方公钥反向加密必须**逐字节复现**原始 58 字节密文 —— 这是唯一能排除"周期对齐偏差"的检验。
3. 补丁后从进程内存读回解出的公钥，与我们的公钥 32 字节比对 —— 这是唯一能证明补丁生效的检验。

第 2 条最容易被省略，也最容易在错位一字节的情况下产生"能跑但偶发失败"的结果。

### 可选持久化补丁

`FUN_140245880` 的 4 个失败出口（RVA `0x245a14` / `0x245ada` / `0x245b12` / `0x245b22`，
指令形如 `C7 07 imm32`）把立即数改为 `0x00000000`，使状态检查恒成功（启动即已激活）。

注意：这条与公钥替换是**两条独立通路**，且稳定性较差 —— 部分环境实测中对话框行为偶有回退。
默认不启用；启用时仍应配合公钥替换，否则"状态检查通过但载荷未验签"会在别的路径上暴露。

## 六、弱点总结

| 弱点 | 说明 |
| :--- | :--- |
| 无服务器签名、无吊销 | 只有 Ed25519 自签名，公钥内嵌可整体替换 |
| 公钥"保护"可逆 | 密钥流由密文与已知明文直接推导，无任何密钥材料参与 |
| 签名消息 = 明文 JSON | 无域分隔、无摘要加固，语义上可重放 |
| 设备绑定偏弱 | 机器码由稳定系统值的哈希派生，且格式定长可构造 |
| 反调试影响可复现性 | 只要无调试器，异或路径确定；但这意味着"带调试器的失败"不能作为结论 |
| 离线状态不落盘 | 效果仅限当前进程；重启回退到免费层 |

最后一行不是漏洞，但它决定了这类交付的实际价值，必须写进结论而不是备注。

## 七、参考实现的分层

| 层 | 职责 |
| :--- | :--- |
| `algo` | 上表中的公式直接实现，附自检向量（公钥还原、设备码、编解码回路、激活码验签、补丁往返） |
| `cli` | 子命令：`gen` / `patch` / `verify` / `selftest` |
| `gui` | 单窗口界面，不做任何算法实现，只调用 `algo` |
| `tests` | 9 项自检，与 `algo` 的自检向量同源 |

分层本身是可迁移的经验：算法层必须能在无 UI、无文件系统副作用的前提下跑自检，
否则"生成出来的码客户端不认"这类问题会一直停留在手工试错阶段。

## 八、限制与未验证项

| 项 | 状态 |
| :--- | :--- |
| 官方在线激活的完整服务端流程 | `[unverified]` 未抓包；仅确认与离线共用验签链 |

| 设备码公式在其他版本上的输入拼接 | `[inferred]` 从本版本探针推断为「产品名 + 版本位 + MachineGuid」，未逐版本比对 |
| 反调试分支之外是否还有其他路径改变验签输入 | `[unverified]` 仅在当前构建上做了全量 hook |
| 公钥密文是否还存在第二处副本 | `[unverified]` 本次只在 `FUN_140249fa0` 内定位到 9 处偏移 |
