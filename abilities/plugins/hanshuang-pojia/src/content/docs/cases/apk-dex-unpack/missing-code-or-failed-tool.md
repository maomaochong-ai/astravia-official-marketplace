# APK 取不到源码：分清「工具失败」与「代码不在文件里」

> 案例类型：Android 包结构与运行期 DEX 恢复／目标：一个反编译只得到骨架的 APK／脱敏：包名与端点以占位符出现，样本哈希写为 `<实测哈希>`，偏移写为 `<实测偏移>`。

---

## 一、现场

第一次反编译的产物是可疑的：`sources/` 里有包前缀对应的目录结构，但目录里几乎只有一两个类的空壳；`AndroidManifest.xml` 里 `application` 的 `android:name` 指向一个包内不存在的类；资源文件齐全，界面布局都在，业务字符串在 `resources.arsc` 里能搜到，可是没有任何一处引用它们。

这时候有两种完全不同的解释，而它们要求完全不同的下一步：

- **工具失败**：反编译器的版本不认识这个 DEX 版本，或者它在中途抛了异常只写了一半。
- **代码不在文件里**：`classes*.dex` 本身只有壳，真正的类在运行时从 `assets/`、`lib/<abi>/` 或服务端解密到内存。

把这两者混为一谈的代价是：在「工具失败」的情况下跑动态脱壳，什么也拿不到；在「代码不在文件里」的情况下反复换反编译器，换十次结果一样。

现场的第二个观察是体积分布：`lib/arm64-v8a/` 下有一个 `.so` 比正常业务库大一个数量级，`assets/` 里有几个名字无语义的大文件，而 `classes.dex` 只有几十 KB。这个比例关系（代码很小、载荷很大）是「代码被搬走了」的直接迹象。

第三个观察来自清单：`application` 的类名、`android:appComponentFactory`、或者一个 `ProxyApplication` 形状的引用，指向的类在 DEX 里查不到。壳必须能被系统调用起来，所以它一定在 DEX 里留了一个入口；但入口后面的东西不在。

## 二、判定

判据是三条信号里的两条。只有一条时不够，因为三条各自都有正常解释。

| 信号 | 观察方式 | 正常解释（反证方向） |
| --- | --- | --- |
| 包前缀下方法数极少 | 逐 DEX 统计 class/method 表 | 应用确实只做很少的事；代码在动态特性模块里 |
| 清单里的入口类不在 DEX | 清单字符串 + 类表交叉 | 类是壳注入的，由 `AppComponentFactory` 在装载期替换 |
| 载荷体积远大于代码 | `assets/`、`lib/<abi>/` 与 DEX 大小比 | 资源包（视频、模型、字体）本来就会很大 |

工具把这三条加上壳的特征名一起评分（`thin-dex` 45、`loader-name` 40、`native-payload` 15、`big-blob` 10），分档沿用同一套口径：≥55 `packed`，25–54 `suspicious`，否则 `thin but unexplained`。第三档是刻意留的：它表示「代码确实少，但不足以说是壳」，这时候的下一步是看有没有动态特性模块，而不是去脱壳。

第二层判定是「转储出来的东西是不是代码」。DEX 头有四个必须同时成立的字段：

| 字段 | 期望值 | 为什么不能只看 magic |
| --- | --- | --- |
| `magic` | `dex\n035` 到 `dex\n039` | 字符串常量可以完整拼出这 8 字节 |
| `header_size` | `0x70` | 固定值，随机数据也能碰上 |
| `endian_tag` | `0x12345678` | 同上 |
| `file_size` | 与文件实际长度接近 | 这一条最难被常量对上 |

四条同时成立才算一个可用的转储；只成立 magic 的文件几乎一定是某个字符串常量恰好拼出了头。这一点在最开始就该写进判据，否则后面的分析全部建立在假文件上。

## 三、取证

```bash
cd tools
python3 dex_pack_triage.py --self-test
python3 dex_pack_triage.py --sample app.apk
python3 dex_pack_triage.py --sample app.apk --dump exports/frida-dump/
```

自检给出的两行（`kit self test: 44/44`、`dex_pack_triage self test: 9/9`）里，第二行覆盖了合成包对照：一个只有薄 DEX 的包应判 `packed`，一个带壳特征名但没有载荷的包应判 `suspicious`，一个体积正常的包应判 `thin but unexplained`。三个分档都被断言过，工具才有资格对真样本给分。

正式跑要保留四张表：

| 表 | 列 | 用途 |
| --- | --- | --- |
| dex units | dex、字节数、类数、方法数、字符串数、版本、结构问题 | 「代码有多少」的底账 |
| signals | 信号、权重、证据行 | 分档依据 |
| native / blobs | 条目、字节、熵 | 「载荷在哪」 |
| loader strings | dex、字符串 | 「是哪个壳」 |

`--dump` 那一步是第二种用途：它不信任任何「脱壳成功」的宣称，只校验头。合格的文件列出 `magic / header_size / endian_tag / file_size` 四项判定；不合格的文件直接让进程以非零码退出——这是刻意的，一个「看起来成功」的退出码会让下一个人跳过校验。

转储本身由 `frida_dump` 完成，本工具只回答两件事：值不值得转储、转出来的东西是不是代码。

动态取证的三个操作细节必须记进证据，否则不可复现：

1. **spawn 而不是 attach。** 首次启动才发生的解密，attach 会错过。
2. **停留在会触发目标代码的界面。** 惰性解密按类进行，停在首页只能拿到首页的类。
3. **等待时间与重复次数。** 一次转储看起来还是骨架，就把等待时间翻倍、保持界面不变再跑一次；记录两次的类数差异，这个差异本身是「惰性解密」的证据。

## 四、否证

**否证一：薄是因为应用本来就小。** 一个只做单一功能的应用可以只有几十个类。反证是看资源与清单：如果布局里出现大量业务界面，而代码里没有任何对应逻辑，那就不是「本来就小」。

**否证二：代码在动态特性模块里。** 使用按需下发模块的应用，主 DEX 天然很薄，业务类在安装后从应用商店下发。判据是 `AndroidManifest.xml` 里的 `dist:` 命名空间、`com.android.dynamic-feature` 声明，或 `split` 相关元数据。这一条成立时，动态路线是错的，正确做法是分析已下发的 split APK。

**否证三：壳的特征名是诱饵或历史遗留。** 空壳 SDK 常常把多个加固厂商的类名一起打进包里做兼容。反证是看调用关系：特征名对应的类有没有被 `System.loadLibrary` 或 `attachBaseContext` 实际引用。没有被引用的名字只是字符串。

**否证四：DEX 头校验通过但内容不对。** 一个合法的、空的 DEX（只有头和一个空字符串池）也能通过四项检查。所以要额外看类数与方法数：数量为 0 或个位数，说明这个文件是骨架，不是恢复结果。

**否证五：你在分析一个空壳安装包。** 有些分发渠道给的包需要首次启动时下载主体。这种情况下清单、DEX、资源都齐全，但业务类确实不在——判据是启动日志里出现下载器的记录，或者包内存在明显的分片清单。

## 五、复现

**步骤一：底账。** 记录 APK 的 SHA-256（`<实测哈希>`）、`classes*.dex` 的份数与各自哈希、`lib/` 下每个 `.so` 的大小与哈希。

**步骤二：判定。** 用第二节的三条信号，写一句结论：「两条以上成立，判 packed」或「一条成立，先排除动态特性模块」。

**步骤三：转储。** 记录脚本版本、spawn/attach、等待时间、停留界面、设备 API 级别。转储目录里的每个文件都要单独过一遍头校验，记录「合格 / 不合格 + 原因」。

**步骤四：对照。** 转储前后同一组指标的变化：

| 指标 | 转储前 | 转储后 |
| --- | --- | --- |
| DEX 份数 | 1–2 | 视解密规模 |
| 类数合计 | 数十 | 数百至数千 |
| 业务字符串命中 | 0 | 出现具体业务词汇 |
| 方法体可反编译比例 | 极低 | 应显著上升 |

**步骤五：回滚与边界。** 设备上不改动已安装的包（不重打包、不置换签名），转储只发生在进程内存里；分析结束后卸载重装即可回到初始状态。这一点要写进报告，因为它决定了结论是不是「对线上包的观察」。

## 六、边界与遗留

- 结论来自转储，不是来自已安装的包；报告必须写出这句话，否则读者会以为安装包本身被修改过。
- 如果载荷被虚拟化（类方法体是解释器字节码），停在「恢复出 DEX」这一步，写清未获得执行语义。
- 没有覆盖的：按需下发的动态特性、服务端在登录后才下发的代码、以及只在特定 ABI 上启用的壳。
- 工具不执行 APK、不联网；它的「验证」只针对文件头，不针对行为。
