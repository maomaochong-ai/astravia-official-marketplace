# 壳与多 dex：为什么「扫到 dex magic」等于没扫

加固包的 apk 里通常仍有 `classes.dex`，但它只有几百 KB、方法数是骨架量级，真实业务代码在运行期解密后 `mmap` 进内存。很多人第一步做的是「在文件里搜 `dex\n035`」，搜到就宣布「dex 在，可以静态分析」。这一步错了，因为**搜到的是壳自己**。

## 文件里的 dex 与内存里的 dex 是两件事

磁盘上的 `classes*.dex` 有三种可能：

- **完整**：未加固，可直接读。
- **壳**：真实 dex 不在文件里，只有加载器。
- **混合**：一部分类被抽走（类抽取型加固），dex 结构完整但 `code_item` 被掏空。

区分它们不需要脱壳，只需要三个廉价信号：方法数、字符串池里是否有业务词、以及 `code_item` 是否普遍为空。骨架 dex 的方法数往往在几百到一千量级，而一个真实应用常在一万以上；字符串池里如果没有业务词（订单、支付、账户名），那它就不是业务 dex。

## 运行期 dump 的判据是头部，不是魔法

内存扫描最容易犯的错是只比对前四个字节 `dex\n`。字符串常量里出现 `dex\n035` 是常见的（尤其混淆器自己会留这种字符串），于是 dump 出一堆假 dex，后面的反编译全部失败，浪费一天。

可靠判据要四条同时成立：

1. `magic` 是 `dex\n0{35..39}\x00`；
2. `header_size == 0x70`；
3. `endian_tag == 0x12345678`；
4. `file_size` 落在合理区间（大于几 KB、小于映像大小）。

四条都过，才把它写成文件；再对写出的文件跑一次同样的校验，因为 dump 时边界可能截断。`dex_pack_triage.py` 就是这套判据的实现：它不执行目标，只读 zip 条目与 dex 头部，输出每个 dex 的方法数、字符串数、是否骨架、以及问题清单（头部尺寸、endian、file_size 与实际长度是否一致）。

## 类抽取型：结构对，代码空

这一类最容易被误判成「脱壳成功」。dex 完整、方法表齐全，但 `code_item` 的 `insns_size` 全是 0，或者指向一个统一的 `nop` 桩。用 jadx 打开会看到大量方法体是 `throw new RuntimeException("Stub!")` 或直接 `return null`。

判据是**方法体密度**：抽样若干业务类，统计 `code_item` 非空比例。低于 10% 基本可以判定为抽取型，此时静态阅读没有意义，必须走运行期 dump 或主动调用（让壳把类还原到内存后再 dump）。

## dump 之后必须做的事

1. **校验**：对每个 dump 文件重跑四判据，记录 sha256 与大小。
2. **归并**：同一个 dex 常被映射两次（dexopt 之后），按 sha256 去重。
3. **重打包分析**：把 dump 出的 dex 交给反编译器，而不是直接读 smali。多 dex 的类分布与原 apk 不同，索引会错位。
4. **标注边界**：dump 是快照，可能只覆盖已加载的类。报告里要写「触发到哪个界面」，否则下一人无法复现覆盖范围。

## 触发时机决定覆盖率

壳是惰性的：类在第一次使用时才解密。所以 dump 时机比 dump 工具重要得多。

- 只启动到首页 → 通常拿到首页与网络层；
- 进入登录、支付、会员页 → 才会解密对应的业务类；
- 对某些壳，需要让目标「跑满」一轮（列表 → 详情 → 下单）才能覆盖全部模块。

实践上有效的方法是**分阶段 dump 并对差**：首页 dump 一次、关键页 dump 一次，两次的文件集合做差，新增的那些就是该页引入的类。差集比全集小得多，也更容易定位。

## 常见误判

- **「dump 出 20 个 dex」**：大部分是重复映射，去重后可能只有 5 个。
- **「字符串里有业务词」**：字符串池是共享的，一个词可能来自任何 dex，不能据此判定归属。
- **「jadx 打开了就成功」**：能打开 ≠ 能反编译出方法体，类抽取型正是「能打开」。
- **「脱壳完成」**：只 dump 了首页，业务模块没覆盖。
- **「补环境跑通了」**：能跑通的是桩，不是真实逻辑。

## 报告要写什么

一份可用的脱壳报告包含：原包指纹、每个 dump 文件的 sha256 与四判据结果、触发路径（点了哪些页面）、去重后的 dex 数量、类抽取判定（方法体密度）、以及**没覆盖的部分**。最后一项最常被省略，也是下一人最需要的信息。
