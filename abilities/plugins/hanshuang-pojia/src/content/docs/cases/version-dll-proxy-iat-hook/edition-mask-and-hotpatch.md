# 版本号掩码、离线鉴权链与三处热补丁（项目C，7.46 / 71822）

> 案例类型：Windows x64 签名商业软件 · 离线对称鉴权（CWE-602） · DLL 搜索序劫持 + 微创热补丁
> 脱敏：产品名、端点、样本哈希与内部署名已移除；RVA、密文结构、掩码公式、补丁字节表完整保留。

这个案例的特点是"看起来很难，实际很薄"：授权链上有硬件指纹、对称加密、六项密文、
多层校验，但最终决定用户拿到什么版本的，是 `+0x120` 这个字段里的**一个被位重排过的整数**。
理解这一点之后，整个工作就收敛到三处 10 字节的完整指令。

## 一、目标画像

| 维度 | 判定 |
| :--- | :--- |
| 平台 | Windows x64（PE32+），单进程 GUI |
| 版本 | 7.46 / Build 71822（`VersionNo.ini` 记 `BuildNo=71822`） |
| 镜像 | ImageBase `0x140000000`，映像 `0x361000`，文件 `0x353570` |
| 签名 | 带 Authenticode，全程未改动 |
| 授权模型 | 离线对称：硬件指纹派生会话密钥，Blowfish 解出注册凭据，本地判定 |
| 硬依赖 | `data\lm.x64.dll`（缺失即 `ExitProcess`） |

最后一行是任何方案的前置条件：这个模块加载失败会弹出
`Error: Failed to load lm.dll. Code: %u` 并直接退出进程，
所以"改搜索路径""重命名目录内文件"这类操作会先把程序弄死，再谈补丁。

## 三、离线鉴权链

`sub_1400D0690` 读 `HKLM\SOFTWARE\<应用>\l`：

1. `g`（16 字节十六进制）→ 用硬件指纹派生的密钥解密 → **会话密钥**；
2. `l / k / h / P / m / t` → 用会话密钥解密 → UTF-8 字符串；
3. 判定：六项全部非空，**且 `k == L"20"`**。

`sub_1400D0370` 在 `HKCU` 侧做一致性检查（`c / r / u`，其中 `u` 是 4 字节硬件指纹）。
成功后 `sub_1400CF980` 回写 `l/k/h/P/m/t/g`。`HKLM\SOFTWARE\<应用>\Edition` 由
`sub_1400CF470` 写入，**只作记录**，不参与判定。

硬件指纹来源（`sub_14002E9D0`）：`\\.\X:` + `IOCTL 0x2D1400`（`SMART_RCV_DRIVE_DATA`）
→ `sub_140022960` 哈希；失败回退 `GetVolumeInformationW`。

内置密码学原语：

| RVA | 函数 | 语义 |
| :--- | :--- | :--- |
| `0x2B6D0` | `sub_14002B6D0` | Blowfish 密钥编排（`P[18]` + `S[4][256]`，常数表 `unk_1402706C0`） |
| `0x2BB40` | `sub_14002BB40` | Blowfish 加密（原地，尾白化 `P[16]`,`P[17]`） |
| `0x2BCD0` | `sub_14002BCD0` | Blowfish 解密（原地，尾白化 `P[0]`,`P[1]`） |
| `0x2D2B0` | `sub_14002D2B0` | `swscanf(L"%02x")` |
| `0xD4B00` / `0xD4BB0` | — | 十六进制串 ↔ 字节（长度须 32/33） |
| `0xD52E0` | — | 编解码主入口：解密 16 字节头 → 校验 `hdr[1]==1 && hdr[2]<=len-16` → 解密载荷 → `MultiByteToWideChar(CP_UTF8)` |
| `0xD0D80` | — | `HKCU` 侧 `c/r/u` 解码 |
| `0xD13A0` | — | 反向编码（加密并写回） |

载荷包（明文）：`0x00` u32 保留；`0x04` u32 = `1`（格式版本，硬校验）；`0x08` u32 载荷长度；
`0x0C` u32 保留；`0x10` UTF-8 载荷。

## 四、掩码：存的值不是版本

```
plain = ((2 * (v & 0xD5555555)) | ((v >> 1) & 0x55555555)) & 0xFFFFFFFF;
```

| 存储值 | 解码值 | 语义 |
| :--- | :--- | :--- |
| `0x98` (152) | `100` | Standard |
| `0x3D4` (980) | `1000` | Professional |
| `0x1B20` (6944) | `10000` | Enterprise |

三组实测校验：`T(152)=0x64`、`T(980)=0x3E8`、`T(6944)=0x2710`，全部吻合。

这一步必须先做对，再谈补丁。因为"把立即数改成 `0x1B20`"这个动作，
只有在你能正反双向验证掩码时才有意义；否则改了以后解码出谁也不认识的值，
表现是"某个功能静默失效"，而不是报错。

解码后的分发：

| 消费点 | 判据 | 效果 |
| :--- | :--- | :--- |
| `sub_1401320C0` | `== 0x2710` | 企业版功能 |
| `sub_14015FB90` | `== 100` | 标准版的注册提醒可见性 |
| `sub_1400CF470` | — | 写 `Edition` 字符串 |

## 五、三处热补丁（`sub_1401316C0`）

三处都是**完整的 10 字节指令**，同形：

| RVA | 原始字节 | 语义 |
| :--- | :--- | :--- |
| `0x13176D` | `C7 86 20 01 00 00 D4 03 00 00` | 写 980 → Professional |
| `0x1317CC` | `C7 86 20 01 00 00 20 1B 00 00` | 写 6944 → Enterprise |
| `0x1317F5` | `C7 86 20 01 00 00 98 00 00 00` | 写 152 → Standard |

三套方案：

| 方案 | 站点 | 字节数 | 结果 |
| :--- | :--- | :--- | :--- |
| **A**（Professional） | `0x13175D` `75 36`→`90 90`；`0x13176B` `75 28`→`90 90` | 4 | 恒定落到 `0x13176D` → `1000` |
| **B**（Enterprise） | A，加 `0x131773` `D4 03 00 00`→`20 1B 00 00` | 12 | `10000`（`Edition` 仍记 `PRO`） |
| **C**（放行服务端检查） | `0x1347E0` `4C 8B DC 49 89 5B 08 …`→`31 C0 C3` | 3 | 黑名单查询恒"未拦截" |

A/B 与 C 相互独立。

### 5.1 方案 C 为什么是"恒 false"

`sub_1401347E0` 的实现是：

```c
v27 = sub_1400296F0(url, L"/checkaccesssecureserver", 1, &v33);
return v27 && v33 == 0;
```

只有"请求成功 **且** 服务端判定拒绝"才返回 `true`。调用点 `0x1401339D2`：

```asm
test al, al
jnz  loc_140133AA5      ; 非零 → 走"被拦截"分支
```

所以 **`true` 意味着"被拦截"**。让它恒 `false`，才是"永不拦截"。
把返回值当成功标志读，会写出方向相反的补丁——这类错误在报告里必须写清，
因为它决定了这个补丁是"放行"还是"封禁"。

## 六、运行时落地形态

代理 `version.dll`（201,216 字节）放在程序同级目录，`DllMain(DLL_PROCESS_ATTACH)` 中：

1. 取主模块基址；
2. 同步实施 3/3 热补丁；
3. 启动 Watchdog（+500 ms）轮询确认代码段未被二次篡改。

日志原文形态：

```
[SUCCESS] edition/std->ent (STD 回退分支) @ 0x1317F5 (10 bytes written)
[SUCCESS] edition/pro->ent (PRO 分支)    @ 0x13176D (10 bytes written)
[SUCCESS] license/server_bypass (黑名单)  @ 0x1347E0 (3 bytes written)
=== Patch summary: 3/3 sites succeeded ===
```

"3/3"这种逐站点汇总很重要：它把"部分成功"变成可观测状态。
只报"完成"的日志，遇到 2/3 时无法察觉。

## 七、UI 侧的落地效果

- 主窗标题 `项目C 7` → `项目C 7 Enterprise`；
- 解码值 `== 100`（Standard）时显示注册提醒控件，Enterprise 下自动隐藏；
- 菜单出现「密码恢复」「修复压缩包」等企业版条目。

这三条正好对应第四节的分发表：标题读 `+0x120`，提醒控件读 `== 100`，菜单读企业版分支。
换句话说，**三个消费点同时变化**才证明那个字段被真正改写，
只看一个（比如标题）不足以排除"另外两个读了别的字段"。

## 八、限制与未验证项

| 项 | 状态 |
| :--- | :--- |
| `Edition` 字符串与实际版本不一致的影响 | `[inferred]` 方案 B 不改 `Edition`，若有消费点信任它，会与 UI 冲突 |
| 黑名单接口的实际可达性 | `[unverified]` 未对真实服务发起请求，方案 C 由反编译判定推导 |
| 产品是否在启动后自校验代码段 | `[unverified]` Watchdog 只确认我方写入存活 |
| 掩码是否在其它版本上更换常量 | `[inferred]` 常量 `0xD5555555/0x55555555` 定位该函数，未跨版本验证 |
| 会话密钥派生中硬件指纹的稳定性 | `[observed]` 换盘/换卷会改变结果，未做兼容性评估 |

把"`Edition` 字段可能冲突"写在这里，是因为它是最容易被忽略的不一致：
一个只信 `Edition` 的消费点，会让方案 B 在某些界面里退回 Professional。
这类"局部一致、整体不一致"的状态，比彻底失败更难排查。
