# 从 IAT 重写对话框：五个攻克点与七个坑（项目C）

> 案例类型：Win32 UI 显示层改写 · 跨进程验证工装 · 工程陷阱复盘
> 脱敏：真实署名、邮箱、端点已移除；控件 ID、样式位、行数、日志形态与踩坑序列完整保留。

版本号那一段决定了"能不能用"，这一篇决定"看起来像不像"。
改一个多行编辑框显示三行文本，听起来是十分钟的工作，实际花掉了整个案例一半的时间——
原因全部集中在"我以为我知道控件是什么"。

---

## 一、为什么不去改语言文件

第一反应是改 `langs\*.lang` 里的模板。三条否证：

| 位置 | 为什么不选 |
| :--- | :--- |
| `langs\*.lang` 模板 | 可能被完整性校验发现；且模板要经过 `${str1}` / `${str2}` 替换（`sub_140046020`）才成型 |
| 模板替换函数 inline hook | 参数是 C++ 字符串对象，需要还原其 ABI，代价高且极易 `0xC0000005` |
| **成品宽字符串交给控件的时刻** | **已是纯 C `wchar_t*`，零 ABI 风险** |

选第三个：`SetDlgItemTextW(hDlg, 0x527, lpString)`。
它同时也是最少依赖模板内容的位置——模板将来改了，这里不需要跟着改。

这就是"落笔点"的概念：不是"哪里最重要"，而是"哪里数据已经变成最简形态"。

## 二、五个攻克点

### 2.1 落笔点精准定位而非改资源

见上。判据是"数据形态最简 + 依赖最少"，不是"改动最小"。

### 2.2 控件 ID 与类名必须运行时实测

反编译只说 ID `0x527`（名为 `IDC_STATIC_LICENSE`），名字里的 `STATIC` 让人自然写成
`Static`。实测类是 `Edit`。首版 Hook 里有这么一行：

```c
if (_wcsicmp(cls, L"Static") == 0) { /* rewrite */ }
```

于是 Hook 装上了、被调用了、日志一行不响、界面毫无变化——**静默跳过**。
修复不是"改成 Edit"，而是：

1. 运行时 `GetClassNameW` 取类名并与白名单比对；
2. 未命中分支**必须打日志**。

第二条比第一条重要：任何一个"条件不满足就 return"的分支，都是未来排查时的黑洞。

### 2.3 编译器吞掉 `\r`

字面量里写 `L"第一行\r\n第二行\r\n第三行"`，编译后只剩 `62 00 0A 00`——
`\r` 不见了。多行 `Edit`（`GWL_STYLE = 0x50010804`，`ES_MULTILINE` 已开）只认 CRLF，
于是三行挤成一行。

三条观察把这件事钉死：

| 观察 | 结果 |
| :--- | :--- |
| 代码里的字面量字节 | 只有 `000A`，没有 `000D` |
| 外部 `WM_SETTEXT` 写入 CRLF | 存活，三行正常 |
| `EM_GETLINECOUNT (0x00BA)` | 纯 LF → `1` 行；CRLF → `3` 行 |

解法是双保险：字面量写 `\u000D\u000A`，运行时再过一个 `NormalizeCrlf()`。
验收不是看截图，是 `len == 52` + 两组 `000D 000A` + `EM_GETLINECOUNT == 3`。

### 2.4 跨进程 UI 反向枚举工装

要"读回控件实际内容"，就得从另一个进程去问。工装组成：

```
EnumWindows → GetWindowThreadProcessId（按 PID 过滤）
  → EnumChildWindows
    → GetDlgCtrlID / GetClassNameW / GetWindowLongPtr(GWL_STYLE) / GetWindowRect
    → SendMessageW(WM_GETTEXT) 逐字符打印 UTF-16 码点
    → SendMessageW(EM_GETLINECOUNT)
GetMenu → GetMenuItemID（"关于" = 147）→ PostMessageW(WM_COMMAND, 147, 0)
```

最后一行让"打开关于框"变成自动化动作，不必手点。
整套东西的价值在于：它把"界面对不对"从主观判断变成了可打印的事实。

### 2.5 让用户可调参，免重编译

`version_patch.ini`：

```ini
[license]
ctrl_id=1319
text="第一行\n第二行\n第三行"
```

支持 `\n` / `\r` / `\t` 转义、UTF-8（含 BOM）、引号剥离、`;` / `#` 注释与空行；
读不到 INI 时回退内置默认值，并打一行 `[CFG] version_patch.ini not found -> default license text`。

第三句是关键：**"文件不存在"必须是一等公民**，不是异常。否则用户删了配置就崩，
或者更糟——静默用了半份默认值。

## 三、七个坑（K1–K7）

| 编号 | 坑 | 现象 | 正解 |
| :--- | :--- | :--- | :--- |
| K1 | 控件类名静态假设 | Hook 装上了但什么也没发生 | 运行时 `GetClassNameW` + 白名单 + 未命中打日志 |
| K2 | 编译器吞 `\r` / `\x000D` | 三行文本显示成一行 | `\u000D\u000A` 字面量 |
| K3 | Windows `Edit` 只认 CRLF | 同上 | 运行时 `NormalizeCrlf()` |
| K4 | `vfprintf("%ls")` 遇非 ASCII 截断 | 日志在汉字处断掉，误判"代码没执行" | 非 ASCII 一律按 UTF-16 码点十六进制打印 |
| K5 | DLL 被占用 | 替换文件失败 | 先 `Stop-Process -Force` 再替换 |
| K6 | Program Files 权限不足 | 写入被拒 | 管理员权限运行 |
| K7 | 只靠截图肉眼判断 | “看起来改好了” | 行数 + 控件 ID + 字节 dump |

K4 值得单独说：它是**观测工具本身在骗人**。
日志被截断时，最自然的结论是"我的 Hook 没被调用"，于是去改 Hook——
方向完全错了。观测链路的可靠性必须先于被测对象的可靠性。

## 四、IAT Hook 的实现要点

- 目标是 IAT 项，不是函数体：改 IAT 槽（`user32.dll!SetDlgItemTextW` 对应槽位）
  指向自己的实现，原件地址保留；
- 日志里同时记槽位地址、原值与新值：
  `[IAT] hooked user32.dll!SetDlgItemTextW @ IAT slot ...6C78 (was ...849F80 -> ...7E2A10)`；
- 调用时先判控件 ID（`0x527`），命中才重写，其余原样转发；
- 重写后仍调用原件，让控件走它原本的绘制路径。

"改 IAT 槽而不是改函数体"的收益：不需要解析函数前导、不需要处理热补丁点被占用的情况，
且回滚只需还原一个指针。

## 五、纵深防御建议

| 层级 | 措施 |
| :--- | :--- |
| 加载路径 | `SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_SYSTEM32 \| LOAD_LIBRARY_SEARCH_USER_DIRS)`，或编译期 `/DEPENDENTLOADFLAG:0x800` |
| 调用完整性 | 启动时对自身 IAT 做快照，运行期比对；显示类 API 改用 `LoadLibrary` + `GetProcAddress` 动态取址，不写 IAT |
| 展示层 | 敏感对话框改自绘（Owner-Draw / Direct2D），并把"内存授权状态"与"展示文案"互校，两者不一致即视为异常 |
| 授权模型 | 废止"本地版本号落地值决定特权"，改服务端签发短效 Ed25519 签名票据 + 在线心跳双层校验 |

第三条容易被当成过度设计，但它针对的正是本案例的核心：
**当一个字段同时决定"功能"和"界面上的说明"时，改一个字段就能同时骗过两者。**
把两者拆开并互校，才需要同时攻破两个地方。

## 六、限制与未验证项

| 项 | 状态 |
| :--- | :--- |
| 自绘对话框对 UI 自动化的影响 | `[inferred]` 未实测；理论上 `WM_GETTEXT` 会失效 |
| IAT 完整性快照的开销 | `[unverified]` 未做性能测量 |
| 动态取址是否能被 inline hook 绕过 | `[inferred]` 能，只是提高了成本 |
| 服务端票据方案在离线场景的可用性 | `[inferred]` 需允许有限期离线宽限，未设计细节 |
| `EM_GETLINECOUNT` 在自绘控件上的语义 | `[unverified]` 该消息本就依赖控件实现 |

这份材料的可迁移结论只有一句：**先找数据形态最简的落笔点，再用运行时事实纠正静态假设。**
版本号、控件类名、换行符这三件事，全部都是"静态看起来对、运行时不成立"。
