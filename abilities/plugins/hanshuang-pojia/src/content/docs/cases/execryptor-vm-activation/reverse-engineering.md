# 虚拟化验签下的授权审计：为什么这里不存在算号器

> 目标：一款 x64 商业桌面软件（主程序约 6.4 MB）+ 伴随的授权运行时（约 460 KB）
> 结论：**验签逻辑被代码虚拟化保护，静态不可还原**；可审计面在主程序侧的单一状态判定
> 脱敏：产品名、公司名、授权服务端点、样本哈希、证书主体均已移除

这是一份**否证式**案例。它的价值不在于"打通了"，而在于把一条看似自然的路线
（还原算法 → 写算号器 → 生成任意序列号）明确地排除掉，并给出替代路径与其代价。
在授权审计里，"这里做不到"若能被证明，比"这里也许能做"有用得多。

---

## 一、目标画像

| 维度 | 判定 | 判据 |
| :--- | :--- | :--- |
| 主程序 | PE32+ / x64，原生 C++ | MSVC 19.50.35227（VS2026 工具链），6,451,848 B |
| 运行库 | 静态链接 CRT | 无 MSVCP/VCRUNTIME 导入依赖 |
| 签名 | Authenticode | 证书目录非空，overlay 为签名数据 |
| 加壳 | 无 | DiE 未识别出 packer；overlay 高熵来自签名而非压缩 |
| 伴随进程 | `项目EHelper.exe`，474,720 B | EXECryptor 授权运行时；安装目录内固定存在 |
| 安装形态 | Inno Setup | 附带 `.cpl`、`PinToTaskbar.exe`、`languages\*.xml` |
| 通信 | 共享内存 + 命名事件 | 见第四节 |

第一步就把"加壳"排除了：文件熵高但节区结构完整，overlay 的熵来自签名数据而非压缩流。
这一步很关键——若误判为加壳，接下来几小时会花在脱壳上，而问题根本不在那里。

## 二、用导入表否掉"本地密码学校验"

在 6.4 MB 的 x64 二进制里读代码之前，先看导入表。这是全案成本最低、结论最硬的一步：

| 导入组 | 存在 | 推论 |
| :--- | :--- | :--- |
| `advapi32!Reg*`（`RegOpenKeyExW` / `RegQueryValueExW` / `RegSetValueExW`） | ✅ | 判定结果会落地到注册表 |
| `wininet` / `ws2_32` | ✅ | 有网络交互 |
| `crypt32`（`Cert*` / `CryptGenRandom`） | ✅ | 传输层与随机数 |
| MD5 / SHA / 对称加密原语（`BCrypt*` / `CryptHashData` / `CryptEncrypt`） | **❌** | **主程序本身不具备校验密码学签名的能力** |

最后一行是全案的支点：一个程序若不能计算哈希、不能验签，它就**不可能**在本地判断一个序列号
是否由厂商私钥产生。于是"本地算号器"这条路在设计上就被排除了——不是难，是不存在。

这一条必须以否证形式写进报告，并附证据（导入表清单）。否则读者会认为你只是没找到。

## 三、静态链路：字符串给的四把钥匙

字符串表按需解密（指针数组 + 逐次 XOR），但程序跑起来就全部可见。四类字符串把整条调用链
锚定住了：

| 字符串 | 作用 |
| :--- | :--- |
| `msgRegFailed` | 注册失败提示（定位失败分支） |
| `RegName` / `SerialNum` | legacy 通道的键名（定位旧路径） |
| `VerifySerialNumberW` | 验签封装函数名 |
| `CLicenseManager::*` | 管理器类方法名 |

链路（主程序侧，全部可读）：

```
注册对话框            FUN_14002da88
  → CLicenseManager::Activate            0x1400320D4
    → VerifySerialNumberW                0x140009E60
      → ExecuteXMLRequest                FUN_140009290
        → 共享内存 Global\项目EHelper_Memory（0x200B）
        → 事件 EventSent / EventComplete，互斥体 Local\UTOOL

启动检查              CLicenseManager::CheckRegistration   0x1400329C4
  → IsRegistered 封装  FUN_140009db0 → 共享内存同一通道
```

注意两个入口：**交互式激活**与**启动检查**是两套代码路径，状态处理各自独立。
只修其中一条，"下一步启动又变回未注册"是必然结果。

### 定位手法

- Ghidra headless（6.4 MB / 15,366 函数 / 300 s+），按字符串查询再导出函数清单；
- 需要看伪代码时用批量导出脚本，注意预览参数默认只截 5,000 字符——大函数会被截断，
  少于这个长度的输出**不代表函数短**；
- 目标函数在 rizin 里反汇编，定位 `call` 偏移；
- 空白区扫描：在 `.text` 尾部找连续 `CC` 填充，得到可写 stub 的位置。

这三步没有一步依赖"猜函数名"，全部有字符串或字节作锚点。

## 四、通道：明文，而验签是黑盒

两个进程之间是一个结构化的共享内存通道：

| 部件 | 名称 | 说明 |
| :--- | :--- | :--- |
| 共享内存 | `Global\项目EHelper_Memory` | `0x200B`（8203 字节） |
| 事件 A | `EventSent` | 主程序 → "请求就绪" |
| 事件 B | `EventComplete` | 运行时 → "响应就绪" |
| 互斥体 | `Local\UTOOL` | 串行化缓冲访问 |

响应是结构化文本，字段为 `result` / `ExpiryMonth` / `ExpiryYear` / `LicType` / `UserParam`。
`result` 的取值含义：`0` 失败、`2` 过期、`3` 成功。

**本案例的核心不对称**：通道是明文的，验签是不透明的。

| 层 | 可读性 | 结论 |
| :--- | :--- | :--- |
| IPC 载荷（请求/响应字段） | 完全可读 | 契约可完整建立 |
| 验签逻辑（序列号→结果） | 不可读（VM） | 无法还原算法 |

于是审计不需要读懂验签：它需要读懂的是"这个 `3` 是怎么被消费的"。

## 五、确认为什么是虚拟化，并且就此停手

运行时的入口函数 `FUN_0046ef97` 反编译出来是一个 **VM stub**：取指令流指针、
按字节码分派、维护虚拟寄存器栈。这不是"混淆过的函数"，是一个解释器。

判定清单：

| 现象 | 说明 |
| :--- | :--- |
| 分派循环 + 字节码表 | 解释器结构，不是普通控制流 |
| 函数体大小与"验签"语义完全不成比例 | 真实逻辑在字节码里 |
| 同一运行时被多个入口调用（激活 / 状态查询） | 核心逻辑集中在此 |

停手，并把结论写成一句话：

> 验签由受保护的运行时执行；该设计下不存在纯本地算号路径，因为被校验的值在 VM 内部产生。

证据等级：

- `[observed]`：分派循环、字节码表、两个入口共用同一运行时；
- `[inferred]`：验签确实发生在 VM 内（通道两侧的语义支持这一判断，但没有逐指令追踪到验签点）。

不能把第二条升格为 `[observed]`。这是报告可信度的一部分。

## 六、可读侧：状态如何变成一个决定

主程序侧的函数链清楚且短：

```
VerifySerialNumberW        → ExecuteXMLRequest（写共享内存、等事件）
  → 解析响应文本
  → 取 result 字段 → 整数
  → 与常量比较 → 走成功分支或失败分支
```

成功分支里做了三件事，每件都要读到：

1. **写注册表**：`HKCU\Software\项目E Software\项目E`，值名 `RN`（注册名）与 `RC`（序列号），
   数据来自响应字段（内存偏移 `param_1+0x170` / `+0x178`）；
2. **归一律类型**：`+0x188` 处存 `LicType`，`0` 会归一到 `1`（单机授权）；
3. **先清零再写**：`local_478` 处先 `memset(0, 0x16)` 清空结构，再写字段。

第三点是补丁时最容易漏的：若只改判定而不让调用方写入类型字段，后续代码读到 0，
会走另一条分支（显示未授权或走便携版逻辑）。

失败分支则弹 `msgRegFailed`。

### 启动检查是另一条路

`CLicenseManager::CheckRegistration`（反编译输出 40,130 字符）做的是：

```
读 RN / RC（非空 → 走与成功分支相同的路径）
  → 为空则读 legacy 通道（SecureReadW，键名 RegName / SerialNum）
    → 都没有 → 试用 30 天（0x1e）
      → 时钟回拨检测：CLCK MVD BCK / CLCK DS LT {} / _atoi64
末尾调用 FUN_140009270 启动 Helper，失败则 TerminateProcess
```

两个细节决定了复现的成败：

- **Helper 必须存在**：启动检查末尾会拉起运行时，拉起失败直接 `TerminateProcess`。
  所以"把 Helper 干掉"不是旁路，是自杀。
- **注册表值是启动检查的输入**：只修交互式激活而不写 `RN` / `RC`，下次启动依旧是未注册，
  且注册名为空。

## 七、补丁：重定向一次解析，而不是改比较

```asm
; 原始
0x140009E0F  E8 B4 4A 2D 00   call 0x1402DE8C8     ; 从解析文档取整数
; 补丁
0x140009E0F  E8 0E 78 F9 FF   call 0x140001622     ; → 自建 stub
```

```asm
; stub（放在 .text 尾部 CC 填充区）
0x140001622  B8 03 00 00 00   mov eax, 3
0x140001627  C3               ret
```

7 字节，不动栈、不改返回寄存器约定。

为什么改 `call` 而不是改比较？因为比较处只决定"这一次"，而返回值的来源在多处被复用；
把来源钉死，后续所有消费点都一致。为什么不动那个通用"取整数"辅助函数？因为它被多个调用点
共用，改它会让无关的整数读取全部返回 3。

### 副作用矩阵

| 面 | 读什么 | 补丁后 |
| :--- | :--- | :--- |
| 注册对话框 | `result == 3` | 成功关闭 |
| 启动检查 | 注册表 `RN` / `RC` | **需自行写入才显示已注册** |
| 关于/注册信息 | 响应里的显示名 | **空**（补丁从未提供） |
| 授权类型 | 归一后的 `LicType` | 保持单机授权；依赖清零-写入顺序 |
| 便携版 | `LicType` 998 / 999 | 不适用（另一条通道，需 `license.dat`） |

两句话值得写进报告：

1. **名字为空不等于补丁失败**：判定变了，数据本来就没有。
2. **启动检查是另一个函数**：它自己读持久化值，自己有 30 天试用与时钟回拨检测。

### 联网仍会发生

运行时依旧会尝试访问授权服务（`<AUTH-SRV>/verify.php`）。补丁不阻止它，也不需要阻止：
`result` 已被钉死为 3。若要完全离线，用 hosts 屏蔽即可，但这属于环境控制，不属于补丁内容。

## 八、复现与验证

| 步骤 | 期望 |
| :--- | :--- |
| 打补丁（对副本） | 两处回读分别命中 `E8 0E 78 F9 FF` 与 `B8 03 00 00 00 C3` |
| 交互式激活，输入非法序列号 | 对话框以成功关闭 |
| 写入 `RN` / `RC` 后重启 | 显示已注册 |
| 运行时进程是否仍在 | 是（补丁不禁用它） |
| 稳定性 | 观察期内无二次校验弹窗 |

补丁器自带 `--verify` 会输出 `is_patched=True`，另有一个 C# 测试工具跑断言全集（ALL PASS）。
这两项能证明"补丁落对了位置"，但**不能替代**上面两行行为验证——回读成功只说明字节写进去了。

### 环境坑

- 目标必须与 Helper、`languages\*.xml` 同目录；单独把一个 exe 拷到临时目录，
  失败原因与补丁无关（是资源缺失）。
- 从批处理/脚本启动 GUI 子进程时，某些宿主会在命令结束时终止其启动的进程。
  想让"启动 → 等待 → 枚举"跨命令存活，必须在同一条命令内完成整个序列。

## 九、根因：权威放错了进程

| # | 根因 | CWE |
| :--- | :--- | :--- |
| 1 | 安全判定在受保护代码里产生，却以**裸整数**交给不受保护的主程序，由后者单独决定权益 | **CWE-602** |
| 2 | 通道为明文共享内存，无认证、无签名、无完整性校验 | CWE-319 |
| 3 | 判定结果以短值名（`RN` / `RC` / `VH` / `VL`）落地注册表，可静态枚举 | CWE-522 类 |
| 4 | 保护投入集中在验签算法，未覆盖"结果的消费方" | CWE-693 |

第 1 条是核心。第 4 条解释了为什么"花大钱做虚拟化"没有降低整体成本：攻击者不需要碰被保护的
那一半。

### 整改

| 层 | 措施 |
| :--- | :--- |
| 服务端权威 | 运行时返回**签名后的权益凭据**（或主程序校验响应签名）；权益判断不得以裸状态码传递 |
| 通道 | 共享内存加消息认证（HMAC，密钥由运行时持有），或改为带校验的本地 socket |
| 客户端 | 判定函数下沉到受保护侧**并在受保护侧消费**；主程序只持有不可伪造的凭据 |
| 数据 | 注册表存加密/签名凭据而非"名字 + 序列号"；值名不做混淆当安全 |
| 运营 | 心跳失败由服务端吊销，而不是客户端自杀 |

## 十、方法论沉淀

1. **先证明"做不到"**：导入表没有密码学原语 → 本地验签在设计上不可能。这条否证省掉整条算号器路线。
2. **成本最低的证据优先**：导入表、字符串表、进程/对象枚举，任何一步的结论都比读 15,000 个函数便宜。
3. **区分"加壳"与"虚拟化"**：前者挡静态阅读，后者挡逻辑还原；误判会把时间花在错误的方向。
4. **找不对称**：明文通道 + 黑盒验签，就是这个案子的入口。审计要找的是"契约可读的那一侧"。
5. **两个入口都要看**：交互式激活与启动检查各自独立；只修一条等于没修。
6. **改来源不改判断**：重定向一次状态解析，优于在多处改比较。
7. **把副作用列成表**：判定变了不等于数据有了，空字段必须在报告里解释清楚。

## 十一、限制与未验证项

| 项 | 状态 |
| :--- | :--- |
| 验签算法是否可还原 | `[unverified]` 仅确认 VM stub 结构，未尝试字节码级还原 |
| 验签确在 VM 内执行 | `[inferred]` 依据分派循环 + 两入口共用运行时，无逐指令追踪 |
| 服务端响应是否带签名 | `[inferred]` 通道明文且客户端直接信任整数，推断未签名 |
| 仅安装版 | `[observed]` 单机授权（`LicType` → 1）；便携版走 `license.dat` 通道，本方法不适用 |
| 长期稳定性 | `[observed]` 观察期内无异常；`[unverified]` 若运行时被服务端推低有效期，后续状态查询会重新返回 2 |
| 样本指纹与产物哈希 | 已脱敏，不在本仓库；复现需自带合法样本 |

最后一行提醒一件事：这是**授权流程审计**，不是密码学攻击。报告若被读成"破解了 EXECryptor"，
就完全错了——我们没有碰它，只是证明碰它没有必要。
