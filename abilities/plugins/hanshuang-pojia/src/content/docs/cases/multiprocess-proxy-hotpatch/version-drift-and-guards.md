# 跨版本攻防演进与护栏（项目B，v12.0 → v6.8.1）

> 案例类型：跨版本补丁工程 · 交付可靠性 · 更新通道风险
> 脱敏：产品名、端点、样本哈希已移除；演进对照、失效案例、工装与加固建议完整保留。

同一个产品被做了两代方案。把两代放在一起看，得到的不是"哪个更强"，
而是**哪一类做法会随构建腐烂**。这一篇记录的是腐烂的位置和护住它的办法。

---

## 一、两代方案的六个维度对照

| 维度 | 早期 v12.0 | v6.8.1 | 机制变化 |
| :--- | :--- | :--- | :--- |
| 广告剥离 | 在 `sub_14012A640` 入口 `mov eax,1; ret` | 在非会员分支 `0x12ada3` 处 6 字节 `NOP` | 旧法短路了信号分发，Qt 信号 `member_remove_ad_ok` 丢失；新法只中和条件跳转 |
| 试用营销流 | `0xce9989` 的 `jle` | `0xcef5df` 的 `jle` → 无条件 `jmp +0xee; nop` | 阻断试用提示与充值弹窗 |
| 网络响应反序列化 | 分散在旧版账号/用户函数 | `0xd1907a`–`0xd196c6` 区间 6 个连续 `call` | 把"提取字段"的调用改为立即数赋值 |
| 守护进程防回写 | `0xCC` 空洞远跳板（`33 c0` → `eb 21`） | 覆盖 `parse_a/b` + `serialize` + 2 处 `is_valid_infos` + 端点本地化 | 跳板依赖布局，被等价替换淘汰 |
| 远程会话与推流 | 仅阻断启动入口 | 启动入口 + RTTI 符号 `isCurrentSessionRemoteSession()`，`0x17d9b0` 短路 `GetSystemMetrics(SM_REMOTESESSION)` | 防远程会话误激活 + 关停推流 |
| 交付形态 | `sentry.dll` + `version.dll` 双文件转发 | `winhttp.dll` 单文件全量裸桩 | 四大主程序均静态导入，免改名 |

六个维度里，有三个是被**否证**推翻后才换的。这些否证比最终方案更有教学价值。

---

## 二、三个被否证的做法

### 2.1 函数入口整体返回

最早的广告剥离是在判定函数入口写 `mov eax,1; ret`。看起来干净，实际后果是
**Qt 信号 `member_remove_ad_ok` 不再发射**。

宿主不是"调用函数拿返回值然后分支"，而是"函数执行后发射信号，界面订阅信号"。
提前返回把信号一起跳过了，于是界面停在旧状态，用户看到的是"补丁无效"。

> 教训：在事件驱动的框架里，判定点不是一个返回值，而是"判定结果被用于何处"。
> 要改的是那个分支，不是函数的入口。

### 2.2 `0xCC` 空洞远跳板

守护进程侧曾用"跳到一段 `0xCC` 填充里执行自己代码再跳回"的办法（`33 c0` → `eb 21`）。
它依赖那条填充在链接后仍然存在且足够长。换一次构建、换一次链接器版本，填充长度就变了。

替代方案是**等价替换**：不动控制流，而是让 `parse_a/b`、`serialize` 与两处 `is_valid_infos`
都按"已授权"路径产出（例如 `is_valid_infos` 直接置真 `b0 01 90…` / `b1 01 90…`），
再把服务端端点从 `v1/member/trial` 本地化为 `v1/member/local`。
结果同样，但不依赖任何内存布局巧合。

### 2.3 按固定差值平移旧点位

旧 53 条语义点位在新构建上**逐字节命中 0 条**。于是尝试用"整体差值"平移：
Main 有效（分区恒定 `+0xcf00` / `+0xadc0` / `+0x1320` / `+0x9530`），
Service 无效（差值不恒定），RemoteService 更无效（体量增长 3.66 倍）。

> 教训：平移只在**同一编译单元内**近似成立。跨编译单元假设平移，得到的是
> "看着像对的错误地址"——它不会立刻崩，而是在几秒到几分钟后以别的方式失败。

## 三、更新通道：最容易被忽略的一条回路

套件带自动更新。更新程序会重新安装被替换的模块，也会重新下载被改写的执行文件。
更关键的是：**更新程序同样静态导入 `winhttp.dll`**，所以它也会加载代理。

这条回路既是风险，也是能力：

- 风险侧：一次自动更新可能让全部工作消失，而用户只会看到"又变回试用版了"；
- 能力侧：代理可以在更新握手的那一刻调用 `ExitProcess(0)`，把更新流程截断在下载之前。

本案选择了后者，但把它明确记为**设计决策**，而不是推荐做法：

| 取舍 | 说明 |
| :--- | :--- |
| 收益 | 阻止更新覆盖补丁 |
| 代价 | 用户也收不到安全更新；静默退出对用户不可解释 |
| 结论 | 报告里单独成节，交由产品方判断；不作为通用建议 |

任何"让产品无法自我修复"的手法，都必须以同样醒目的方式写进报告。

## 四、合成宿主：不碰真实安装也能验证写入器

补丁器最难测的部分是"写对了没有"，而真实安装目录既不该反复写，也不该是唯一的测试环境。

做法是构造一个**合法 PE64 宿主**（本例 17,830,912 字节）：在精确 RVA 处植入原始字节，
加一个入口桩，让代理以为自己是目标。然后：

1. 用测试代理跑一次，日志应报出期望点位数且全部 `APPLIED`；
2. 逐字节比对目标区域，期望 `BEFORE=[11,22,33,44,55,66,77,88]` →
   `AFTER=[de,ad,be,ef,de,ad,be,ef]`（测试图案）；
3. 第二次加载同一镜像，日志应为 `ALREADY` 而不是再写一遍。

这个工装的价值在于**可重复**：它把"写入器是否正确"从一次性的安装实验变成了回归测试。
本案还用它验证了 `MISMATCH` 路径——把合成宿主的某处字节改掉一个，日志立刻变成
`mismatch=4` 且**零写入**。

## 五、护栏清单

| 护栏 | 实现 |
| :--- | :--- |
| 先比对再写 | 每条点位携带原始字节，不匹配即跳过 |
| 四态日志 | `APPLIED` / `ALREADY` / `OUTOFRANGE` / `MISMATCH` / `SKIPPED` |
| 幂等 | 二次加载走 `ALREADY`，不重复写 |
| 宿主识别 | 非目标宿主走 `SKIPPED`，明确记录"不覆盖" |
| 备份 | `backup_proxy_guard\<时间戳>\` |
| 可回滚 | `Restore-ProxyDll.ps1`，且实验室里跑过一次 |
| 写入范围声明 | 只写程序目录内的代理与日志；EXE / 注册表 / 系统目录 / 服务配置零写入 |
| 签名确认 | 部署后 `Get-AuthenticodeSignature` = `Valid` |

这八条里，只有"先比对再写"是技术性的；其余七条是工程纪律。
而恰恰是纪律决定了这套东西能不能交给别人复现。

## 六、纵深防御建议（给产品方）

| 层级 | 措施 |
| :--- | :--- |
| 客户端加固 | 特权判定下沉 Native + 控制流平坦化；周期性 CRC 自校验；反调试/反注入；模块枚举白名单；第三方 DLL 签名校验 |
| 交付完整性 | 启动时校验同目录模块的 Authenticode 与预期签名主体，拒绝未签名同名 DLL |
| 传输层收敛 | TLS 双向证书 + SSL Pinning；请求加 `Sign + Nonce + Timestamp`；关键字段单独签名 |
| 服务端权威 | 权益由服务端签发短效票据，客户端只验签不决策；心跳失败由服务端吊销 |
| 检测与响应 | 完整性失败上报遥测，并降级为受限模式（而不是静默退出） |

最后一行值得单独说：本案把"断权"实现在客户端（自毁/退出）。
正确做法是**服务端吊销**——客户端只负责如实上报，不负责自行了断。

## 七、限制与未验证项

| 项 | 状态 |
| :--- | :--- |
| 早期 53 点位在新版的逐字节比对 | `[observed]` 0/53 命中 |
| Service 位移不恒定的具体成因 | `[inferred]` 由跨编译单元重排推断，未逐符号核对 |
| 更新阻断对产品完整性的长期影响 | `[unverified]` 未评估安全更新的缺失风险 |
| 合成宿主的行为等价性 | `[observed]` 字节级；行为级仍需真实安装复核 |
| 反注入/反调试是否已被宿主启用 | `[unverified]` 本版本未观察到，但未穷举检测项 |

这份材料的结论可以压成一句：**能被随构建腐烂的，都不是方案，只是这一次的运气。**
把交付建立在"宿主本来就导入的模块 + 逐点比对 + 四态日志"上，
才有资格说"换一个版本还能用"。
