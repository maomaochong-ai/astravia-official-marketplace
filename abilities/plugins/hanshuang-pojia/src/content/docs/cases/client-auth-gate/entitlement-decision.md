# 客户端特权判定：从候选门到可复现的裁决点（CWE-602）

> 案例类型：客户端鉴权旁路验证（CWE-602）／目标：一个把付费能力写在客户端的 Android 应用／脱敏：端点写为 `<AUTH-SRV>`，密钥与卡密一律不落文档，样本哈希写为 `<实测哈希>`。

---

## 一、现场

这个案子不是从「找 license 字符串」开始的，而是从一句互相矛盾的观察开始的：应用里那个付费入口在界面上是灰的，但它在离线状态下也会灰；把网络断掉，灰的依旧是灰的，说明这个「灰」不是在等服务器回话，而是一个本地判断的结果。

先把能静态看到的东西摆出来。反编译之后，字符串池里同时存在三类东西：

1. 一组业务字符串（列表、导出、批量处理这些功能名）；
2. 一组权限语义词（`isPro`、`premium`、`vip`、`trial`、`quota` 这类），它们出现在方法名和字段名里；
3. 极少量网络字符串，而且都不指向「校验购买」这件事——没有 `verifyPurchase`、没有收据字段、没有 `<AUTH-SRV>` 上的权益端点。

这个组合本身就是现场的定义：**名字说它在决定权益，而同一个包里没有任何东西去问服务器**。CWE-602 的形态到这里已经成立了一半，但只有一半——名字可以是遗留代码，调用者才决定它是不是真的在发放权益。

静态能拿到的第二层事实更关键：候选方法都有一个调用者，调用者都在渲染路径上（列表项的可用状态、导出按钮的 enable、批量任务的配额检查），而不是在某段没有被引用的死代码里。三条渲染路径共用同一个布尔取值，这个「漏斗」形状是后面所有取证的支点。

## 二、判定

判定分成两层，先后顺序不能颠倒。

**第一层：这是不是客户端的裁决。** 判据是把两张表并排放：

| 观察 | 含义 |
| --- | --- |
| 候选门非空 + 权威面为空 | 权益在本机被决定，按 CWE-602 处理 |
| 候选门非空 + 权威面非空 | 门存在，但它是否**调用**了权威面尚未知，属于待解问题，不是结论 |
| 候选门为空 | 名字被混淆了，换字符串池检索，不要宣布「没有门」 |

工具只负责把这两张表并排打印，结论留给操作者——这一点是刻意的。一个工具如果直接输出「存在客户端鉴权漏洞」，它就在替操作者越过「调用者是否存在」这一步，而这一步恰恰是最容易错的地方。

**第二层：严重性由两个问题决定。**

1. **服务器是否逐请求复核？** 如果每次请求都带着服务端可验证的凭据重新判权，那么客户端那个布尔只是界面装饰，结论应写成「界面信任本地标志」，严重性低。它依旧是缺陷，只是不是「权益绕过」。
2. **客户端状态是否随请求上行？** 如果请求体里带着 `is_pro`、`plan`、`credits` 这类字段，而服务端照着用，那就从 CWE-602 升级成失效的功能级访问控制（BFLA）。这一条必须用**请求**证明，不能用二进制证明——二进制只能说明客户端愿意发，不能说明服务端愿意信。

这两问的回答决定报告的第一段怎么写，也决定要不要继续做补丁。很多时候答案是「服务器会复核」，那么补丁只是演示可达性，价值有限；真正该写的是「为什么界面要相信一个可以被本地翻转的标志」。

## 三、取证

取证的顺序是「静态并列 → 动态观察 → 成对运行」，三步各自产出可引用的东西。

**第一步，静态并列。** 在案例目录里跑：

```bash
cd tools
python3 gate_scan.py --self-test
python3 gate_scan.py --sample target.apk --out findings/
```

自检先跑，是因为它证明工具本身可用：`kit self test: 44/44` 证明共享层解析正常，`gate_scan self test: 5/5` 证明这个工具在合成样本上确实能定位到门。没有这两行输出，后面任何一张表都不能作为证据。

正式跑的输出要保留三样：

- `dex units` 的逐文件摘要（字符串数、方法数、版本、结构问题）——它是「这个包里有几份代码」的底账；
- `candidate gates` 表（dex / method / 命中的提示词）；
- `authority surface` 表（dex / 字符串），以及它在什么情况下为空。

`--out findings/` 会写一份 `patch-table.skeleton.txt`，里面每一行是 `# 0x000000 | 0F 85 ?? ?? ?? ?? | 0F 84 ?? ?? ?? ?? | <method> -> force the non-entitled branch`。这份骨架**不是证据**，它是待填的表：地址和原始字节要由反汇编填，填不上就说明还没有定位到裁决点。

**第二步，动态观察。** 静态只能证明「有调用者」，不能证明「返回值决定分支」。用 observe 模式的 hook，一次拿到三件事：是否被调用、从哪儿调用、入参是什么。

```text
generate_hook(mode="observe", query="<候选方法名>", backtrace=true)
```

观察结果里最有价值的不是返回值，而是**调用栈**：如果栈上出现的是渲染层，说明这个布尔在被用来画界面；如果栈上出现的是某个 `verify` 类的本地方法，说明它背后还有一层判断，刚才的候选只是二传手。

**第三步，成对运行。** 同一份输入、同一个入口，跑两次：

| 运行 | 期望 |
| --- | --- |
| 未修改的构建 | 受控能力关闭，且关闭的原因来自那一条分支 |
| 修改后的构建（或运行时覆写） | 同一能力可用 |

只有这一对才能叫证明。单独一张「改完之后能用了」的截图，无法排除「本来就能用，只是我刚才点错了」。

## 四、否证

这一节比前面三节都重要，因为真正会写错的不是「找不到门」，而是「找到了门却不是那个门」。

**否证一：门是死的。** 候选方法存在但没有任何调用者，或者调用者的结果被丢弃（返回值赋给一个从不被读的变量）。反证方式是列出调用者并说明每一个的去向；做不到就不能声称它是门。

**否证二：门后面有服务器。** 门的调用者里出现了一个同步请求，响应被解析成权益对象，本地的布尔只是缓存。这种情况下 CWE-602 不成立，成立的是「缓存没签名」或者「离线宽限期太长」，严重性完全不同。

**否证三：门是签名的收据。** 本地确实在验证一个收据，但收据是用内嵌公钥验签的，而且公钥确实参与了运算。这时候「改一个布尔」不会让功能可用，除非同时伪造签名——那就退回到密码学问题，不是客户端权威问题。

**否证四：补丁打在了错误的层。** 在实际演练里最常见的一种假成功：改了一个 `isPro` 的读取点，界面亮了，但真正干活的那条路径还会再查一次配额，于是功能在第二步失败。正确的否证是「把补丁点与失败点对齐」——如果失败点不是补丁点，补丁只证明了「这个布尔被渲染层读过」。

**否证五：名字误导。** `isLicensed` 这类名字在不少应用里指的是「协议已接受」，与付费无关。否证方式是看这个布尔在哪儿被写：如果写入点是一个「同意条款」的按钮回调，它就不是权益门。

**否证六：你以为的空权威面其实是检索空。** 如果字符串池里没有端点，先确认检索跑过了（`authority surface` 段落里出现 `none - no endpoint or receipt string found` 才算真的检索过），再确认没有被加密的字符串表（DEX 里出现高熵字符串区是信号）。

## 五、复现

一份可复现的记录必须包含下面这几项，缺一项就会被下一个人重做一遍。

**1. 环境与身份。** 样本 SHA-256（写 `<实测哈希>`）、包名、版本号、DEX 份数与大小、反编译工具与版本。

**2. 定位。** 两种粒度都要给：

```text
smali：Lcom/<pkg>/<Class>;-><method>(...)Z
        第 <n> 条指令：const/4 v0, 0x0  ->  const/4 v0, 0x1
native：<lib>.so + 0x<偏移>（RVA 0x<偏移>）
        B0 <原字节>  ->  20 00 80 52 C0 03 5F D6   (MOV W0,#1 ; RET)
```

ARM64 那条 `MOV W0, #1; RET` 的编码是 `20 00 80 52 C0 03 5F D6`，它把「返回值恒真」压缩成两条指令，前提是函数的唯一返回值在 `w0`、且调用约定没有被尾调用改写。这个前提必须验证过才能写进表里——用 `disassemble_range` 看函数尾部即可。

**3. 补丁表。** 每一行是「地址 | 原始 | 补丁后 | 效果」，一处一行，不合并：

| 地址 | 原始 | 补丁后 | 效果 |
| --- | --- | --- | --- |
| `0x<实测偏移>` | `0F 85 ?? ?? ?? ??` | `0F 84 ?? ?? ?? ??` | 反转条件跳转，走非权益分支 |
| `0x<实测偏移>` | `B0 <原字节>` | `20 00 80 52 C0 03 5F D6` | 返回值恒真 |

**4. 验证。** 同一输入在改前改后各跑一次，给出退出码或输出片段；运行时覆写要给出脚本路径与命中日志。

**5. 回滚。** 恢复原始字节的确切步骤：从备份文件拷回，或者在同一个偏移写回原始字节，然后重算哈希与备份比对。要说清「回滚的是字节，不是状态」——缓存里的权益状态要另外清。

## 六、边界与遗留

- 只测了范围内的那一个应用、那一个账号；没有把同一台设备上其他应用的流量带进来。
- 没有记录任何真实密钥、卡密、收据或令牌；样本里出现的凭据只以「存在、长度、位置」描述。
- 运行时覆写是**可达性演示**，不是可发布的绕过；报告里必须用「演示」这个词，不能用「已绕过」。
- 如果服务器逐请求复核，本案例的结论应停在「界面信任本地标志」；把它写成权益绕过是过度声明。
- 未解问题要写出来：如果门背后还有一层用服务端下发密钥解密的判断，本轮没有触及，应标为未知而不是补全。

这一节的写法决定了这份记录能不能被第二个人接手。宁可写「不知道」，也不要写一个看起来很完整、但复现不出来的结论。
