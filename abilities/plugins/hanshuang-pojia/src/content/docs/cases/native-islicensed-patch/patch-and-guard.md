# 项目G —— 补丁常量、防回退与回滚

> 补丁表与字节序列为教学值；VA 以 `0x140000000` 为基址，文件偏移按 `.text` 起始 RVA `0x1000` 反算。
> 换版本后必须按第五节重新定位，不要照抄偏移。

---

## 一、补丁表

| 项 | 值 |
| :--- | :--- |
| 符号 | `项目G::isLicensed(void)`（无参数成员函数，C++ 修饰名） |
| 虚拟地址 | `0x140b83910` |
| 文件偏移 | `0xB82D10` |
| 原始字节 | `48 89 4C 24 08`（`mov qword [rsp+8], rcx`，把 `this` 溢出到影子空间） |
| 补丁字节 | `B0 01 C3 90 90`（`mov al,1; ret; nop; nop`） |
| 原始 SHA-256 | `<实测哈希>` |
| 补丁后 SHA-256 | `<实测哈希>` |

补丁写入后，`isLicensed` 恒返回 `true`，函数体的读 INI、解析 payload、校验 `key_hash` 全部不执行。
由于入口桩在函数帧分配之前就返回，不存在栈平衡问题；五字节长度与原序言相等，后续指令地址不变。

## 二、为什么补入口而不是补尾部

原函数体里有若干失败出口，每个出口最终都返回 `false`。两种改法都可行：

| 改法 | 位置 | 适用条件 |
| :--- | :--- | :--- |
| **入口桩**（本案例） | 函数入口五字节 | 函数体是纯粹的"读 + 判"，无副作用 |
| 尾部改判 | 最后那处 `xor eax,eax` → `mov al,1` | 函数体会初始化调用方依赖的状态 |

本案例选入口，是因为函数体唯一的可观测效果就是返回值。判据很直接：反汇编里检查函数体内是否
存在对 `[rcx+偏移]` 的写、是否有对全局变量的写。两者都没有，入口桩就是安全的。

**不要因为入口桩更短就默认选它。** 一旦函数体负责填充一个对象，入口桩会把那份填充一起跳过，
表现是"窗口打开了，但某个功能不可用"或者"运行十几秒后访问违例"—— 后者尤其容易被误判成补丁
无效，然后继续叠加第二个补丁，把问题埋得更深。

## 三、兼容性三分支

按模式直接写字节，会在一份"序言恰好相同"的其他版本上命中错误的函数。因此写入前先分类：

| 状态 | 判据 | 动作 |
| :--- | :--- | :--- |
| 已补丁 | 目标字节等于 `B0 01 C3 90 90` | 跳过，输出 `patched (已激活)` |
| 原版 | 目标字节等于 `48 89 4C 24 08` **且** 文件哈希命中已知构建 | 写入补丁 |
| 未知 | 字节不同 | 拒绝写入，打印警告，不做任何修改 |

第三行是最容易被省略的一行，也是"工具"与"隐患"的分界：在未识别的构建上，那五字节可能属于
完全另一个函数。拒绝写入的代价是"这次没生效"，而误写的代价是"程序坏了且不知道为什么"。

脚本的自检（`python -m pytest tests -q` → 5 passed）覆盖了：常量自洽、补丁往返、版本识别、
样本哈希、以及"引导用户购买正版"的链接存在。第三项就是上面这张表的回归测试。

## 四、防回退机制

产品更新会覆盖 `项目G.exe`，所以补丁需要一层"登录后自动修复"：

```
HKCU\Software\Microsoft\Windows\CurrentVersion\Run
    项目GActivateGuard = "<tool>.exe --silent --fix"
```

守卫在登录后执行：

1. 枚举安装目录（含多用户、多版本路径）；
2. 读取目标文件的五字节，按第三节三分支分类；
3. **仅在"原版"状态下重写**；已补丁则跳过；未知则保留并记日志；
4. 退出，不驻留、不联网。

三个附加开关：`--silent`（无窗口）、`--fix`（执行修复）、`--unguard`（删除 Run 键）、
`--revert`（从 `.bak` 还原原始字节）。还原流程是：删除 Run 键 → 用 `.bak` 覆盖 → 校验哈希回到原值。

两条可迁移的设计原则：

- **幂等要基于字节判据，不能基于标志文件**。标志文件在升级后会撒谎：它说"已补丁"，
  而二进制已经被覆盖成原版。
- **回滚路径必须能在工具本身损坏时走通**。如果只有守卫知道怎么还原，守卫一坏，安装就锁死了。
  所以 `.bak` 是独立文件，还原命令也不依赖守卫进程存活。

## 五、换版本时的重新定位

1. 确认符号仍然存在、仍然无参数。若修饰名变了，通常是类名改了，而不是函数被删。
2. 确认前五字节仍然是"溢出 `rcx`"的形态。编译器升级可能重排序言（例如先 `sub rsp` 再溢出），
   这时五字节桩的边界要跟着变。
3. 确认目标区间之后有至少五字节可覆盖，且**没有跳转落在被覆盖范围内**（有则改用尾部改判）。
4. 读一个调用点，确认返回值仍然喂给一个二分支，而不是被塞进三态枚举。
5. 重跑一次启动对照，确认分支日志仍然命中 pass 分支。

## 六、验证序列

```
# 0) 基线
sha256sum 项目G.exe                     → <实测哈希>
# 1) 原始行为
项目G.exe                                → [branch] free-trial @46a3e7
# 2) 打补丁
python <tool>.py 项目G.exe               → 写入 5 字节，回读一致
xxd -s 0xB82D10 -l 5 项目G.exe           → b0 01 c3 90 90
# 3) 补丁行为（同一输入）
项目G.exe                                → [branch] pass @46a6b6，无 INI 许可读取
# 4) 重启持久
关闭 → 启动 → 仍为 pass 分支
# 5) 守卫
模拟升级覆盖 → 注销/登录（或直接跑 --silent --fix）→ 五字节恢复为补丁
# 6) 回滚
<tool>.exe --unguard --revert            → 哈希回到 <实测哈希>
```

第 3 步的两个观察缺一不可：分支日志证明判定被改，文件访问消失证明函数体确实没执行。
只有前者，无法排除"函数体跑了一遍但结论被覆盖"；只有后者，无法证明最终走的是放行分支。

## 七、回归到方法论

这套补丁的形状可以概括成一句话：**当一个决定从唯一出口返回时，改出口比改条件便宜**。
它的前提条件有两个，都必须现场确认，而不是假定：

1. 没有完整性自校验（否则改完即失效或拒绝启动）；
2. 函数体无副作用（否则入口桩会破坏后续状态）。

两个前提只要有一个不成立，就要退回到"改条件跳转"那条更保守的路线。

## 八、限制与未验证项

| 项 | 状态 |
| :--- | :--- |
| 补丁在其他小版本上的字节一致性 | `[unverified]` 仅本版本实测；未知构建默认拒写 |
| 多用户/多安装目录下的守卫覆盖度 | `[inferred]` 从枚举逻辑推断，未在多用户环境逐一验证 |
| 与反病毒产品的交互 | `[unverified]` 未做多引擎扫描 |
| 尾部改判方案的等价性 | `[unverified]` 未在本样本上实测，仅作方法论备选 |
| 服务器侧是否另有吊销/心跳 | `[inferred]` 从"补丁后无 INI 读取、无网络请求增长"推断无周期性校验，未做长时段抓包 |
