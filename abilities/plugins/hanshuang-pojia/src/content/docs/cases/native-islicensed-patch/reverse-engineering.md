# 项目G —— 单个布尔符号即全部授权判定（逆向证据链）

> 案例类型：原生 x64 · Qt 桌面程序 · 本地布尔裁决（CWE-602）
> 脱敏：产品名、安装包名、密钥与签名模板的值、样本哈希均已移除或置为 `<实测哈希>`；保留 VA、文件偏移、补丁字节与算法结构。

本案例的价值在于"判定的形状"：整个授权体系最後收敛成一个无参数的成员函数，返回 `bool`。
既然只有一个返回值决定一切，那么真正需要证明的就不是"能不能改"，而是"**改了之后有没有第二处还在判**"。
本文记录这条证据链是怎么建立的。

---

## 一、样本概况

| 项 | 值 |
| :--- | :--- |
| 主程序 | `项目G.exe`（x64，Qt，MSVC，**无壳无签名**） |
| 体积 | 约 27 MB（Qt 静态依赖带来的体量） |
| 分发形态 | 安装包 NSIS 3.12 解包，内层 `项目G.7z` 二次解压 |
| SHA256 | `<实测哈希>` |
| MD5 | `<实测哈希>` |
| 授权子系统 | 内置，网络激活 + 本地 INI 状态 + grace token |

"无壳无签名"这一条决定了路线：不需要脱壳、不需要处理完整性校验，直接做文件级字节补丁即可。
如果这里是有壳、有自校验或代码段运行期才解密，本案例的结论不成立，应改走运行期内存补丁那条路。

## 二、反汇编方法：为什么放弃全量分析

Ghidra headless 对 27 MB 的 Qt 二进制做全量分析，耗时过长且环境容易中断（大内存 + 长任务，
中途 OOM 或超时都会让前功尽弃）。因此改用**确定性扫描**，流程是：

```
解析 PE 节表
  → 在 .rdata 中定位目标字符串的 VA
  → 扫描 .text 中所有 LEA r64,[rip+disp32]（编码 48/4C 8D /r，mod=00 rm=101）
  → 反算每条 LEA 的引用目标，命中即得到一个引用点
  → 对引用点做局部分片线性反汇编（rizin pd）
```

这条链路的价值不在"快"，而在**可复现**：同一份二进制、同一份脚本，输出一定一致；
换个版本重跑一次，就能拿到新旧版本的引用点差异。相比之下，分析器的自动分析结果会随版本、
插件、内存状态漂移，两次运行未必给出同一份函数边界。

代价是只看到"引用点附近"，看不到全局调用图。所以下一步必须靠符号表与调用点补齐，而不是靠猜。

## 三、函数入口表

基址 `0x140000000`。下表是本次样本的实测值（`[observed]`）：

| 函数 | VA | 说明 |
| :--- | :--- | :--- |
| `项目G::isLicensed(void)` | `0x140b83910` | **启动授权判定，补丁目标**；文件偏移 `0xB82D10` |
| `项目G::activate(const QString&)` | `0x140b82640` | 激活入口，对应源码 `项目G.cpp` 第 341 行附近的日志 |
| `项目G::readIni` | `0x140b85xxx` 一带 | 读 INI 许可；"license key data empty" 字符串引用在 `0x140b85631` |
| `项目GV2::isLicensed(...)` | `0x140ba1d70` | 本地复验：`sha384(p)` 对比 `payload["key_hash"]` |
| `项目GV2::writeIniFromPayload` | `0x140ba7060` | 写 INI 的 `Others/reg_id`（Base64）与 `Others/reg_key` |
| `项目GV2::handleDeviceReplyInternal` | v2 区 | 服务器响应处理；"MD5 signature check failed" 引用在 `0x140ba4fbd` |
| `checkLicense` | `0x14046a264` | 每次启动执行；分支 free-trial `@0x14046a3e7` / pass `@0x14046a6b6` |

两个要点：

1. **`isLicensed(void)` 无参数**。无参数意味着它的输入全部来自全局状态（INI、内存缓存、
   grace token），不来自调用方 —— 这既解释了为什么它能被一个 `mov al,1; ret` 完全替代，
   也说明它的返回值是唯一出口。
2. **`checkLicense` 是分支所在，`isLicensed` 是值所在**。分支日志落在 `checkLicense` 里，
   这是后面做对照实验的观测点。

## 五、校验语义（四层）

```
V1 网络激活: POST property_key → 服务器签发                    （不可离线复现）
V2 响应签名: sig = hex(sha1(TEMPLATE + payload[32:])) == payload[0:32]
V2 本地复验: hex(sha384(payload_utf8)) == payload["key_hash"]   ← 自引用，无解
grace token: AES-CBC 解密 → JSON{ids, last_ok, deadline} 校验
```

第三行是这套体系里最有意思的一处：`key_hash` 是被验证载荷自身的一个字段，而它又是该载荷的
哈希。要构造一个满足它的载荷，等于要求 `payload` 包含自己的哈希 —— 在密码学上无解。
换句话说，**本地复验这条路径不构成一条可伪造的通路，它只是把"这确实是我们签发的那一份"
这件事再说了一遍**。真正决定签发权的是 V1，而 V1 在服务器。

这也解释了为什么 keygen 路线不成立（见第九节）：能离线构造的部分，全部被自引用哈希堵死；
能签发的部分，需要服务器私钥。

## 六、动态验证记录

Frida 17.16，逐项对照（`[observed]`）：

| 实验 | 结果 |
| :--- | :--- |
| 传 7 种 key 调 `activate` | 均为 `licenseModeForKey=mode=1` 且 `activate=0`（被拒） |
| 传构造 payload 调 `V2::isLicensed` | 均为 0；`QCryptographicHash::hash` 未触发（早退） |
| 原版启动 | `[branch] free-trial @46a3e7` |
| 补丁版启动 | `[branch] pass @46a6b6`；进程存活 10 s 以上；**无 INI 许可读取** |
| 防回退守卫 | 注册 → revert 模拟覆盖 → `--silent --fix` 自动恢复 |

第二行值得单独说：`QCryptographicHash::hash` 未触发，说明函数在校验之前就返回了。
这是"早退"的直接证据，也是为什么往 `V2::isLicensed` 里塞构造 payload 不会有任何反应 ——
不是哈希算错了，而是根本没走到哈希。

第四行的"无 INI 许可读取"是补丁生效的旁证：入口被替换后，函数体（读 INI、校验 payload）
整段不执行，文件访问自然消失。这条观察比"界面显示已激活"更硬，因为它不依赖对 UI 文案的解读。

## 七、结论

- **keygen 离线不可行**：服务器签发 + 自引用校验，两个条件各自单独就足以否定离线构造
  （`[observed]`：7 种 key 全被拒；`[inferred]`：自引用哈希无解）。
- **本地判定点单一且无自校验** → 补丁路线成立，重启持久，升级覆盖可由登录守卫自动修复。
- 工具仅修改本地判定，不涉及服务器与计费逻辑。

第三点是这类交付里必须写明的一句：它界定了"做了什么"与"没做什么"。没有这句，
报告读者无法区分"旁路了客户端"与"绕过了计费"。

## 八、为什么五字节就够

补丁把入口改成 `mov al,1; ret`，五个字节：

| 字节 | 指令 | 作用 |
| :--- | :--- | :--- |
| `B0 01` | `mov al, 1` | 返回值低字节置 1；`bool` 只读 `al` |
| `C3` | `ret` | 直接返回，**不执行原函数体** |
| `90 90` | `nop` ×2 | 补齐到原序言的 5 字节，避免后续指令位移 |

三点技术依据：

1. **x64 上一个字节的返回值只需 `al`**。`rax` 高 56 位对 `bool` 无意义，不必清零。
2. **函数帧未分配即返回，因此无栈平衡问题**。原序言 `mov qword [rsp+8], rcx` 只是把 `this`
   溢出到影子空间，尚未 `sub rsp, N`；跳过它不会留下任何待恢复的栈。
3. **五字节正好等于原序言长度**（`48 89 4c 24 08`），所以补丁不改变任何后续指令的地址 ——
   这一点在多处代码共用同一段、且有跳转落在其后的情况下尤其重要。

反过来，如果原函数体里有调用方依赖的副作用（填充对象、设置全局标志），入口桩就会把这些一起
跳过，"能启动但功能缺失"或"延迟崩溃"随之出现。本案例的函数体是纯粹的读 + 判，因此入口桩安全；
判定依据是函数体内没有对 `[rcx+…]` 的写，也没有对全局的写。

## 九、限制与未验证项

| 项 | 状态 |
| :--- | :--- |
| 服务器签发流程（V1）的协议细节 | `[unverified]` 未抓包还原；仅从客户端侧看到"不可离线复现"这一后果 |
| `sig` 校验中模板常量的具体作用域 | `[inferred]` 从 `sha1(TEMPLATE + payload[32:])` 的形态推断为固定前缀，未逐字节验证 |
| grace token 的有效期语义 | `[inferred]` 从字段名 `grace_deadline` / `last_ok` 推断，未构造过期样本验证 |
| 补丁在其他小版本上的可用性 | `[unverified]` 仅在本文所述版本实测；字节级检测对未知构建默认拒绝写入 |
| 守卫在升级后的恢复成功率 | `[observed]` 单次模拟覆盖可恢复；跨大版本升级未测 |
| 反病毒/EDR 对补丁产物的判定 | `[unverified]` 未做多引擎扫描 |

把这张表留在报告里，比把它删掉更有价值：`[observed]` 的那几行支撑结论，`[unverified]` 的那几行
界定结论的边界。读者据此知道哪些可以直接引用、哪些必须自己复测。
