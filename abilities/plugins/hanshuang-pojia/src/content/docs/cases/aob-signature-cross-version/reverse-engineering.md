# 跨版本补丁引擎：五个 build、十六个位点、一套双态特征码

> 目标：项目D（PE32 / x86，五节区商业软件）
> 覆盖：6.43.10.2 · 6.43.11.2 · 6.43.11.3 · 6.43.12.3 · 6.43.15.3
> 脱敏：产品名、公司名、注册表厂商键、样本哈希、签名主体信息均已移除；偏移、特征码、补丁字节、
> 常量与校验和算法全部保留。

本案例要解决的问题不是「怎么找到授权判定」，而是**找到之后怎么让结论活过下一次重编译**。
同一份工具从只支持 build 10，扩到五版本支持，中间被一次结构性问题打回过：老引擎把 18 个位点写成
硬编码绝对偏移，其中 3 个还是硬编码的 PE 头字段值。目标一升级，产物立刻「不是有效的 Win32
应用程序」。修复不是补几个新偏移，而是把定位方式换掉。

---

## 一、为什么偏移会失效

先看五版本的位移分布（代码段 / 数据段分开看）：

| 对比 | 代码段位移 | 数据段位移 |
| :--- | :--- | :--- |
| build 10 → build 11.2 | −384 ~ −896（跨度 512） | **+512** |
| build 11.2 → build 11.3 | −48 ~ −96（跨度 48） | 0 |
| build 11.3 → build 12.3 | **0**（位点完全重合） | 0 |
| build 11.3 → build 15.3 | +0x184 ~ +0x4F0（全部为正） | **+0x648** |

四点结论，每一点都否掉一种省事的做法：

1. **同一发布里代码段与数据段反向移动。** build 10 → 11.2，代码段整体后退 384–896 字节，
   数据段却前进 512 字节。所以「所有位点加同一个 delta」在结构上就不可能成立。
2. **位移不是常数。** 同一版本内，−384 到 −896 意味着不同函数之间的相对位置也在变，
   不是整体平移。这排除了「锚定一个位点再按相对距离推算其余」。
3. **有些版本是真正的零位移。** 11.3 与 12.3 的 15 个位点偏移完全相同，产物只差若干字节。
   把两版当两个独立目标维护，会白做一遍验证。
4. **跨度越大，硬编码越不可行。** build 15 的数据段位移（+0x648）是代码段位移上限（+0x4F0）的
   1.5 倍以上，任何基于「代码段位移」的推断在数据段上都会错。

顺带得到一条判断版本关系的经验：`.text` 的 VSize 增长 0x210、RawSize 增长 0x200，意味着其后所有
节区整体后移 0x200 —— 这是「较大重编译」的指纹；而位移只有 48–96 字节、位点几乎重合，说明是
「同布局微修订」。两者的维护成本差一个数量级。

## 二、双态特征码：把「位置」换成「形状」

定位方式换成 AOB 特征码后，还有第二个坑：**单版本特征码会把重定位指针吸进窗口**。

实测：一个位点在 build 11.2 上的特征码里含 `38 83 69 00`，在 build 11.3 上同一段变成
`30 83 69 00` —— 那是绝对指针的低位字节，节区一移位就变。14 个位点里 13 个命中，
唯一失效的那一个正是窗口里含指针的那个。这类失败最难排查，因为它表现为「大部分对，一个不对」。

修法不是把窗口开大，而是取**交集**：

- 对每个位点，在**所有支持的版本**上取共同字节区；
- 同时要求「原始态」与「已补丁态」两种形态**各自唯一**（1/1）；
- 相邻小于等于 4 字节的两个位点**合并成一条**，否则两条特征码互相包含，谁都不唯一。

实测效果：某位点三版本共同稳定区 50 字节 → 收窄到 46 字节；五版本共同稳定区把授权分支从
118 字节收到 24 字节、守护线程 F 从 80 收到 29、试用期最大值从 90 收到 13，总特征码体量
约 1,050 → 378 字节。**收窄不是妥协，是去掉随版本漂移的字节之后的必然结果。**

最终规模：14 个位点、755 字节特征码、平均 53.9 字节/点，最短 14 字节（看门狗关联函数）、
最长 118 字节（授权分支检测）。

### 双态的唯一性检查怎么用

- 原始态特征码在**纯净文件**里命中且仅命中 1 次；
- 补丁态特征码在**产物文件**里命中且仅命中 1 次；
- 两次命中的偏移差 == 被改字节数。

第三条是幂等性的来源：工具第二次运行时先看补丁态，命中就报「已打补丁」并拒绝写入，
而不是再打一遍。把这条省掉，重复执行会二次改写已经改过的字节。

### 一个必须记住的失败：模糊匹配只能产生候选

build 15 的数据段填充发生了漂移：位点 14 所在数据块**前方多出 2 个零填充字节**。

```
b11.3/b12.3 : … 6E 74 73 40 40 │ 00 00 00       │ 01 00 00 00 │ 01 00 00 00 │ 1E 00 00 00 …
b15.3       : … 6E 74 73 40 40 │ 00 00 00 00 00 │ 01 00 00 00 │ 01 00 00 00 │ 1E 00 00 00 …
                                      ↑ 多出 2 字节
```

「滑动汉明距离」在这种输入上会给出**距离 2** 的「极佳匹配」，而位置**早 2 字节**：
错在 `0x379546`（该处是 `01 00 00 00 01 00 00 00`），对在 `0x379524`
（`01 00 00 00 1E 00 00 00`）。距离 2 远低于「≤8 即命中」的判据，所以判据本身救不了你。

固化成四步流水线纪律：

1. 模糊匹配（汉明距离）**只产生候选**，永远不作为结论；
2. 候选必须经**期望字节精确匹配**；
3. 字节不符时改用**精确锚点搜索**（附近字符串常量 + 常量对）重新定位；
4. 最终必须经 **capstone 反汇编语义对照**确认与基线一致。

这也解释了为什么「汉明距离 ≤ 8 就算命中」不能当验收标准：在一个六兆字节的映像里，
距离 2 的巧合比你想的多得多。

## 三、COMDAT 折叠：两个字节完全相同的前 24 字节

「守护线程 D」与「看门狗关联函数」是两份不同的逻辑，但前 24 字节**逐字节相同**，且共享同一张
SEH 作用域表 —— 编译器把相同的函数序言折叠成了 COMDAT。

后果：这两个位点**不能依赖函数序言**做特征码。可用的办法只有一个：向前锚定到**前一个函数的尾部**，
用那 14 个字节唯一定位，然后按相对距离落到目标入口。

这条经验可以推广成一句话：**当一个「函数头特征」在两个不同函数上同时命中时，问题不在窗口大小，
而在提示词（锚点）选错了地方。**

## 四、PE 侧：三个必须动态求解的事实

老引擎把 PE 头也当成普通位点，写死了三个值：校验和、证书目录 RVA、证书目录长度。这三个值
每个版本都不同，是最典型的「把记忆当常量」。

新引擎改为运行时求解：

| 事实 | 求法 |
| :--- | :--- |
| 校验和字段偏移 | `e_lfanew = DWORD@0x3C`；`COFF = e_lfanew+4`；`Optional = COFF+20`；字段 = `Optional+0x40` |
| 证书目录 | `DataDirectory[4]`，位于 `Optional+0x60`（PE32）/ `Optional+0x70`（PE32+） |
| 映像末尾 | 节区表里 `RawPointer + RawSize` 的最大值 |
| 安全门 | 校验 MZ / PE 签名 / 节区边界 / `RawPointer+RawSize ≤ 文件长度` |

### 截断：一次真实事故

老做法是把文件**无条件截断**到 `6,189,056` 字节（build 10 的「减去 10,608 字节签名」结果）。
到 build 11 上，文件本身长了 512 字节，同一个硬编码长度砍掉的就不再只是签名，而是签名之后的
`.rsrc` / `.reloc` 一部分。结果：加载器直接拒绝，用户侧看到
`Win32Exception (0x80004005)` + Win32 `193`（`ERROR_BAD_EXE_FORMAT`）。

安全截断规则（三条同时成立才砍）：

1. 待砍区间**整体位于映像末尾之后**；
2. 区间长度 == 证书目录声明的 `Size`；
3. 砍之前已把 `DataDirectory[4]` 的 RVA 与 Size 清零。

### 校验和：一个没人校验、但必须写对的字段

标准 PE 校验和算法（16 位累加 → 折叠 → `(t + len) & 0xFFFFFFFF`，跳过校验和字段自身 4 字节）
对官方原版**100% 吻合**（三版均实测一致）。而上一代工具写进去的 `0x005F0BEA`，
用 4 种输入状态 × 16 种算法变体穷举**都无法复现** —— 说明它写入的是无效值，而程序照常运行。

结论有两层：

- 事实层：目标程序与 Windows **都不校验该字段**（`[observed]`，依据是无效值仍可运行）；
- 工程层：仍然要用标准算法重算。因为「没人校验」是当前实现的行为，不是接口契约；
  写一个无效值等于给后来者埋一个「为什么这个文件校验和算不出来」的坑。

## 五、版本感知备份：一次当场拦住事故的守卫

复现流程需要备份原文件，而备份文件名固定（`项目D.exe.BAK`）。多版本共存时，
一个 build 11 的备份放在那里，用户在 build 15 上做「一键还原」就会把 v15 的目录还原成 v11 的
可执行文件 —— 版本不匹配，且用户完全看不出发生了什么。

守卫做成四分支：

| 分支 | 条件 | 动作 |
| :--- | :--- | :--- |
| 1 | BAK 不存在 | 直接创建备份 |
| 2 | BAK 存在且版本相同 | 覆盖（同一版本的新备份） |
| 3 | BAK 存在、版本不同、当前文件**纯净** | 归档为 `项目D.exe.BAK.<旧版本>`，再写新备份 |
| 4 | BAK 存在、版本不同、当前文件**已含补丁** | 拒绝，要求人工确认 |

第 4 分支在回归测试里当场拦下一次真实误操作：测试脚本在已打补丁的目录上重跑，
守卫直接拒绝写入，而不是把「已打补丁的文件」当成新备份存档。

## 六、原子写入与差异白名单

写入流程三级回滚：

```
写 .rollback.tmp（原文件副本）
→ 写前 PE 终检（结构 + 全部位点签名仍唯一）
→ 写临时文件
→ 落盘后复读并重新解析 PE（能否被解析回来）
→ 任一步失败 → 从 .rollback.tmp 回滚
```

同时维护差异字节白名单 `HashSet<int> expected`：产物的每一个变化字节都必须在集合内，
否则判定「改到了不该改的地方」并回滚。这条检查抓的是特征码命中了错误位置 ——
只靠回读校验（比对目标位点）是发现不了的，因为错位命中的位点自己回读也是「成功」的。

## 七、流水线：八个脚本，一条判据链

上游工具的脚本按编号串起来，每个都可单独跑：

| 脚本 | 职责 |
| :--- | :--- |
| `00_scan_only.py` | 只扫描不写入：列出版本、节区、候选位点 |
| `01_extract_sfx.py` | 解出自定义 SFX 包内的主程序 |
| `02_locate_points.py` | 逐位点定位，输出候选与偏差 |
| `03_gen_signatures.py` | 生成双态特征码并验证唯一性 |
| `04_emit_cs_table.py` | 把特征码表生成为 C# 常量，避免手抄 |
| `05_verify_disasm.py` | capstone 语义对照（补丁前/后） |
| `06_e2e_validate.py` | 端到端：五版本各跑一遍，比对产物 |
| `07_splice_into_cs.py` | 把生成表拼回工程源文件 |
| `08_compare_versions.py` | 版本间差分，输出位移矩阵 |

统一判据：汉明距离 ≤ 8（仅候选）、双态唯一性 == 1、差异字节 ⊆ 白名单、校验和自洽。
依赖只有 `numpy` / `capstone` / `pefile`。

`04`、`07` 这两个「生成代码」的步骤值得单独说：手抄 14 条特征码和五版本偏移，
出错率接近必然，而且错法很隐蔽（少一个字节仍然能在某些版本上命中）。生成而非手写，
是这类工程的硬要求。

### 自定义 SFX 条目格式

主程序被打包在一个自定义自解压结构里，条目格式：

```
[0x00] DWORD   原始大小
[0x04] DWORD   压缩大小
[0x08] FILETIME × 3（创建/修改/访问）
[0x20] zlib 流（魔数 78 DA）
下一条 = 当前条 + 0x20 + 压缩大小
```

共 192 条目，主程序在条目 #5（压缩 2,602,327 字节 → 解压 6,200,176 字节）。
链式解包必须按 `next = cur + 0x20 + compressedSize` 走，不能用「顺序扫描 `78 DA`」——
压缩流内部可能出现同样的两字节。

## 八、节区一致率说明了什么

同一程序两版本逐节区对照（相同偏移区间内的字节一致率）：

| 节区 | 一致率 |
| :--- | :--- |
| `.rsrc` | 100% |
| `.data` | 95.43% |
| `.rdata` | 38.33% |
| `.reloc` | 35.45% |
| `.text` | 5.78% |

`.text` 只有 5.78%，已经说明「代码段整体位移」这件事本身不可信 —— 位移之外，代码内容也在变。
再补一个证据：`.text` 里 `E9 rel32` 的**跳转目标差值恒为 +0x210**，而指令本身的位置差值在
−896 ~ +64 之间浮动。这说明编译器**没有重写相对跳转**，只是把函数块按新顺序摆放了。

这条观察对定位有直接用处：一个函数的入口位移，不能用它内部某条相对跳转的位移去推断。

## 九、五版本时代收窄稳定区

扩到五版本后，共同稳定区自然收窄（每多一个版本，交集只会更小）：

| 位点 | 三版本 | 五版本 |
| :--- | :--- | :--- |
| 授权分支检测 | 118 B | 24 B |
| 守护线程 F | 80 B | 29 B |
| 试用期最大值 | 90 B | 13 B |
| 全表合计 | ~1,050 B | 378 B |

收窄到 13 字节仍然唯一，靠的是精确锚点 + 双态验证；这也说明「特征码必须够长」是个错觉，
**够不够只看唯一性，不看长度**。

## 十、六条可复用纪律

1. **三重确认**：模糊候选 → 精确字节 → 反汇编语义。少一层就会把「距离 2 的巧合」当成命中。
2. **数据段尤其危险**：填充漂移让代码段的方法在数据段上失效，且错位后字节「看起来也很像」。
3. **特征码必须基于全部支持版本重新生成**，不能拿单版本特征码去扩版本。
4. **引擎必须 fail-closed**：任一位点未解析或命中数 ≠ 1，零字节写入并报原因。
5. **扩版本要断言既有产物哈希零变化**：五版本引擎对 b10 / b11.2 / b11.3 的产物 SHA-256
   与上一代逐字节一致（零回归确认）。
6. **客户侧关闭自动更新**：内置更新器会在后台静默替换主程序，让「已打补丁」变成「版本又变了」
   而用户毫无感知。

## 十一、限制与未验证项

| 项 | 状态 |
| :--- | :--- |
| 校验和被官方当作无效值仍可运行 | `[observed]` 无效值与标准算法值均可加载；`[inferred]` 目标与系统均不校验该字段 |
| build 15 数据段位移规律 | `[observed]` +0x648；`[unverified]` 无统一公式，每次重编译需重新测量 |
| 注册表侧「无序列号 + 有姓名 = 终身授权」 | `[observed]` 在 b10 / b11.2 成立；`[observed]` 在 b11.3 被官方封堵（新增弹框分支） |
| 位点 15（注册对话框抑制）在 b10 / b11.2 | `[observed]` 特征码零命中，该版本无此逻辑，故设为可选位点 |
| 补丁对后续未测试版本的可移植性 | `[unverified]` 只验证到 build 15.3；更新器会继续引入新版本 |
| 上游样本的签名主体与哈希 | 已脱敏，不在本仓库；复现需自带合法样本 |

最后一行要说清：本仓库不含任何样本字节、签名证书或哈希，`docs/patch-table.md` 里的偏移是
教学值，作用是展示漂移的量级与特征码的方法，不是可以直接套用的表。
