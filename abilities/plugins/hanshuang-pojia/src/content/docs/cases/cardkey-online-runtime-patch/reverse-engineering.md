# 在线卡密客户端：全量加密壳下的免脱壳运行期旁路（CWE-602）

> 案例类型：Windows PE32 · 客户端授权流审计 · 免脱壳运行期内存补丁
> 目标：一款在线卡密授权的 Windows 桌面工具（明文 TCP 私有协议 + 本地裁决）
> 脱敏：产品名、公司名、真实端点与样本哈希均已移除；保留 RVA、字节序列、检测方法与复现步骤。

本案例的价值不在"绕过了一个卡密校验"，而在于**一个结论推翻了一整条默认路线**：目标被全量加密壳包裹，
但壳只做了反静态阅读，完全没有做反运行期改写。于是整条脱壳链路可以跳过。

## 一、目标画像

| 维度 | 判定 | 判据 |
| :--- | :--- | :--- |

## 二、保护壳分析：决定"能不能静态打补丁"

```
$ rabin2 -I <target>.exe
arch x86 / bits 32 / baddr 0x400000 / binsz 0x27F200
subsys Windows GUI / canary true / nx false / relocs false / signed false
```

| 观察项 | 值 | 研判 |
| :--- | :--- | :--- |
| 段表 | `ev3n`(VA 0x1000, vsize 0x2F5000, **rawsize 0**)、`yukP`(VA 0x2F6000, 0x27E000)、`.rsrc` | 段名为随机 4 字符；首段**磁盘上无数据**，运行期才被填充 |
| 入口点 | RVA `0x5724C0` | 落在 `yukP` 密文段尾部（外壳 stub） |
| 导入表 | 仅 **23 项**，位于 `.rsrc`，IAT 由外壳重建 | 其余 API 动态解析 |
| `DllCharacteristics` | **0x0000** | **无 ASLR、无 NX** |
| `.ev3n` 段权限 | `0xE0000080` = **RWX** | **运行期可直接改写代码** |
| 全文件熵 | 逐 64 KB 块 ≈ **7.997** | 除首块（含 PE 头）7.985 外，整段为密文/压缩体 |

### 2.1 关键结论：免脱壳路线成立

> **判据（本案例最重要的经验）**：只要满足
> ① `DllCharacteristics` 未置 `DYNAMIC_BASE`（无 ASLR → 地址固定），且
> ② 目标代码所在段为 `RWX`（或可 `VirtualProtectEx` 提升为可写），
> 就**不需要脱壳、不需要静态补丁**，直接用外部进程 `WriteProcessMemory` 改写运行期内存即可。

保护壳只做了"反静态阅读"（整体加密 + 随机段名 + EP 藏于密文段 + 导入表外置），
**完全没有做"反运行期改写"**（无段降权、无自校验、无 VM 虚拟化）。

这条判据是可以直接复用的：拿到任何加壳样本，先看这四项，再决定要不要花时间脱壳。

## 三、动态分析链路

### 3.1 内存转储与解密判据

`.ev3n` 段在运行期被解密为 RWX（`Process.enumerateRanges('r-x')` 显示
`base=0x401000 size=0x571000 prot=rwx`）。进程启动 1–2 秒后整段转储：

```javascript
Memory.readByteArray(ptr('0x401000'), 0x2F5000)   // → unpacked_ev3n.bin
```

**解密完成判据**（后续所有补丁器都靠它同步时序）：

```
读取 0x0041AB86 处 3 字节 == 55 8B EC   →  .ev3n 已解密
未解密时该处为随机密文
```

用"函数序言字节"当同步信号，比 `sleep 3` 稳得多：不同机器解密耗时不同，固定等待要么慢要么漏。

### 3.2 鉴权协议抓包

Hook `ws2_32!connect / send / recv`，一次登录即可拿到完整交互：

```
[CONNECT] <AUTH-SRV>:4001                      ← 明文 TCP，无 TLS
[SEND] len=723
       E8 03 00 00 | CB 02 00 00 | <715 字节密文>
       └ 命令号 1000 └ 载荷长度 715
[RECV] len=28
       01 02 04 02 05 04 | 1C 00 00 00 | <18 字节密文>
       └ 固定魔数(6B)      └ 总长 28
```

- 请求载荷为高熵密文，含卡密、机器码、版本号等；结合内置 MD5，推断为"卡密 + 机器码 + 盐 → 摘要"结构；
- **服务端下发的错误文案直接由客户端展示**：字符串「卡号不存在」在整个本地镜像中**检索不到**
  （GBK / UTF-16LE 双编码检索均为空）→ 该提示来自服务端响应解密后的内容。

第二点值得写进报告：它说明客户端对服务端文本**完全信任**，连文案都没有本地副本，
那么它对这个响应的处理也就只可能是一个布尔裁决。

### 3.3 `recv` returnAddress 回溯定位业务函数

Hook `ws2_32!recv`，读取 `this.returnAddress`，一次即可把调用链钉在业务函数上：

```
recv returnAddress = 0x0043ED44                 ← 位于 .ev3n 解密段内
准确回溯链：
  0x0043ED44  (recv 调用点，socket 类虚调用返回)
  → 0x004165AC
  → 0x00403067
  → 0x004015C8  (0x401549 内 call 0x40197E 之后)
  → 0x00401277  (登录事件处理函数内 call 0x401549 之后)
```

比全量反汇编快一个数量级：**先抓包 → 再用 returnAddress 定位收发函数 → 再上溯到事件处理函数**。
中间那几层不需要读懂，只需要确认真的是 `call` 关系。

### 3.4 裁决点定位

```asm
0x00401272  call 0x401549                  ; 授权包装：构造请求(0x401620) → 收发解析(0x40197E)
0x00401277  mov  dword ptr [ebp-0x10], eax
0x0040128A  mov  eax, dword ptr [ebp-0x10]
0x0040128D  mov  dword ptr [ebp-4], eax
0x00401290  cmp  dword ptr [ebp-4], 0      ; ★★ 客户端本地裁决
0x00401294  je   0x004014E7                ; ==0 → 失败（显示服务端下发的「卡号不存在」）
0x0040129A  ...                            ; !=0 → 成功分支
```

成功分支：

```asm
0x004014A0  mov  dword ptr [0x922C18], 1   ; 置"已授权"全局标志
0x004014AA  call 0x0041AB86                ; 授权心跳 / 二次复检
0x004014DA  call 0x447930                  ; 创建主功能窗口（易语言运行时）
```

心跳函数 `0x0041AB86` 内部：

```asm
0x0041AC3C  push 1 ; call 0x41AFA6         ; 复检请求 #1（返回值经 0x448360 转换为整数）
0x0041AC7D  cmp  dword ptr [ebp-0xC], 1
0x0041AC81  jge  0x0041ADBB                ; ★ 复检裁决 #1
0x0041ADC0  push 3 ; call 0x41AFA6         ; 复检请求 #2
0x0041AE01  cmp  dword ptr [ebp-0xC], 1
0x0041AE05  jge  0x0041AF3F                ; ★ 复检裁决 #2
```

注意结构：登录裁决之后紧接着一次心跳，心跳里还有两处同类裁决。**只改登录那一处**等于把
"通过"与"立刻被复检撤回"叠在一起 —— 这正是第五节对照实验 A 的现象。

## 四、易语言（EPL）函数识别三件套

> 易语言编译产物充斥"看似指令、实为混淆"的垃圾字节，先识别再分析能省大量时间。

| # | 特征 | 说明 |
| :--- | :--- | :--- |
| ① | 清单 `assemblyIdentity name="E.App"` | 全局唯一判据 |
| ② | 类型常量 `push 0x80000002 / 0x80000004 / 0x80000005 / 0x80000301` | 整数 / 文本 / 字节集 / 逻辑 |
| ③ | **函数头死代码混淆块** | 每个函数入口后紧跟 `pushal` → `mov eax,1` `mov eax,2` `mov eax,4` `mov eax,2` `mov eax,5` `mov eax,4` … → `popal` → `fninit`；这些 `mov` 是死代码，可直接跳过 |
| ④ | 运行时调度 | `mov ebx, 0x44xxxx; call 0x44749d`（支持库命令）；`mov eax, <cmd>; call 0x447497`（系统 API） |
| ⑤ | 栈帧约定 | `push ebp; mov ebp,esp; sub esp,N` + 连续 `mov [ebp-x],0` 批量清零 |

**类型敏感警告**：易语言函数返回值有类型（字节集 / 文本 / 整数）。
**补丁必须落在"比较 / 跳转"处，不要落在"返回值"处** —— 强行让一个返回字节集的函数返回整数，
会破坏后续的类型转换调用（本案例实验 C 即因此失败）。

## 五、补丁与对照实验

### 5.1 最终补丁（3 处 / 22 字节）

| # | 虚拟地址 | 原始字节 | 补丁字节 | 语义 |
| :--- | :--- | :--- | :--- | :--- |
| **P1** | `0x00401290` | `83 7D FC 00 0F 84 4D 02 00 00` | `C7 45 FC 01 00 00 00 90 90 90` | `cmp [ebp-4],0`+`je fail` → `mov dword [ebp-4],1`+`nop×3` |
| **P2** | `0x0041AC81` | `0F 8D 34 01 00 00` | `E9 35 01 00 00 90` | `jge 0x41ADBB` → `jmp 0x41ADBB` |
| **P3** | `0x0041AE05` | `0F 8D 34 01 00 00` | `E9 35 01 00 00 90` | `jge 0x41AF3F` → `jmp 0x41AF3F` |

### 5.2 对照实验矩阵（本案例最有价值的方法论）

| 实验 | 补丁内容 | 结果 | 教训 |
| :--- | :--- | :--- | :--- |
| 对照 | 无 | 任意卡密 → 「卡号不存在」 | 基线 |
| **A** | 仅 P1 | 主窗口创建失败，进程 **5 秒内自行退出** | 心跳复检失败会让客户端自杀 |
| **B** | P1 + 心跳函数整体 `ret`（`C3`） | 主窗口打开，**约 17 秒后访问违例崩溃** | 不要"跳过整个函数体"，会跳过必要初始化 → 延迟崩溃 |
| **C** | P1 + `0x41AFA6` 改 `mov eax,1; ret` | 5 秒退出 | 返回值类型不匹配：该函数返回字节集，后续 `0x448360` 类型转换失败 |
| **F ✅** | **P1 + P2 + P3** | 主窗口正常，任意卡密通过，**实测稳定 ≥ 320 秒** | 正解：改判条件跳转，而非跳过函数或篡改返回值 |

> 两条硬规则：
> 1. 授权旁路必须做 A/B/C 对照实验才能确定"最小稳定补丁集"；
> 2. 遇"改判点"优先改条件跳转（`jge`→`jmp`），不要改返回值、不要整体 `ret`。

矩阵本身也有结构性价值：A 证明"复检存在"，B 证明"函数体不可整体跳过"，C 证明"返回类型受约束"。
三条否证合起来，才使 F 的"只改条件跳转"从猜测变成结论。

### 5.3 落点时机

`.ev3n` 段磁盘 `rawsize = 0` → 文件上不存在这些指令，绝对不能改文件。
必须：`启动进程 → 轮询 0x41AB86 是否为 55 8B EC → 命中后写入 P1/P2/P3`。

## 六、CWE-602 根因分析

| # | 根因 | CWE | 说明 |
| :--- | :--- | :--- | :--- |
| 1 | 服务端只回传布尔信号，是否放行由客户端本地 `cmp/je` 决定 | **CWE-602** | 核心缺陷；改写 10 字节即获完整授权 |
| 2 | 授权心跳复检同样在客户端本地裁决，失败仅导致客户端自杀（非服务端吊销） | CWE-602 / CWE-693 | 把"断权"能力交给了客户端 |
| 3 | 鉴权通道为明文 TCP，无 TLS、无传输层完整性 | CWE-319 | 可观测 / 重放 / 篡改；可构造鉴权中继 |
| 4 | 卡号与第三方 API 凭据明文落盘 | CWE-522 | 同机任意进程可读取 |
| 5 | 保护壳无 ASLR / 无 NX / 代码段 RWX / 无自校验 | CWE-693 | 防护机制失效 |

第 1 条与第 5 条的组合尤其值得注意：单独看，一条是"客户端裁决"，另一条是"壳配置不当"；
合起来才解释了为什么这个目标的旁路成本只有 22 字节。

## 七、纵深防御整改建议

| 层级 | 措施 |
| :--- | :--- |
| **服务端权威（根本解）** | 服务端下发签名授权凭据（HMAC-SHA256 / JWT），客户端只验签不决策；核心功能（文书渲染 / 素材 / 导出）服务端化，或以一次性 nonce 令牌换取；卡密绑定机器码 + 并发控制；心跳失败由服务端吊销凭据，而非客户端自杀 |
| 传输层 | 全链路 TLS 1.2+ 与证书校验（SSL Pinning）；请求加 `timestamp + nonce + sign` 防重放；服务端下发文案白名单化 |
| 客户端 | 开启 `DYNAMIC_BASE \| NX_COMPAT`；解包完成后调用 `VirtualProtect` 把代码段降权为 RX；授权函数下沉 Native + 代码虚拟化 + 完整性自校验（篡改即逻辑错乱而非退出）；集成 Anti-Debug / Anti-Hook |
| 数据 | 卡号与第三方 API 凭据禁止明文落盘（DPAPI / AES-GCM）；第三方 API 凭据改由自家服务端代理调用 |
| 工程卫生 | 清理镜像中残留的保护方案调试字符串与 PDB 路径 |

## 八、方法论沉淀（可复用）

1. **外壳 ≠ 保护**：先查 `DllCharacteristics` 与段权限。无 ASLR + RWX 段 = 免脱壳内存补丁路线成立，
   可跳过整个脱壳环节。
2. **抓包优先于纯静态**：`ws2_32!send/recv` hook 成本极低，能立刻确认"是否联网鉴权"并确定协议形态。
3. **`returnAddress` 回溯**：在 `recv`/`send` 上读 `this.returnAddress`，一次定位业务函数。
4. **易语言识别三件套**：清单 `E.App` + 类型常量 `0x8000000x` + 函数头 `pushal/mov eax,1..6/popal` 死代码块。
5. **补丁必须做对照实验**：A/B/C/F 四组才确定最小稳定补丁集。
6. **不要迷信"函数整体 ret"**，也不要改返回值：优先改判条件跳转。
7. **时序同步**：用"函数入口字节 == 55 8B EC"作为外壳解密完成判据，比定时 `sleep` 稳。
8. **GUI 目标必须脱离调用方控制台**：`CreateProcess` 加 `CREATE_DETACHED_PROCESS`，否则批处理退出时
   控制台关闭会触发 `CTRL_CLOSE_EVENT`，把目标一起杀掉。

## 九、限制与未验证项

| 项 | 状态 |
| :--- | :--- |
| 服务端响应密文的完整算法还原 | `[unverified]` 仅确认非签名结构（本地无验签表），未还原密钥 |
| 卡密的机器码绑定强度 | `[inferred]` 请求含 715 字节密文与内置 MD5，推断存在机器码参与，未逐字段验证 |
| 伪造服务端响应实现离线激活 | `[unverified]` 未尝试；理论上因本地无验签而可行 |
| 服务端下发文案的完整清单 | `[observed]` 仅捕获到「卡号不存在」一条 |

把这三行 `[unverified]` 留在报告里，是这类审计可信度的一部分：
"改写 10 字节即获完整授权"是 `[observed]`，"理论上可以伪造服务端"只是 `[inferred]`。
