# Payload chain — the shape of an injection job

`cases/payload-chain` 把「一段代码进到目标进程」拆成三段，并把每个目标相关数值留成
具名占位符。这里解释**为什么这样拆**、每一段用什么证据成立或否证、以及这条链在报告里
应该怎么写才不会把「生成成功」说成「目标可被接上」。

## 三段的分界

| stage | 输入 | 产出 | 判据 |
|---|---|---|---|
| 1 carrier | 要执行的东西 | 自描述 blob：`magic(4) version(2) name_len(2) body_len(4) name body sha256(32)` | 解析时能自校验；改一字节即报错 |
| 2 mapper | blob | 目标进程里的一块可执行内存 + 一次跳转 | 映射地址就是 `TARGET_RVA`，不是「某个地方」 |
| 3 injector | blob + 目标 | 写入、改入口、回滚 | 补丁点是 `偏移 / 原始字节 / 补丁字节 / 回滚` 四元组 |

三段分开的价值在于**每一段都能单独被否证**：blob 改一字节能测；映射失败有错误码；
补丁是否落在预期位置有原始字节可比。合成一个脚本之后，失败只剩「没生效」三个字，
而这句话没法写进报告的证据段。

## 为什么占位符必须具名

上游等价脚本把地址写成常量。换目标后三种静默错误会同时出现：

1. 写到错偏移 —— 目标里那块内存从未被执行；
2. 补丁打在另一处 —— 调用链看起来改了，实际分支没变；
3. 回滚恢复错字节 —— 下一次比对基线时把「本来没改」当成「已经还原」。

三者都不抛异常，只产出一个看起来成立的结论。具名占位符把「还缺几个数」变成可数的
东西：`chain.md` 里列了五个，填了几个一目了然。

## 五个占位符从哪来

| 占位符 | 来源 | 拿不到时的替代 |
|---|---|---|
| `TARGET_RVA` | `list_code_symbols` 的导出地址 + 节区基址 | 用 `disasm` 从入口线性扫到目标调用点 |
| `TARGET_FILE_OFFSET` | 同一个 RVA 减去节区 `VirtualAddress` 再加 `PointerToRawData` | `disassemble_range` 的偏移直接给文件位置 |
| `ORIGINAL_BYTES` | 改动前从样本读那 N 个字节 | 无替代：没有原始字节就没有回滚依据 |
| `PATCH_BYTES` | 目标架构的指令编码（例如 `ret` = `C3`、`xor eax,eax;ret` = `31 C0 C3`） | 无替代：编不出来就说明还没定位到点 |
| `SLACK_CAVE` | `triage_binary` 的节区 slack（对齐填充） | 找 `.rsrc` 之后的可写节，但那会改变节属性，要单独记 |

两个「无替代」是有意的：它们分别是**回滚依据**与**改动本身**。缺任何一个，这次改动就
不该落地。

## 三段各自的失败形态

**carrier**：`parse_blob` 会拒绝坏 magic、截断、以及 sha256 不符。最常见的是第三种 ——
生成之后有人用编辑器改了 blob，长度没变但内容变了。

**mapper**：本机跑 `loader.py` 只能验「blob 结构与校验」，不能验「能分配并能跳」。后者
需要目标进程，属于第 3 段的动态验证。这一点写清楚，是为了避免把「loader 跑通了」
当成「注入成功」。

**injector**：只打印五步计划。计划里第 5 步固定是回滚，且顺序不可调 —— 把回滚放前面
等于允许「改完发现问题但已经覆盖了原字节」。

## 报告里怎么写

三段对应三段证据，分开写：

```
## 链条
- carrier: payload.bin, sha256 <…>, body <n> bytes（自校验通过）
- mapper: TARGET_RVA=0x…, SLACK_CAVE=0x…（来源：list_code_symbols / triage_binary）
- injector: TARGET_FILE_OFFSET=0x…, ORIGINAL_BYTES=<…>, PATCH_BYTES=<…>

## 验证
- 改动前：<命令> → 退出码 <n>，行为 <…>
- 改动后：<命令> → 退出码 <n>，行为 <…>
- 回滚后：sha256 与改动前一致（<…>）

## 结论边界
- 已证明：链条在本机可生成、可自校验、补丁点可定位
- 未证明：目标接受这次改动（需要第 3 段的动态运行）
```

最后一段是这类工作最容易被省略、也最容易被读者误读的地方。

## 常见误用

- **把生成的 blob 当载荷**：body 是惰性的（win 全零 / linux `nop` + `ret`）。它证明链条接得通，
  不证明任何目标能被接上；
- **跳过 loader 的本机运行**：那一步只花一秒，能拦住「blob 被改过」这个最常见错误；
- **省略回滚**：一次失败的注入留下半改状态，下一次分析会把它当成基线；
- **把五个占位符中的一个「估」出来**：估出来的数值不会报错，只会让整条链静默偏一格。

## 一条自我约束

这个包不提供可执行载荷，也不提供任何目标的具体偏移。它的产出是**检查表 + 骨架**：
缺哪几个数、每个数从哪一步拿、拿到之后怎么写进报告、以及哪些结论必须留到动态阶段。

## 与单点补丁的分水岭

单点补丁只回答「这一处能不能改」；链条要回答四个额外问题，每一个都会在真目标上暴露：

1. **装载位置够不够**：补丁字节只有几个，放进任意空隙都行；blob 可能上百字节，需要一段
   真正连续、可执行且不被其它代码引用的空间。`SLACK_CAVE` 就是为了把这个搜索前置成一次
   可核对的值，而不是在执行时才去找。
2. **搬动后谁来调用**：改入口只是第一步。如果目标在启动后会把入口重新指回去，改动就只在
   第一次有效。这一点必须在动态阶段观察，静态只能说明补丁落了。
3. **写完之后谁验签**：带签名的二进制改动后签名失效。如果进程启动时验签，链条会在加载阶段
   被断，而这一点在静态三阶段里完全看不到 —— 这是本包把「验签」单独列出来的原因。
4. **失败时留下什么**：链条多段，任何一段失败都会留下半完成状态。计划里的回滚步骤是为了
   让「失败」也回到一个可重复的基线，而不是一个只能重装的现场。

把这四个问题写进报告，比多贴几段反汇编有用：它们决定了这份评估是可复现的，还是只能作为
一次性的观察。这也是包里把注入器写成「五步计划」而不是「一段脚本」的原因 ——
计划能被审阅，脚本只能被运行。

## 再看一眼上游

上游 `Tool/cases/项目A` 之所以值得读，不是因为它把链写全了，而是因为它把**同一件事的
四份产物**摆在一起：构造载荷的 Python、映射的 Python、注入的 Python、以及宿主侧那份 C。
四份放在一起才能看出「哪一段的输出是下一段的输入」。

它不值得抄的地方同样明显：地址是常量、没有自查、没有回滚、OCR 类辅助脚本八个只差参数。
本包的做法是**留形状、去常量、加自查**：`payload.bin` 带 sha256 自校验，
`loader.py` 先校验再映射，`injector.py` 把回滚固定在第五步，五个占位符一个都不预设。

这条差异可以直接用一句话检验：把生成的四个文件交给一个没参与过这次工作的人，
他能不能只靠文件本身说出「还缺哪几个数、每个数从哪一步拿」。能，说明形状是对的；
不能，说明还有常量藏在里面。
