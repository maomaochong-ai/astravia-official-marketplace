# 授权状态机：试用横幅不是开关（项目A，28.40.0100）

> 案例类型：Windows x64 原生桌面程序 · 纯本地授权（CWE-602） · 版本演进 28.30 → 28.40
> 脱敏：产品名、公司名、安装路径、样本哈希与密钥均已移除或替换；RVA、指令字节、补丁表、注册码结构、判据矩阵完整保留。

这个案例真正的价值，不是"打通了一个注册"，而是**一次错误的测绘持续了三个版本才被推翻**。
前几轮把"关于"框里显示的许可等级当成激活判据，于是做出了五处补丁，UI 上样样正常，
程序行为一点没变。直到找到那个只有一处写入的 16 位状态字，整件事才闭合。

## 一、目标画像

| 维度 | 判定 | 判据 |
| :--- | :--- | :--- |
| 平台 | Windows x64（PE32+） | ImageBase `0x140000000`，镜像 37.5 MB |
| 运行时 | twinBASIC 982 重编译 | 窗口类 `ThunderRT6FormDC`；WideString 即 BSTR |
| 数字签名 | 无 | 属性页签名栏为空，`WinVerifyTrust` 无有效签名 |
| 网络能力 | **零** | 导入表仅 7 个系统库，无 socket、无 HTTP、无加密提供者 |
| 配置 | `%APPDATA%\<产品>\<产品>.ini` | UTF-16 LE **带 BOM**，含 `[Register]` 段的 `Name` / `Code` / `dc` |
| 授权模型 | 纯本地自治判定 | 无服务端、无签名票据、无心跳 |

导入表这一行是整份报告的基准线：**这个产品在技术上不可能做在线校验**。
既然没有服务端，那么"是否已购买""许可类型""试用天数"全部只能来自进程内部的内存变量。
这不是一个实现缺陷，而是一个架构选择，后面所有结论都由它派生。

## 二、五个"看起来像答案"的全局变量

初步扫描时，宿主里有五个候选，每一个都能被合理地说成"授权开关"：

| 全局 | RVA（28.40） | 类型 | 语义 |
| :--- | :--- | :--- | :--- |
| 许可等级 | `0x22FD724` | int | `0` 试用；`1..5` 对应 `xy01..xy05`；`5` 为终身 |
| 版本覆盖标志 | `0x230170C` | int | `1` 覆盖当前版本；`2` 不覆盖升级 |
| **授权状态字** | `0x230CDEA` | word | `0xFFFF` 试用；`0x0000` 已激活 |
| 许可证名 WideString | `0x2235A88` | 指针 | "关于"框显示的用户名 |
| 许可证码 WideString ×2 | `0x2281C70` / `0x21FDDE0` | 指针 | 两处副本，均用于显示 |

区分它们的方法不是名字，而是**引用计数**：许可等级被 18 处读取，版本覆盖标志被 33 处读取，
而授权状态字只有**一处写入**、其余读取全部落在功能开放判定上。

> 读取者多的是"显示层"，写入者少的是"状态机"。这条经验在本案上花了三个版本才被接受。

## 三、写入块：整个门就在这五行里

```
0x670CA4   mov   ax, word [rsp+0x308]      ; 注册加载器返回值：-1 成功，0 失败
0x670CB1   not   eax                       ; ★ -1 → 0（已激活）；0 → 0xFFFF（试用）
0x670CB9   lea   rax, [rip+0x1C9C12B]      ; → 0x230CDEA
0x670CBF   mov   word [rax], dx
```

`not` 是整个门。加载器沿用 BASIC 家族的习惯：成功返回 `-1` 而不是 `0`，
于是 `not -1 = 0` 表示已激活，`not 0 = 0xFFFF` 表示试用。把这个语义读出来的那一刻，
"为什么改标题栏没用"就同时有了答案——标题栏读的是状态字派生出来的文案。

除主路径外还有两条降级写入，各自有独立触发条件：

| 站点 | 28.40 RVA | 28.30 RVA | 触发条件 |
| :--- | :--- | :--- | :--- |
| 前置跳过 | `0x670BFF` | `0x66FBB8` | 某全局标志的第 `0x10` 位为 0，注册加载器根本没被调用 |
| 空注册信息 | `0x670CD5` | `0x66FC8E` | `[Register]` 的 `Name` 或 `Code` 长度为非正 |

两处都写立即数 `66 C7 00 FF FF`（`mov word [rax], 0xFFFF`）。
只补主路径会在"另一条启动分支"上被悄悄改回试用，这类反弹最难查，因为它在单次会话里看不出来。

## 四、最终补丁集（4 处）

| # | 28.40 RVA | 原始 Hex | 补丁 Hex | 语义 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | `0x670CB1` | `F7 D0` | `31 C0` | `not eax` → `xor eax,eax`，状态字恒 `0x0000` |
| 2 | `0x670BFF` | `66 C7 00 FF FF` | `66 C7 00 00 00` | 前置跳过分支改写"已激活" |
| 3 | `0x670CD5` | `66 C7 00 FF FF` | `66 C7 00 00 00` | 空注册信息分支同上 |
| 4 | `0x15E2A47` | `44 8B 5C 24 7C` | `E9 40 00 00 00` | "关于"框许可等级分支无条件跳入终身档 |

28.30.2600 的同源点位为 `0x66FC6A` / `0x66FBB8` / `0x66FC8E` / `0x15CEA84`；
三处指令序列完全同构，偏移差恒为 `-0x1039`。这个差值是构建产物，不是规律，换个版本必须重新定位。

### 4.1 被取代的历史补丁（反面教材）

| 28.40 RVA | 原始 Hex | 补丁 Hex | 改了什么 |
| :--- | :--- | :--- | :--- |
| `0x859AE7` | `0F 84 37 06 00 00` | `E9 38 06 00 00 90` | 短路标题栏试用文案 |

五处补丁，行为零变化。这张表在报告里比任何论述都有力：
它证明显示层全局不是门，也说明"看起来成功了"是这类审计最贵的陷阱。

## 五、弱校验：四字符前缀决定许可等级

注册加载器入口 RVA `0x66A600`，签名约 `func(Name, Code)`。
字面量池在 `.data` 的 `0x21B3A44`（`xy01 xy02 xy03 xy04 xy05`），
逐代次调用 `CompareStringXxx(..., 0x30001, ...)`，其中 `0x30001` 是
`NORM_IGNORECASE | NORM_KANATYPE | NORM_WIDTH`。命中即写等级：

| 命中段 | 写入等级 |
| :--- | :--- |
| `0x66A750` | 1 |
| `0x66A7CD` | 2 |
| `0x66A84D` | 3 |
| `0x66A8BC` | 4 |
| `0x66A93C` | 5 |

无签名、无校验和、无 HMAC、无网络回执。四个字符决定等级——这解释了两件事：
为什么等级可以被本地"造"出来，以及为什么造出来并不等于激活。

## 六、注册码结构（实测 28.40.0100）

```
xy05-<用户数>-<4hex>×5-<重复段>-<主次版本>
xy05-0100-D0F0-3970-185A-1963-A172-D0F0-28.40
```

- 第 1 段 `xy05` → 等级 5；
- 第 2 段 4 位十六进制 = 用户数（`0100` → 1 用户；缺失或非十六进制 → 0）；
- 第 3–7 段自由填充；
- 第 8 段重复首个填充段，贴合宿主自身编码器的输出结构；
- 第 9 段必须与宿主主次版本一致（`28.40` / `28.30`）——版本覆盖判定读的就是这一段。

关于框原生呈现（未打第 4 处补丁时按等级分支）：
`Lifetime License Enterprise` / 名字 / 密钥 / `1 用户授权 (不可转让)` / `适用于所有未来版本`。
注意"1 用户"这一行来自第 2 段的字面解析，**不是**校验结果，这正是加固建议里
"权益内容必须进签名载荷"的直接依据。

## 七、注入时序：堆损坏的真因不是跨堆

代理 DLL 路线第一次尝试就撞上 `0xC0000374`（`STATUS_HEAP_CORRUPTION`）。
当时的判断是"跨堆分配 BSTR 必崩"，这个判断是错的。

逐步排除后的结论：**根因是写入时机**。在 `DllMain` 阶段写入字符串全局时，宿主还没完成授权初始化，
随后它用自己的堆管理器覆盖/释放了那块内存，于是崩溃点在稍后的一次 `SysFreeString`。

正解三条：

1. 等宿主稳定（约 **3 秒**），用可验证的方式确认，而不是 `sleep`；
2. 用**宿主进程自身 IAT 槽位**的 `OLEAUT32!SysAllocString`（RVA `0x2675408`）分配 BSTR，
   指针归属 OLE 堆，宿主后续释放安全；
3. **有限次重试：仅 4 次、间隔 2 秒**。无休止轮询会让堆膨胀，实测 20 秒即 `0xC0000005`。

这三条合起来是一条通用纪律：**写别人的堆，就要用别人的分配器，并且在别人初始化之后再写。**

## 八、三重客观判据

| 场景 | 许可等级 `0x22FD724` | 覆盖标志 `0x230170C` | 状态字 `0x230CDEA` | 标题栏 |
| :--- | :--- | :--- | :--- | :--- |
| 官方原版（`[Register]` 空） | `0` | `1` | `0xFFFF` 试用 | `### 30 - 天试用版本 - 第 1 天 ###` |
| 仅填 `[Register]` | `5` | `1` | `0xFFFF` 试用 | 同上，**未激活** |
| 补丁 1–3 | `5` | `1` | `0x0000` 已激活 | 纯净无试用标记 |
| 补丁 1–4 全量 | `5` | `1` | `0x0000` 已激活 | 纯净 + 关于框终身档 |

第二行是本案最重要的一格：注册信息齐全、等级已到顶，状态字仍然是 `0xFFFF`。
任何在第二行就停下的方法，测的都是错的变量。

## 九、双向生命周期

| 阶段 | 观察 | 证据等级 |
| :--- | :--- | :--- |
| 官方试用态 | 状态字 `0xFFFF`，标题栏显示试用天数 | `[observed]` |
| 部署代理 DLL | 写入成功率 4/4，回读一致 | `[observed]` |
| 已激活态 | 状态字 `0x0000`，30 秒稳定观察无回退 | `[observed]` |
| 还原 | 删除代理 DLL，重启 | `[observed]` |
| 回落试用态 | 状态字回到 `0xFFFF`，配置目录零残留 | `[observed]` |

"还原后回落"这一格是区分"内存内变更"与"永久修改"的唯一证据，也是最常被跳过的一格。
主机本体与签名在全程保持原样，这是选择代理 DLL 而非改文件的直接收益：回滚只需删一个文件。

| 项 | 状态 |

| 28.30 的偏移差 `-0x1039` 是否适用于其它点位 | `[unverified]` 仅在这三处同构站点观测到，不能外推 |
| 第 4 处补丁对功能开放的实际影响 | `[inferred]` 只确认"关于"框呈现变化，功能开放由状态字驱动 |
| 后续版本是否对注册块加签名 | `[unverified]` 若加了，状态字不再离答案只有四个字节 |
| 用户数与有效期是否参与任何判定 | `[inferred]` 当前只见于显示，未见判定分支引用 |
| 上游曾引用的"手动验证指南"文档 | `[unverified]` 归档中实际不存在，未纳入本案例 |

把这些留在正文里，是因为这类审计里最容易被夸大的正是"影响面"：
能证明的是"状态字被改写并维持"，不能证明的是"所有付费功能都已开放"。
