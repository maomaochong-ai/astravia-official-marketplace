# 第三方破解件载荷解剖与加固规范（项目A，28.30 参考样本）

> 案例类型：代理 DLL 载荷逆向 · 供应链风险与 IOC · 纵深防御设计
> 脱敏：产品名、端点、样本哈希、内部署名均已移除；偏移、补丁字节、检测判据完整保留。

同一个目标，还有第二条叙事线：**别人已经做过一遍，而且做错了**。
分析这份第三方破解件不是为了复用它，而是因为它把"错误的测绘方法会留下什么痕迹"
完整地展示了出来——以及它顺手暴露了宿主有哪几个真正可被利用的面。

---

## 一、样本整体形态

| 观察项 | 值 |
| :--- | :--- |
| 文件类型 | x64 DLL，`version.dll`（Windows 版本查询库的系统同名文件） |
| 文件大小 | 55,192 字节 |
| 对照 | 与某 Windows 11 24H2 系统原件**同为 55,192 字节** |
| 差异 | 仅 11 段、共 562 字节 |
| 差异位置 | 全部集中在 `fothk` 节（RVA `0x4000–0x5000`，正常 PE 中该节为 `0xCC` 填充的延迟加载辅助节）+ `DllMain` 一处 2 字节的调用目标替换 |

"与系统同名文件尺寸完全一致、差异只有 562 字节"这个组合本身就是最强的 IOC：
它不是自己编译的转发器，而是**拿系统原件改的**。所以它的导出表、导入表、
甚至版本资源都是真的，只有那一节异常。

---

## 二、入口改造：让 `DllMain` 先跑自己的代码

```
文件偏移 0x1449：
  原版  E8 43 03 00 00     call RVA 0x1791（原始初始化）
  破解  E8 AF 2C 00 00     call RVA 0x40FD（注入代码）
```

注入代码内部再 `call 0x1785` 回调原始初始化，于是"原始行为"被完整保留，
宿主不会因为缺少版本 API 而异常退出。这是这类加载器最省事的做法：
**只改一个 call 目标，不动其它任何东西。**

---

## 三、载荷主体：`fn_4100`

```
mov rax, gs:[0x60]          ; PEB
mov rbx, [rax+0x10]         ; ImageBaseAddress —— 拿到宿主基址
LoadLibraryW("kernel32.dll")
GetProcAddress(hK32, "VirtualProtect")
×4  VirtualProtect(PAGE_EXECUTE_READWRITE) + rep movsb
```

四段覆写，全部落在宿主的授权模块与显示路径上：

| 目标 RVA | 长度 | 写入内容 | 意图 |
| :--- | :--- | :--- | :--- |
| `0x66FC95` | 34 字节 | `66 C7 05 …` 三连写 + `E9 F0 00 00 00` | 把授权预检字 `0x22F434A` 置 0、版本覆盖 `0x22E8D44` 置 0、许可等级 `0x22E4D5C` 置 5，再跳过后面 0xF0 字节的版本覆盖校验块 |
| `0x66DB7B` | 5 字节 | `66 B8 FF FF 90` | `mov ax,0xFFFF; nop`，让校验返回值恒成立 |
| `0x8E75ED` | 6 字节 | `FF 25 15 6E D7 01` | `jmp qword [<宿主>+0x265E408]`，即 `OLEAUT32!SysAllocString`（实测 `OLEAUT32.dll+0x10CF0`） |
| `0x8E6D83` | 14 字节 | `FF 25 00 00 00 00` + `qword 0x180004300` | 绝对跳转 → `fn_4300` |

`fn_4300` 接着做真正的"伪造"：

```
mov rsi, [<宿主>+0x265E408]      ; 宿主自己的 SysAllocString
"VIPUesr"                        → 0x221CEF8（许可证名）
"xy01-Lifetime-License-Pro-vipuser" → 0x22694A0 与 0x21E52F0（两份码副本）
再分配 10 字节附加块
```

它的巧妙之处在于**借宿主的分配器写宿主的字符串**：因为 Delphi/twinBASIC 的 `WideString`
底层就是 `BSTR`，用宿主自己的 `SysAllocString` 分配，宿主后续 `SysFreeString` 不会崩。
这与本项目自己踩过的堆损坏坑是同一个道理——只是它先踩对了。

载荷明文串偏移（教学值）：`0x4500` `kernel32.dll`、`0x4530` `VirtualProtect`、
`0x4550` 字节序列、`0x4570` 许可证名占位、`0x4590` 伪造的码串。

---

## 四、它错在哪：版本适配性缺陷

四个覆写偏移**只对 28.30 成立**。在 28.40 上：

- 同偏移落在 `add rsp,0x28` 指令中部，错位 1–2 字节；
- `0x66FC95` 处 34 字节的覆盖会破坏 `0x66A000–0x66D000` 整段授权模块。

即便在 28.30 上也不稳定，多次出现 `0xC0000374`。

> **要注意归因**：这些是破解件自身的缺陷，不是宿主漏洞的特性。
> 报告里如果写成"目标不稳定"，就把攻击者的工程质量问题错记成了产品缺陷。

这也是为什么本项目最终没有沿用它的方法，而是回到状态机：**抄偏移就是抄别人的运气**。

## 五、检测判据（可直接落成规则）

| 判据 | 说明 |
| :--- | :--- |
| `fothk` 节内容非 `0xCC` 填充 | 正常 PE 的该节应全为 `0xCC`；有真实代码即高度可疑 |
| 与系统同名 DLL 尺寸一致但哈希不同 | 差值小于 1 KB 时尤其可疑 |
| `DllMain` 的 call 目标不在 `.text` 常规区间 | 本例指向 `0x40FD`（`fothk` 内） |
| 载荷串组合命中 | `kernel32.dll` + `VirtualProtect` + 一个 `xy0N-` 前缀串 + 一个非产品用户名 |
| `gs:[0x60]` 取 PEB 的指令出现在 DLL 的加载路径上 | 代理 DLL 极少需要自取基址 |

YARA 层面的最小组合：`{ E8 ?? ?? ?? ?? }` 于入口附近 + `gs:[0x60]` + `VirtualProtect` 字符串 +
`xy0` 前缀字面量，同时命中即可判定同源。样本哈希在归档中记作 `<实测哈希>`，
不作为规则的一部分——它只对那一个样本有效。

## 六、它暴露了宿主的四个面

这份载荷之所以能成，不是因为作者高明，而是因为宿主把四件事都留在了默认状态：

1. **DLL 搜索序**：没有 `SetDefaultDllDirectories`，程序目录优先级最高，
   于是同目录放一个 `version.dll` 就会被加载。
2. **`VirtualProtect` 可用**：`.text` 原本 `PAGE_EXECUTE_READ`，可以被任何同进程代码改成
   `PAGE_EXECUTE_READWRITE`，因为没启用 `ProcessDynamicCodePolicy`。
3. **关键函数头部无完整性校验**：`0x8E6D83`、`0x8E75ED` 这类核心函数没有前导字节校验、
   没有 CFG，14 字节的 `FF 25` 跳板就能整体劫持。
4. **单点返回值判定**：`0x66DB7B` 返回 `0xFFFF` 即视为有效，没有非对称签名做深度关联。

这四条正好对应加固规范的四个层级。

## 七、三层纵深防御

### Level 1 启动加载防护

```c
SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_SYSTEM32 | LOAD_LIBRARY_SEARCH_USER_DIRS);
```

配合 Authenticode 校验与强完整性检查：加载任何同目录 DLL 前先验签，
未签名或签名主体不符即拒绝。这一步直接消灭本例的投递方式。

### Level 2 运行时内核缓解

```c
PROCESS_MITIGATION_DYNAMIC_CODE_POLICY policy = {0};
policy.ProhibitDynamicCode = 1;
SetProcessMitigationPolicy(ProcessDynamicCodePolicy, &policy, sizeof(policy));
```

启用后，任何把 `.text` 提升为可写可执行的操作都会失败，
`GetLastError()` 返回 `ERROR_DYNAMIC_CODE_BLOCKED`。
再叠加 `SignaturePolicy`，阻止未签名二进制被映射进进程。

### Level 3 内存完整性主动巡检

- 前 16 字节探测：`0xE9`（JMP rel32）、`0xFF 0x25`（JMP [rip+disp32]）、`0xCC`（INT 3）、
  `0xEB`（JMP rel8）；
- `VirtualQuery` 校验关键段保护属性应为 `PAGE_EXECUTE_READ`（`0x20`），
  出现 `0x40`（RWX）即判定被改；
- 核心代码块哈希与只读常量对比，周期执行。

### 鉴权令牌的重新设计

废弃明文 BSTR 松散结构，改为对 `(LicenseeName, Key, Scope, Expiration)` 做集中签名
（ECDSA / Ed25519 / RSA-PSS）。关于框只接受验签通过的数据，签名不符时强制显示未激活。
这样即使有人写进了字符串全局，显示的也是"未激活"，而不是伪造的"终身授权"。

## 八、验证矩阵（加固是否真的生效）

| 编号 | 操作 | 期望结果 |
| :--- | :--- | :--- |
| V-01 | 主程序目录投递同名 `version.dll` | `GetModuleFileName(hModule)` 恒为系统路径 |
| V-02 | 调用 `VirtualProtect(..., PAGE_EXECUTE_READWRITE)` | 返回 `FALSE`，`GetLastError() = ERROR_DYNAMIC_CODE_BLOCKED` |
| V-03 | 注入 `FF 25` 跳板到关键函数 | 自检返回 `TAMPER_DETECTED` 并安全退出 |

三条都能过，才叫"加固完成"；只过 V-01 只说明搜索序改了。

---

## 九、处置建议

1. 立即删除安装目录下的同名代理 DLL；
2. 复核 `%APPDATA%\<产品>\` 下的 ini 与自动备份目录，确认 `[Register]` 段未被写入伪造值；
3. 生产环境升级到已修复授权模型的版本（状态字不再由单一 `not` 决定）。

第 2 条容易被忽略：代理 DLL 只改内存，但"关于"框里的伪造串会被用户手工抄进配置，
这属于持久化残留，重启不会消失。

## 十、限制与未验证项

| 项 | 状态 |
| :--- | :--- |
| 破解件在 28.40 上的完整行为 | `[observed]` 确认错位与崩溃，未做功能完整性评估 |
| 562 字节差异之外是否还有隐藏改动 | `[observed]` 逐段比对得出，未做重定位/资源层深比对 |
| 载荷是否具备反调试或环境检测 | `[unverified]` 未见相关指令，但未穷举 |
| 伪造串是否会被写入持久化配置 | `[inferred]` 由关于框可见性推断，未逐路径验证 |
| 三层加固在真实宿主上的实测 | `[unverified]` 规范给出 API 序列与期望值，未在目标上逐条跑通 |

这份材料里最值得带走的不是那四段覆写，而是它的失败方式：
**它把偏移当成常量，于是下一次构建就全错**。任何以偏移为交付物的方案，
都必须附带"如何在新版本上重新定位"的方法，否则它只是一次性的演示。
