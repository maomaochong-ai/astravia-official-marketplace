# 网页签名链：顺序、覆盖集与一次只改一个字段

> 案例类型：前端签名的还原与完整性复核／目标：一个每次请求都带签名的 Web 应用／脱敏：端点写 `<AUTH-SRV>`，密钥与令牌不落文档，样本哈希与常量一律以 `<实测值>` 出现。

---

## 一、现场

现场从一个对不上的响应对开始：抓到的请求原样重放，返回「签名错误」；把时间戳换成当前的，仍然「签名错误」；把整个请求体删掉只保留头，返回「参数缺失」。三条加起来说明签名的计算输入里既有请求体也有某个与时间有关的东西。

第二个观察来自 JS 的体积：主 bundle 有两万多行，其中大部分是打包器注入的运行时代码。直接用「搜索 sign」的办法只会命中断言函数和 UI 文案。有用的线索只有三个：

1. 头部名字（`x-sign` 一类）在 bundle 里出现的次数很少，一处是常量，一处是写入头的地方；
2. 请求构造函数附近总有一个把对象拍平成查询串的函数；
3. 存在一个看起来像十六进制常量的字符串字面量，长度超过常见哈希输出。

这三条本身就勾勒出了链的形状：取参数 → 排序 → 拼接 → 加常量 → 摘要 → 写头。真正的工作是把每一段的**具体规则**定下来，因为签名对规则极度敏感：键序换一个、编码方式换一个、参与字段少一个，结果全变，而服务端只回一句「签名错误」。

## 二、判定

把链拆成六段，其中四段有位置关系：

| 段 | 有位置 | 线索 | 缺了意味着 |
| --- | --- | --- | --- |
| collect | 是 | `Object.keys`、`URLSearchParams`、`params` 对象 | 输入不是对象拼装，可能是预格式化字符串 |
| order | 是 | `.sort()`、`join('&')`、`qs.stringify`、`encodeURIComponent` | 排序规则未知，应去断点看实际字符串 |
| secret | 否 | 长度达到密钥级别的十六进制/base64 常量 | 密钥在运行时取（登录响应或配置接口） |
| digest | 是 | `md5`、`sha1`、`sha256`、`hmac`、`createHash`、`subtle.digest` | 摘要在 WebAssembly 里，或签名由服务端下发 |
| attach | 是 | `x-sign`、`signature`、`authorization` | 值没有写进请求，可能被上层包装 |
| replay-guard | 否 | `nonce`、`timestamp`、`Date.now()` | 没有防重放，重放可能直接成立 |

「有位置」的意思是：这几段在源码里有先后关系，如果它们的偏移已经按 collect → order → digest → attach 递增，那么链可以从源码读出来，不必猜。`secret` 与 `replay-guard` 没有位置，因为常量声明在被打包器随手放置的位置，nonce 是载荷内容而不是步骤——把这两段也纳入顺序检查，会让任何真实 bundle 都判成「顺序不对」，从而把有意义的信号变成噪音。

判定句因此分三档：

- 四段位置齐全且递增 → 链可读，进入复现；
- 四段齐但顺序不递增 → 打包器内联了 helper，按 `order` 段的实际字符串去断点确认；
- 缺 `digest` 或缺 `secret` → 先回答「密钥/摘要从哪来」，再谈复现。

## 三、取证

```bash
cd tools
python3 sign_chain_scan.py --self-test
python3 sign_chain_scan.py --sample app.min.js --query x-sign
```

自检的第二行（`sign_chain_scan self test: 8/8`）跑在两个合成 bundle 上：完整的一个必须六段齐全且位置递增，残缺的一个必须把 `digest` 和 `secret` 报进 missing。第二行断言里还包含「渲染出的表头必须是 `| stage`」，这是防止工具退化成散文的手段——表格化的输出才能被逐行引用。

正式跑之后，记录里要有：

| 项 | 内容 | 为什么 |
| --- | --- | --- |
| 阶段表 | 段、是否有位置、命中数、首个偏移、命中的 token | 链骨架 |
| 顺序结论 | 位置段是否递增 | 决定「读源码」还是「去断点」 |
| 候选字段 | 排序调用附近 600 字节内的字段名字面量 | 这就是覆盖集 |
| 缺失段 | missing 列表 | 下一步该问什么 |

**覆盖集是这个案子最重要的产出。** 服务端能强制的只有「被签进去的字段」；一个不在覆盖集里的字段，改了签名照旧通过，那才是可报告的缺陷。工具只给出候选（排序调用前后的字符串字面量），最终覆盖集必须由「改一个字段再发一次」的实验确认——静态候选会漏掉动态拼进去的字段，也会多报只用于日志的键。

## 四、否证

**否证一：你找到的是诱饵。** 页面里常有两套摘要：一套用于埋点上报，一套用于业务签名。判据是「输出有没有写进请求头」。只算出值而没有写入路径的函数，是诱饵。

**否证二：还有第二段。** 复现出的值与真实头不一致，差一个固定前缀或后缀，说明还有一段（常见的是「先 HMAC 再拼设备指纹」或「对头部做二次摘要」）。判据是差异的形态：长度差固定、或前若干字节相同，都是第二段存在的证据。

**否证三：密钥其实不参与。** 有的实现把 `secret` 拼在末尾当盐，但真正被校验的只有「参数序列」本身。判据是「去掉 secret 重算，服务端是否仍接受」。如果接受，那么安全边界不是密钥，而是字段集合。

**否证四：密钥在 bundle 里就等于公开。** 如果签名密钥随包下发，那么这套签名只能防「随手改请求」，不能防「照着算法自己签」。把它写成「硬编码密钥」是弱结论；正确写法是「签名不构成对具备前端能力的对手的防护」，并另外核查服务端是否有别的强制。

**否证五：服务端根本不验签。** 把签名头删掉或改成随机值，如果仍然 200，那么整个链不重要，重要的事实是「完整性校验缺失」。这一条必须实测，不能从源码推断——有些网关只在特定版本或特定路由上验签。

**否证六：重放成立不一定是缺陷。** 如果请求体里带一次性业务单号、且服务端对单号做幂等，那么重放不会造成后果。判据是重放两次的业务结果，不是两次的状态码。

## 五、复现

**步骤一：取函数。** 从 bundle 里把 `order`、`digest`、`attach` 三段所在的函数抽出来，保持原样（不改写、不美化到丢语义）。记录它们所在的文件与偏移。

**步骤二：搭最小运行环境。** 只提供这三个函数需要的依赖：摘要库、序列化工具、以及被引用的常量。其余一律不引。目的是让「输入 → 输出」这条路径上不存在任何隐藏状态。

**步骤三：比对。** 用抓到的真实输入跑一次，与真实头的值逐字节比较：

| 输入 | 期望 | 实际 | 结论 |
| --- | --- | --- | --- |
| 抓包时的参数集 | 真实头 | `<实测值>` | 一致则链完整 |
| 同上但键序反转 | 不同值 | 与期望不同 | 证明排序是真规则 |
| 同上但少一个字段 | 不同值 | 不同 | 证明该字段在覆盖集内 |

**步骤四：变一个字段。** 选一个**不在**覆盖集里的字段（界面上的分页大小、排序方向一类），只改它，签名保持不变重发。服务端接受 → 该字段不受完整性保护，这就是可报告的结论；服务端拒绝 → 说明覆盖集比静态候选更大，回到步骤三补全。

一次只改一个字段，是因为批量改动之后无法归因。这一条纪律比任何工具都重要。

**步骤五：回滚与留存。** 复现脚本、输入、输出、以及「哪个字段被改过」的记录一起留存；不要把令牌、密钥、真实账号写进案例。脱敏要在抓包时就做，事后再改容易漏。

## 六、边界与遗留

- 只处理了范围内的一个应用、一个账号、一组端点；没有向 `<AUTH-SRV>` 发起范围外的请求。
- 复现脚本里的密钥一律替换为占位符，真实值随抓包一起销毁；文档里只保留「长度与算法」这类不构成凭据的事实。
- 如果摘要发生在 WebAssembly 里，本工具只会报 `digest` 缺失；此时应转到二进制侧分析，而不是宣布「没有签名」。
- 没有覆盖的：WebSocket 帧上的签名、以及在原生容器里由系统 API 完成的签名。
- 结论的措辞要守住一条线：「签名可被本地复算」是事实，「签名无效」是判断。后者需要服务端行为的证据，否则只能写成「签名不构成对本地对手的防护」。
