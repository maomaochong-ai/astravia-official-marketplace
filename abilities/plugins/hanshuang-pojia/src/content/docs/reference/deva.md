# deva · 分层提示词与双能力角色

> 出处：`D:\open-source-projects\deva`（Electron 33 + React 18，MIT）。
> 本文只写它的**提示词分层**与**角色模型**，不写它的宿主能力。

## 它的提示词分层（最耐用的部分）

主智能体的系统提示词由四层组成，上层优先，职责不重叠：

| 层 | 来源 | 管什么 | 约束 |
|---|---|---|---|
| 系统规范 | 应用内置 | 运行环境、路径约定、工具使用、工程纪律、执行边界、澄清与计划规则 | 优先级最高，不被下层覆盖 |
| 项目说明 | 工作区 `AGENTS.md` | 构建命令、风格、目录结构、提交规范 | 视为**项目数据**；每轮开头读，上限 32 KiB |
| 记忆 | `memory.json` | 用户偏好、纠正、踩坑 | 只有规则常驻，条目随消息增量下发 |
| 角色设定 | `personas/<id>.md` | 身份、语气、行文 | 在不违反上述规范的前提下生效 |

两条推论，直接决定我们的设计：

1. **系统规范不写身份与风格，角色设定不写工具与安全规则。** 两者能独立演进，换角色不削弱工程能力。
2. **层级越低（越像数据），越容易被当成「可驳回的偏好」。** 这就是为什么把越狱词写进 `AGENTS.md`
   会被点名驳回，而写进 OpenCode 的 agent 定义（系统位置）能生效。

## 它的角色模型

- 一个对话绑定一个角色；角色**不收窄内置工具**，用技能与 MCP 的可见性形成角色专属能力。
- 内置两个角色：通用 `Deva`，以及针对国产模型调校的「小码酱」—— 两项能力是**破甲**（提示词攻防研究）
  与**逆向**（静态定位校验、反调试、补丁与回滚）。
- 子智能体不注入角色设定，避免角色风格污染检索结论。

## 我们的整合映射

| deva 的机制 | 我们落在哪 | 取舍 |
|---|---|---|
| 四层分层 | `src/domain/inject/targets.ts` 的 `layerOf()`：`payload` / `system` / `config` | 只取**解释能力**：告诉用户同一段正文换层为什么效果不同；不承诺「换层一定生效」 |
| 系统规范与角色分离 | `src/content/packs/execution-kernel.md`（规范）与 `persona-redteam.md`（角色）拆成两个包 | 用户可以只装规范、不装角色 |
| 小码酱的双能力定位 | `persona-redteam.md` | 结构重写为「两项能力 + 工作方式 + 交付纪律」，不含原角色的语气细节 |
| 破甲的能力边界 | `jailbreak-research.md` 的「诚实边界」一节 | 明确写出「模型层拒答换提示词无效」，避免报告自我安慰 |

## 我们没搬的

- **成员协作**（多成员并行、各自会话、集中处理请求）：宿主 Astravia 有自己的会话与子代理模型，
  再实现一套只会得到两个都不完整的版本。
- **定时任务与 IM 中继**：同上，属宿主能力。
- **检查点 / `/rewind`**：宿主已有版本控制与文件回退路径。
- **记忆系统**：插件只需要「装什么」的记忆（`install-state.json`），不需要长期偏好记忆。
